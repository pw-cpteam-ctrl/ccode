# influencer-board — 인플루언서 응대 보드 (계획서)

> 이 문서가 이 프로젝트의 설계도다. 구조(배포·데이터)를 바꿀 일이 생기면
> 코드보다 이 문서를 먼저 고친다. 화면 배치 같은 세부는 프로토를 보며 정한다.

## 0. 왜 만드나

메가하우스 인플루언서 응대에 1인당 약 2시간이 든다. 병목은 메일 작성이 아니라
- 정보가 세 군데(접수 현황 / 웍스 메일함 / NotebookLM)로 흩어져 매번 다시 모으는 것
- 쿠폰 발급(건당 약 10분)을 위해 정보를 손으로 옮겨 적는 것

이 보드는 **판단에 필요한 정보를 한 화면에 모아 주는 것까지만** 한다.
선정 확정·초안 피드백·리워드 예외 처리 같은 판단은 사람이 한다.

## 1. 세 갈래 구조

| 트랙 | 폴더 | 누가 보나 | 이번 작업 후 |
|---|---|---|---|
| 크리에이터 가이드 | `creator-guide/` | 크리에이터 | 가이드·챗봇·**접수 받기**만 남는다. 관리자 화면은 빠진다 |
| 인플 보드 (신규) | `influencer-board/` | 담당자 | 관리자 화면을 옮겨 와서 출발점으로 삼고 기능을 더한다 |
| 업로드 보드 | `mh-upload-board/` | 담당자 | 손대지 않는다 |

폴더끼리 파일을 불러 쓰지 않는다(CLAUDE.md 3번). 필요한 코드는 복사해서 각자 갖는다.

## 2. 데이터 — 위치는 그대로, 읽고 쓰는 쪽만 바뀐다

- 접수 데이터는 지금처럼 **비공개 저장소 `creator-logs/`** 에만 둔다. 옮기지 않는다.
- 크리에이터 제출(`rewards-*.jsonl`)은 계속 가이드 쪽 서버가 쓴다.
- 확정·보관·수령 방식 변경·오픈일·접근 차단 기록은 인플 보드 쪽 서버가 읽고 쓴다.
  (`confirmed.json`, `archived.json`, `track-override.json`, `open-days.json`, `admin-guard.json`)
- 가이드는 오픈일을 지금처럼 `/api/open-days`로 **읽기만** 한다 → 인플 보드에서 바꾼
  오픈일이 가이드에도 그대로 반영된다. 인스타 카드 생성기(insta-gen)도 영향 없음.
- 브라우저에는 개인정보(네이버 ID 등)를 저장하지 않는다. 관리자 코드 기억만 지금처럼.
- 새 칸이 생기면 기존 파일을 고치지 않고 **새 파일을 나란히 추가**하고, 읽을 땐
  없으면 빈 값으로 본다(하위호환, CLAUDE.md 8번).

## 3. 배포

- **새 Vercel 프로젝트** 하나. 루트 폴더 = `influencer-board`.
  이 폴더가 바뀔 때만 재배포되게 막는다(가이드와 같은 방식).
- 환경변수는 가이드 프로젝트와 **같은 이름·같은 값**:
  `ADMIN_PASSWORD`, `GITHUB_TOKEN`, `GITHUB_OWNER`, `GITHUB_REPO`, `GITHUB_LOG_BRANCH`
- 페이지 문구는 존댓말.

### 사용자가 준비할 것 (내가 대신 못 하는 부분)
1. Vercel에서 새 프로젝트 만들기(저장소 `ccode`, Root Directory `influencer-board`)
2. 위 환경변수 5개를 Vercel 대시보드 → Settings → Environment Variables에 입력
   (값은 채팅에 적지 말 것 — 가이드 프로젝트 설정 화면에서 보고 옮겨 적기)
3. 정해진 주소를 알려주기

## 4. 옮기는 순서 — 끊기는 시간 없이

1. 새 폴더에 관리자 화면·서버 코드 복사 → 새 주소에서 **기존과 똑같이 동작**하는지 확인
2. 루트 허브(`index.html`)의 "접수 현황" 카드 링크를 새 주소로 교체
3. 확인되면 가이드에서 관리자 화면·`api/admin.js`를 제거하고,
   옛 주소(`/reward-view-admin`)로 들어오면 새 주소로 넘겨준다(즐겨찾기 깨짐 방지)

1이 확인되기 전에는 3을 하지 않는다. 그 사이엔 두 주소가 같은 데이터를 본다.

## 5. 기능 — 1단계 (프로토 범위)

### ① 회차별 진행 현황  — 새 입력 없음
- 회차 = 오픈 월. 초안 예정일로 어느 회차인지 자동 계산(지금 로직 재사용).
- 크리에이터별 단계: 접수 → 초안 대기(D-day) → 업로드 확인 → 1차 지급 → 정산 → 완료
  (지금 있는 업로드 확인·지급 상태 값으로만 판단)
- 회차를 나란히 놓고 **이전 회차 정산(오픈 +40일)** 과 **이번 회차 초안 기간**이
  겹치는 주를 강조.

### ② 쿠폰 발급 목록  — 새 입력 없음
- 대상: 지급일이 다가왔거나 지났는데 아직 지급 표시가 안 된 건
- 칸: 네이버 ID / 활동명 / 차수 / 쿠폰 유형 / 금액 또는 상품 / 지급 예정일
- 금액 표시 규칙:
  - 선지급 1차 → 5만
  - 선지급 2차 → 5만 (750↑ 확인 필요)
  - 후지급 → 5만~10만 (정산 후 확정)
  - 상품 쿠폰 → 금액 대신 희망 상품
- 출력: 표 복사(노션·시트 붙여넣기) + CSV 내려받기(나중에 브라우저 자동 입력용)
- 발급 끝나면 기존 "지급 표시"를 누르는 것으로 목록에서 빠진다.

### ③ 노션 백업
- 회차가 끝나면 그 회차 전체를 노션에 붙여넣을 표로 복사(기존 "표 전체 복사" 확장).
- 노션 자동 연동은 하지 않는다. 써보고 붙여넣기도 번거로우면 그때 검토.

## 6. 하지 않는 것 / 나중에

- **원장 칸 추가(메모·링크·사유)**: 원본이 노션에 있어 이중 입력이 된다. 1단계 제외.
  "페이지에서 일하고 노션은 백업" 방식이 자리 잡은 뒤 필요한 칸만 다시 판단.
- **선정 체크리스트·탈락 기록**: 브라우저 AI 결과 형식을 본 뒤, 붙여넣기 한 번으로
  받는 구조로 설계. 기준: 팔로워 규모 / 브랜드 논란 소지 / 수위성 콘텐츠 / 심한 욕설 / 캐릭터 비하.
- **메일 추출 파일 반영**: 추출 파일 샘플을 받은 뒤 설계.

## 7. 작업 단위 (커밋 하나씩)

1. 계획서 (이 문서)
2. 관리자 화면 + 서버 코드를 새 폴더로 복사, 배포 설정 — 기존과 동일 동작
3. ① 회차별 진행 현황
4. ② 쿠폰 발급 목록
5. ③ 노션 백업 복사
6. 허브 링크 교체 + 가이드에서 관리자 화면 제거·옛 주소 넘겨주기 (새 주소 확인 후)

각 단계는 Playwright로 화면을 실제로 눌러 확인(서버 응답은 가짜 데이터로 대체)한 뒤 보고한다.
푸시는 매번 확인받고 한다.
