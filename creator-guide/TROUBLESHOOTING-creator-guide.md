# TROUBLESHOOTING - creator-guide

이 프로젝트에서 실제로 겪은 문제와, 그때 **뭘 잘못 판단했는지**를 남긴 문서.
같은 증상이 다시 나왔을 때 처음부터 다시 헤매지 않기 위한 것이므로,
"이렇게 하면 된다"보다 **"이렇게 판단하면 틀린다"** 를 더 크게 적는다.

작업을 시작하는 세션(사람이든 AI든)은 배포·반영 관련 작업 전에 이 문서를 먼저 읽는다.

---

## 🚨 가장 먼저 — 배포 반영 확인은 이 방법으로만 한다

### 올바른 방법

`index.html` 안의 `styles.css?v=NN` 번호를 올려서 커밋하고, **라이브에서 그 번호를 직접 읽는다.**

```
# 1) 번호 올리기 (예: 34 → 35)
#    creator-guide/index.html 의 <link rel="stylesheet" href="styles.css?v=NN" />

# 2) 커밋·푸시 후 라이브에서 확인
curl -sS "https://pw-creator-guide.vercel.app/?cb=$RANDOM" | grep -o 'styles.css?v=[0-9]*'
```

여기 나오는 번호가 방금 올린 번호와 같으면 **배포가 실제로 반영된 것**이다.
`index.html`은 암호화되지 않고 그대로 서빙되므로, 이 값은 추정이 아니라 실제 값이다.

보통 푸시 후 **30초 ~ 2분** 안에 바뀐다. 5분이 지나도 안 바뀌면 아래 "배포가 안 돌 때"로 간다.

### 절대 쓰면 안 되는 방법 — 잠긴 본문 파일의 크기 대조

```
# ❌ 이렇게 판정하면 틀린다
curl -sI https://pw-creator-guide.vercel.app/locked/megahouse.enc | grep content-length
```

**왜 틀리는가**

- 배포되는 본문은 암호화돼 있어서(`locked/megahouse.enc`) 내용을 직접 읽을 수 없다.
  그래서 "파일 크기가 같으면 같은 내용"이라고 대조하고 싶어진다.
- 그런데 이 파일은 내용을 base64라는 방식으로 바꿔 담는데, 이 방식은 **3바이트 단위로
  묶어서 저장**한다. 그래서 원문에서 한두 글자만 바뀌면 **파일 크기가 전혀 변하지 않는다.**
- 실제로 2026-09-03의 서로 다른 커밋 3개(`aa4114f`, `90402a1`, `03863c7`)를 각각
  빌드해보면 크기가 전부 **150655바이트로 똑같이** 나온다. 크기로는 구분 자체가 불가능하다.

**이 방법으로 판정했다가 벌어진 일**: 반영되지 않은 배포를 "바이트 단위로 일치하니 최신"
이라고 두 번 잘못 보고했고, 사용자가 옛날 화면을 계속 보면서 같은 지적을 반복하게 만들었다.
크기 대조는 "완전히 다른 버전인지"를 가릴 때만 참고용으로 쓰고, **최신 여부 판정에는 쓰지 않는다.**

### "푸시 완료"는 완료가 아니다

이 프로젝트에서 가장 자주 반복된 실수다. `git push`가 성공해도 라이브는 그대로일 수 있다
(아래 배포 한도 문제 때문). **푸시했다는 사실만으로 "반영됐다"고 보고하지 않는다.**
위의 번호 확인까지 끝낸 뒤에 결과를 말한다.

## 배포가 안 돌 때 — 하루 배포 횟수 한도

### 증상

- 커밋·푸시는 정상인데 라이브가 몇 시간째 옛날 내용
- Vercel 배포 목록(Deployments)에 **해당 커밋이 아예 안 보임** — 실패도 취소도 아니고 없음
- 배포 도구로 직접 올리면 이런 오류가 뜬다
  ```
  Error: Resource is limited - try again in 24 hours
  (more than 100, code: "api-deployments-free-per-day")
  ```

### 원인 구조 (이걸 모르면 엉뚱한 데를 고치게 된다)

- 이 저장소(모노레포) 하나에 **Vercel 프로젝트가 7개** 붙어 있다
  (`creator-guide`, `insta-gen`, `b2b-scraper`, `sns-report-scraper`,
  `product-sns-formatter`, `inbound-image-composer`, `code-handoff-package`)
- 그래서 **커밋 1개를 올리면 배포가 7개 만들어진다.** 6개는 "내 폴더는 안 바뀌었다"며
  1초 만에 취소되지만(`vercel.json`의 `ignoreCommand`), **취소된 것도 하루 100회에 포함된다.**
- 챗봇에 문의가 들어올 때마다 문의 로그가 커밋으로 올라간다
  (`creator-logs/questions-YYYY-MM.jsonl`). 이것도 한 건당 7회를 소모한다.
- 즉 **하루 커밋 15개 정도면 한도에 닿는다.**

### 한도는 24시간 롤링이다 (자정 리셋이 아니다)

"내일 자정에 초기화된다"고 가정하면 틀린다. 지난 24시간 안에 몇 개를 썼는지를 계속 세는
방식이라, **오래된 배포가 24시간을 지나 빠지는 만큼 조금씩 여유가 생긴다.**

2026-09-03에는 오전에 한도가 찼고, **같은 날 저녁 무렵에 이미 풀려서 자동 배포가 정상
동작했다.** 그런데 "내일 아침에나 풀린다"고 단정하고 확인하지 않아, 이미 반영된 것을
하루 더 기다리게 만들었다. 막혔다고 판단했으면 **몇 시간 뒤에 다시 확인한다.**

### 대응 — 급할 때 우회 배포 (사용자 컴퓨터에서, Windows)

Vercel 배포 도구로 직접 올린다. **한 줄씩** 실행한다(여러 줄을 한 번에 붙여넣으면
중간에 `y`를 묻는 자리에 다음 줄이 들어가서 취소된다).

```
npm i -g vercel
```
```
vercel login
```
```
cd C:\Users\Brain\ccode\creator-guide
```
```
git pull origin main
```
```
vercel --prod
```

- 접속 코드(`GUIDE_PASSWORD`)는 Vercel 서버에 등록돼 있어 따로 입력할 필요 없다
- 이 우회 배포도 하루 100회 한도를 똑같이 소모한다 — 한도에 걸린 상태면 이것도 막힌다
- **주의**: 이렇게 올리면 Windows 줄바꿈 문자 때문에 배포 파일이 서버 빌드보다
  2~3KB 커진다. 내용은 같지만, 크기로 대조하면 또 헷갈리게 된다 (그래서 위의
  번호 확인 방법을 쓴다)

### 근본 대책 (미적용)

요즘 손대지 않는 프로젝트 5개의 저장소 연결을 끊으면 커밋당 배포가 7개에서 2개로 줄어든다.
**Vercel → 해당 프로젝트 → Settings → Git → Disconnect.**
연결을 끊어도 이미 배포된 사이트는 그대로 살아 있고, 나중에 그 프로젝트를 작업할 때
다시 연결하면 된다.

대상: `b2b-scraper`, `sns-report-scraper`, `product-sns-formatter`,
`inbound-image-composer`, `code-handoff-package`

## 오진 기록 — 배포가 안 될 때 이렇게 판단해서 틀렸다

2026-09-03에 실제로 밟은 잘못된 경로. 같은 길로 다시 가지 않기 위해 남긴다.

| 잘못된 판단 | 왜 틀렸나 |
|---|---|
| "GitHub 앱 권한에서 이 저장소가 빠졌다" | 권한 문제였다면 직전 커밋도 안 떴어야 하는데, 04:43 커밋은 정상으로 찍혀 있었다. 시간표를 먼저 봤으면 걸러낼 수 있었다 |
| "다른 프로젝트는 배포되니 한도가 아니다" | 그 배포가 마지막 남은 몇 개를 쓴 것이었다. 다른 프로젝트가 된다고 한도가 아닌 게 아니다 |
| "Git 연동이 끊겼으니 재연결하자" | 연결은 멀쩡했다. 끊었다 다시 붙이는 동안 오히려 배포가 더 안 됐다 |
| "프로젝트가 일시정지(Pause)됐다" | 그런 상태가 아니었다 |
| "파일 크기가 일치하니 최신이다" | 크기로는 구분이 안 되는 값이었다 (위 참조) |

**진단 순서** — 배포가 안 될 때는 이 순서로 본다.

1. Vercel Deployments 목록에 그 커밋이 **찍혔는지 아닌지**부터 본다
   - 안 찍혔다 → 배포가 만들어지지도 않은 것 → **한도를 먼저 의심한다**
   - 찍혔는데 Canceled → `ignoreCommand`가 건너뛴 것 (폴더 밖 변경이면 정상)
   - 찍혔는데 Error → 빌드 로그를 본다
2. 한도가 의심되면 배포 도구로 한 번 실행해본다 — 한도면 오류 문구에 그대로 나온다
3. 원인을 모르는 채로 **트리거 커밋을 반복해서 올리지 않는다.** 커밋 1개가 배포 7개를
   소모하므로, 안 그래도 부족한 한도를 더 태운다 (실제로 이걸로 한도를 앞당겨 채웠다)

## 라이브 화면을 직접 열어볼 수 없다는 제약

라이브 페이지는 접속 코드로 잠겨 있고, 코드는 Vercel 환경변수(`GUIDE_PASSWORD`)에만
있어서 저장소 어디에도 없다 (`ACCESS-creator-guide.md` 참조). 그래서 작업 세션이
라이브 화면을 열어 눈으로 확인하는 것은 **불가능하다.**

그래서 검증은 이렇게 나눠서 한다.

- **화면이 제대로 그려지는지** → 로컬에서 확인한다
  ```
  cd creator-guide && python3 -m http.server 8913
  # 브라우저(Playwright)로 http://localhost:8913/index.html 접속
  # 이벤트 페이지는 #event 를 붙여야 열린다 (메뉴에 링크 없음)
  ```
  로컬에는 `.jsx` 파일이 그대로 있어서 잠금 없이 바로 열린다.
- **그 화면이 라이브에 올라갔는지** → 위의 `styles.css?v=NN` 번호로 확인한다
- **내용까지 라이브에서 맞는지** → 확인할 수 없다. 이건 **사용자에게 부탁해야 한다.**
  이 한계를 숨기지 말고 "여기까지는 확인했고, 실제 문구는 열어서 봐달라"고 명확히 말한다

## 기타 자주 걸리는 것

### 이벤트 페이지가 안 열린다

메뉴에 링크가 없다. 주소 뒤에 `#event`를 직접 붙여야 열린다 (의도된 동작).
챗봇이 출처로 안내할 때도 이 경로로 이동한다.

### 로컬 서버를 띄웠는데 404

Bash 도구는 명령 사이에 작업 폴더가 초기화되므로, 서버를 띄운 폴더가 저장소 루트인지
`creator-guide`인지 헷갈리기 쉽다. 띄운 직후 반드시 확인한다.

```
cd /home/user/ccode/creator-guide && (nohup python3 -m http.server 8913 >/dev/null 2>&1 &) ; sleep 2
curl -s -o /dev/null -w "%{http_code}\n" http://localhost:8913/index.html
```

### 챗봇을 코드에서 못 찾겠다

`ChatWidget`이라는 이름은 이 프로젝트에 없다. 실제 이름은 `ChatBox`(대화 본체)와
`FloatingChatDock`(떠 있는 버튼 + FAQ 공용 UI)이다. 이름만 보고 "챗봇이 빠졌다"고
판단한 적이 있다.

### 브라우저 자동화가 안 뜬다

이 환경에서는 실행 파일 경로를 직접 지정해야 한다.

```js
chromium.launch({ executablePath: '/opt/pw-browsers/chromium' })
```

React·Babel은 외부 주소에서 받아오므로, 로컬 검증 시 `.vendor-cache` 폴더의 파일로
가로채서 넣어준다.
