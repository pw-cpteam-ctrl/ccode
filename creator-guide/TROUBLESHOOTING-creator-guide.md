## A. 배포와 라이브 반영

### A-0. 배포 반영 확인은 이 방법으로만 한다

**올바른 방법** — `index.html` 안의 `styles.css?v=NN` 번호를 올려 커밋하고,
**라이브에서 그 번호를 직접 읽는다.**

```
# 1) creator-guide/index.html 의 <link rel="stylesheet" href="styles.css?v=NN" /> 번호를 올린다
# 2) 커밋·푸시 후
curl -sS "https://pw-creator-guide.vercel.app/?cb=$RANDOM" | grep -o 'styles.css?v=[0-9]*'
```

나온 번호가 방금 올린 번호와 같으면 **배포가 실제로 반영된 것**이다.
`index.html`은 암호화되지 않고 그대로 서빙되므로 이 값은 추정이 아니라 실제 값이다.
보통 푸시 후 **30초~2분**이면 바뀐다. 5분이 지나도 그대로면 A-2로 간다.

**절대 쓰면 안 되는 방법** — 잠긴 본문 파일(`locked/megahouse.enc`)의 크기 대조

- 배포되는 본문은 암호화돼 있어 내용을 직접 읽을 수 없다. 그래서 "크기가 같으면 같은
  내용"이라고 대조하고 싶어진다.
- 그런데 이 파일은 내용을 base64 방식으로 담는데, 이 방식은 **3바이트 단위로 묶어서
  저장**한다. 원문에서 한두 글자만 바뀌면 **파일 크기가 전혀 변하지 않는다.**
- 실제로 2026-09-03의 서로 다른 커밋 3개(`aa4114f`, `90402a1`, `03863c7`)를 각각
  빌드하면 크기가 전부 **150655바이트로 동일**하게 나온다. 구분 자체가 불가능한 값이다.
- 이 방법으로 판정했다가, 반영되지 않은 배포를 "바이트 단위로 일치하니 최신"이라고
  **두 번** 잘못 보고했다. 사용자는 그동안 옛날 화면을 보며 같은 지적을 반복했다.

### A-1. "푸시 완료"는 완료가 아니다

이 프로젝트에서 가장 자주 반복된 실수다. `git push`가 성공해도 라이브는 그대로일 수 있다.
**푸시했다는 사실만으로 "반영됐다"고 보고하지 않는다.** A-0의 번호 확인까지 끝낸 뒤에
결과를 말한다.

### A-2. 하루 배포 횟수 한도 (2026-09-03)

**증상**

- 커밋·푸시는 정상인데 라이브가 몇 시간째 옛날 내용
- Vercel 배포 목록에 **해당 커밋이 아예 안 보임** — 실패도 취소도 아니고 없음
- 배포 도구로 직접 올리면:
  ```
  Error: Resource is limited - try again in 24 hours
  (more than 100, code: "api-deployments-free-per-day")
  ```

**원인 구조** (이걸 모르면 엉뚱한 데를 고치게 된다)

- 이 저장소(모노레포)에 **Vercel 프로젝트가 7개** 붙어 있다 — `creator-guide`,
  `insta-gen`, `b2b-scraper`, `sns-report-scraper`, `product-sns-formatter`,
  `inbound-image-composer`, `code-handoff-package`
- **커밋 1개를 올리면 배포가 7개 만들어진다.** 6개는 "내 폴더는 안 바뀌었다"며 1초 만에
  취소되지만(`vercel.json`의 `ignoreCommand`), **취소된 것도 하루 100회에 포함된다.**
- 챗봇 문의가 들어올 때마다 로그 커밋이 올라간다(`creator-logs/questions-YYYY-MM.jsonl`).
  이것도 한 건당 7회를 소모한다.
- 즉 **하루 커밋 15개 정도면 한도에 닿는다.**

**한도는 24시간 롤링이다 (자정 리셋 아님)**

지난 24시간 안에 몇 개를 썼는지를 계속 세는 방식이라, 오래된 배포가 24시간을 지나
빠지는 만큼 조금씩 여유가 생긴다. 2026-09-03에는 오전에 한도가 찼고 **같은 날 저녁에
이미 풀려 자동 배포가 정상 동작했다.** 그런데 "내일 아침에나 풀린다"고 단정하고 확인하지
않아, 이미 반영된 것을 하루 더 기다리게 만들었다. **막혔다고 판단했으면 몇 시간 뒤에
다시 확인한다.**

**근본 대책 (미적용)** — 요즘 손대지 않는 프로젝트 5개의 저장소 연결을 끊으면 커밋당
배포가 7개에서 2개로 줄어든다. Vercel → 해당 프로젝트 → Settings → Git → Disconnect.
연결을 끊어도 이미 배포된 사이트는 살아 있고, 나중에 다시 연결하면 된다.
대상: `b2b-scraper`, `sns-report-scraper`, `product-sns-formatter`,
`inbound-image-composer`, `code-handoff-package`

### A-3. 폴더에 변경이 없어 배포가 건너뛰어짐 (2026-08-31)

**증상** — 메인에 병합했는데도 "ANTHROPIC_API_KEY가 설정되지 않았습니다" 오류가 계속됨.
환경변수는 분명히 등록돼 있었다.

**원인** — 환경변수는 **새 빌드가 돌 때만 반영**되는데, `creator-guide/` 폴더에 실제
변경이 없어서 배포가 Skipped 처리되고 있었다. 즉 환경변수 문제가 아니라 빌드가 아예
안 돈 것.

**대응** — 폴더 안 파일에 실제 변경을 만들어 새 빌드를 강제로 돌린다
(A-0의 `styles.css?v=NN` 번호 올리기가 이 용도로도 쓰인다).

**구분** — A-2(한도)는 배포 목록에 **아무것도 안 뜨고**, A-3(스코프)은 목록에 뜨지만
**Canceled/Skipped**로 찍힌다. 목록을 먼저 보면 둘을 바로 구분할 수 있다.

### A-4. 결과물 위치 미지정으로 첫 배포 실패 (2026-08-31)

접속 코드 잠금을 도입하면서 빌드 명령을 넣었는데, 빌드 결과를 어디서 가져갈지
(`outputDirectory`)를 안 적어서 배포가 실패했다. `vercel.json`에 `"outputDirectory": "."`
추가로 해결.

### A-5. 급할 때 우회 배포 (사용자 컴퓨터, Windows)

**한 줄씩** 실행한다. 여러 줄을 한 번에 붙여넣으면 중간에 `y`를 묻는 자리에 다음 줄이
들어가서 취소된다 (실제로 그렇게 실패한 적 있음).

```
npm i -g vercel
```
```
vercel login
```
```
cd C:\Users\Brain\ccode\creator-guide
```
```
git pull origin main
```
```
vercel --prod
```

- 접속 코드(`GUIDE_PASSWORD`)는 Vercel 서버에 있어 따로 입력할 필요 없다
- **이 우회 배포도 하루 100회 한도를 똑같이 소모한다** — 한도에 걸려 있으면 이것도 막힌다
- 사용자 컴퓨터에 git 이름·이메일이 설정돼 있지 않으면 `git pull`이 도중에 멈춘다
  (`Please tell me who you are`). `git config --global user.email/user.name` 먼저.
- **주의**: 이렇게 올리면 Windows 줄바꿈 문자 때문에 배포 파일이 서버 빌드보다 2~3KB
  커진다. 내용은 같지만 크기로 대조하면 또 헷갈린다 (그래서 A-0의 방법을 쓴다)

### A-6. 오진 기록 — 배포가 안 될 때 이렇게 판단해서 틀렸다

2026-09-03에 실제로 밟은 잘못된 경로.

| 잘못된 판단 | 왜 틀렸나 |
|---|---|
| "GitHub 앱 권한에서 이 저장소가 빠졌다" | 권한 문제였다면 직전 커밋도 안 떴어야 하는데 04:43 커밋은 정상으로 찍혀 있었다. 시간표를 먼저 봤으면 걸러낼 수 있었다 |
| "다른 프로젝트는 배포되니 한도가 아니다" | 그 배포가 마지막 남은 몇 개를 쓴 것이었다. 다른 프로젝트가 된다고 한도가 아닌 게 아니다 |
| "Git 연동이 끊겼으니 재연결하자" | 연결은 멀쩡했다. 끊었다 붙이는 동안 오히려 더 안 됐다 |
| "프로젝트가 일시정지(Pause)됐다" | 그런 상태가 아니었다 |
| "파일 크기가 일치하니 최신이다" | 크기로는 구분이 안 되는 값이었다 (A-0) |

**진단 순서**

1. Vercel Deployments 목록에 그 커밋이 **찍혔는지 아닌지**부터 본다
   - 안 찍혔다 → 배포가 만들어지지도 않은 것 → **한도(A-2)를 먼저 의심**
   - 찍혔는데 Canceled → `ignoreCommand`가 건너뛴 것 (A-3, 폴더 밖 변경이면 정상)
   - 찍혔는데 Error → 빌드 로그를 본다
2. 한도가 의심되면 배포 도구로 한 번 실행해본다 — 한도면 오류 문구에 그대로 나온다
3. 원인을 모르는 채로 **트리거 커밋을 반복해 올리지 않는다.** 커밋 1개가 배포 7개를
   소모하므로 안 그래도 부족한 한도를 더 태운다 (실제로 이걸로 한도를 앞당겨 채웠다)

### A-7. 도메인 — 유료 도메인과 무료 주소는 별개 (2026-08-31)

`www.pw-creator-guide.app`을 등록하려다 "잘못된 구성" 오류. 원인은 그 도메인을 **구매하지
않은 상태**였던 것. `.app` 같은 유료 도메인과 Vercel 무료 주소(`.vercel.app`)는 별개이고,
무료 주소는 구매 없이 이름만 바꾸면 된다. 현재 주소는 `pw-creator-guide.vercel.app`.

## B. 검증 방식

### B-1. 라이브 화면을 직접 열어볼 수 없다 (구조적 제약)

라이브는 접속 코드로 잠겨 있고, 코드는 Vercel 환경변수(`GUIDE_PASSWORD`)에만 있어
저장소 어디에도 없다(`ACCESS-creator-guide.md`). 그래서 작업 세션이 라이브 화면을 열어
눈으로 확인하는 것은 **불가능하다.** 검증은 이렇게 나눈다.

- **화면이 제대로 그려지는지** → 로컬에서 확인 (로컬에는 `.jsx`가 그대로 있어 잠금 없이 열림)
  ```
  cd /home/user/ccode/creator-guide && (nohup python3 -m http.server 8913 >/dev/null 2>&1 &) ; sleep 2
  curl -s -o /dev/null -w "%{http_code}\n" http://localhost:8913/index.html
  # 이벤트 페이지는 http://localhost:8913/index.html#event
  ```
- **그 화면이 라이브에 올라갔는지** → A-0의 번호 확인
- **내용까지 라이브에서 맞는지** → 확인할 수 없다. **사용자에게 부탁해야 한다.**
  이 한계를 숨기지 말고 "여기까지 확인했고 실제 문구는 열어서 봐달라"고 명확히 말한다

### B-2. 스타일 값만 대조하고 "일치한다"고 말하면 틀린다 (2026-09-02)

GPT가 만든 개편안(v10)을 기존 파일로 옮긴 뒤 "레이아웃 일치한다"고 보고했으나, 화면은
달랐다. 스타일 값만 골라 비교했고 **실제로 그려지는 글과 구조는 대조한 적이 없었다.**

**바꾼 방법** — 두 버전을 각각 브라우저로 띄우고 7개 탭을 눌러가며 그려진 화면 구조를
통째로 비교(Playwright로 `.section` 텍스트 추출 후 diff). 그러자 01·02·03에서 놓친
차이가 나왔고, 06·07은 이미 일치한다는 것도 그때 확인됐다.

**교훈** — "일치"를 주장하려면 **사용자가 보는 것과 같은 층위**에서 비교해야 한다.
CSS 값, 파일 크기, 코드 diff는 사용자가 보는 것이 아니다.

### B-3. 05만 보고 "다 됐다"고 하지 않는다 (2026-09-02)

05 화면 차이를 고친 뒤 "일치한다"고 했으나 06도 달랐다. 지적받은 곳만 고치고 나머지는
확인하지 않은 것. **한 탭에서 문제가 나오면 나머지 탭도 같은 방식으로 전수 확인한다.**

### B-4. 저장된 값 때문에 "기본 선택"으로 보이는 것 (2026-09-02)

06 보상 탭이 "이미 선택된 상태로 보인다"는 지적에 "코드 초기값은 비어 있으니 기본 선택이
아니다"라고 답했는데, 이건 틀린 답이었다. 그 브라우저에 **24시간 안에 고른 값이 저장돼
있어 복원된 것**이고(`loadReply()`, `REPLY_KEY = 'cg-reply'`, TTL 24시간), 사용자 화면에서는
실제로 골라진 채 보이는 게 맞다.

**교훈** — 코드의 초기값과 사용자가 보는 화면은 다를 수 있다. "코드상으로는 아니다"는
답이 되지 않는다. 저장 기능이 있는 화면은 **새 브라우저 세션**으로 확인한다.

### B-5. 비교본 파일들이 서로의 저장값을 공유함 (2026-09-02)

before/after 비교용 단독 HTML 두 개를 만들어 전달했는데, 한쪽에서 고른 값이 다른 쪽에도
나타났다. 브라우저 저장소는 **주소 단위로 구분**되는데 둘 다 `file://`로 열려서 같은
저장 공간을 쓴 것. 비교본을 만들 때는 이 점을 감안하거나, 저장을 쓰지 않는 형태로 만든다.

### B-6. "다 훑었다"고 말하기 전에 (2026-09-03)

이벤트 문서에서 기한 표현을 정리하면서 "7일 관련 표현은 전부 봤다"고 보고했는데, 정작
"3일 이내" 규칙이 그대로 남아 있었다. 심지어 그 문장은 앞서 내가 직접 고치자고 제안했다가
되돌린 자리였다.

**교훈** — 특정 키워드만 검색해놓고 "전부 봤다"고 말하지 않는다. 범위를 말할 때는
**무엇을 기준으로 훑었는지**를 같이 밝힌다.

## C. 코드·구조 함정

### C-1. 챗봇을 코드에서 못 찾겠다 (2026-09-02)

`ChatWidget`이라는 이름은 이 프로젝트에 **없다.** 실제 이름은 `ChatBox`(대화 본체)와
`FloatingChatDock`(떠 있는 버튼 + FAQ 공용 UI)이다. 이름만 보고 "챗봇이 빠졌다"고
잘못 보고한 적이 있다.

`FloatingChatDock`은 화면에 **한 번만** 마운트된다(`inline={tab === 'faq'}`). 01~06에선
떠다니는 버튼, 07에선 본문에 박힌 형태로 **모습만** 바뀌기 때문에 두 자리 사이에서 대화
내용이 유지된다. 개별 탭 컴포넌트 안으로 옮기거나 두 번째 인스턴스를 만들면 이 성질이 깨진다.

### C-2. 접속 코드 잠금 구조를 깨뜨리지 않기

- `index.html`은 반드시 `<script type="text/babel" src="...jsx">` 형태로 외부 파일을
  불러와야 한다. 내용을 통째로 안에 넣은 단일 HTML로 바꾸면 잠금 파이프라인이 무너진다.
- 배포 시점에 `build-lock.js`가 그 스크립트들을 암호화해 `locked/*.enc`로 만들고
  `.jsx`는 배포본에서 지운다. 브라우저는 `gate.js`로 코드를 받아 직접 복호화한다.
- 접속 코드 값은 **저장소 어디에도 적지 않는다.** Vercel 환경변수에만 둔다.
- `GUIDE_PASSWORD`가 없으면 빌드가 일부러 실패한다 — 실수로 잠금 없이 공개되는 것 방지.

### C-3. `package.json` 추가로 기존 스크립트가 깨짐 (2026-08-07)

챗봇 패키지를 쓰려고 `package.json`을 만들면서 `"type": "module"`을 넣었는데, 그 순간
폴더 전체가 최신 문법 기준이 되어 먼저 만들어둔 `build-standalone.js`(구식 `require` 문법)가
실행되지 않았다.

**교훈** — 새 파일을 추가할 때 **이미 있는 스크립트에 미치는 영향**까지 같이 확인한다.

### C-4. 커밋 훅이 배포용 파일의 이미지를 시크릿으로 오탐 (2026-08-07)

오프라인 배포용 단일 파일에 이미지가 base64로 내장돼 있는데, 그 난수 문자열 안에서 우연히
구글 API 키 형태(`AIza` + 35자)가 만들어져 pre-commit 훅이 커밋을 막았다.

**대응** — `--no-verify`로 우회하지 않고 원인을 없앴다. 배포용 단일 파일은 원본에서 다시
만들 수 있는 파생물이므로 생성 스크립트(`build-standalone.js`)를 두고 결과물은
`.gitignore`로 제외했다.

**원칙** — 훅이 막으면 우회하지 않는다. 오탐이든 진짜든 원인을 사용자에게 설명하고
확인받은 뒤 조치를 정한다.

### C-5. 정의되지 않은 색 변수는 의도된 것일 수 있다

`.trk-detail li`가 쓰는 `--ink-650`은 이 프로젝트에도, 원본 v10에도 **정의가 없다**
(사용 2곳, 정의 0곳). v10 화면을 그대로 재현하기 위해 일부러 같은 상태로 두었고 코드에
그 이유를 주석으로 남겼다. "버그처럼 보인다"고 고치지 않는다.

### C-6. 나중에 오는 스타일 블록이 앞을 덮어쓴다 (2026-09-02)

v10은 기본 스타일 뒤에 **별도 블록**을 두어 테두리·배경을 걷어내는 구조였다. 이식할 때
앞부분만 가져오고 뒷블록을 빠뜨려 화면이 달라 보였다. 스타일을 옮길 때는 **같은 선택자가
뒤에서 다시 정의되는지**를 반드시 확인한다.

### C-7. 저장 스키마에 항목을 더할 때

브라우저에 저장된 예전 데이터에는 새 항목이 없다. 있다고 가정하고 읽으면 예전 데이터를
불러오는 순간 화면이 깨진다. `값 = 저장된값 ?? 기본값` 형태로 항상 기본값을 깔고,
기존 항목은 지우지 말고 나란히 추가한다.

## D. 도구·작업 환경

### D-1. 이벤트 페이지가 안 열린다

메뉴에 링크가 없다. 주소 뒤에 `#event`를 직접 붙여야 열린다 (의도된 동작).
챗봇이 출처로 안내할 때도 이 경로로 이동한다.

### D-2. 로컬 서버를 띄웠는데 404

Bash 도구는 명령 사이에 작업 폴더가 초기화되므로, 서버를 띄운 폴더가 저장소 루트인지
`creator-guide`인지 헷갈리기 쉽다. 띄운 직후 반드시 응답 코드를 확인한다 (B-1의 명령 참조).
백그라운드로 띄운 서버가 다음 명령에서 죽어 있는 경우도 있으니 매번 확인한다.

### D-3. 브라우저 자동화가 안 뜬다

이 환경에서는 실행 파일 경로를 직접 지정해야 한다.

```js
chromium.launch({ executablePath: '/opt/pw-browsers/chromium' })
```

React·Babel은 외부 주소에서 받아오므로, 로컬 검증 시 `.vendor-cache` 폴더의 파일로
가로채서 넣어준다 (`ctx.route('**://unpkg.com/**', ...)`).

### D-4. 외부 파일 내려받기

이 환경의 `fetch`는 프록시 설정을 따르지 않는다. `build-standalone.js`가 `curl`을 쓰는 게
그 이유다. 과거 "이 환경은 CDN 접속이 막혀 있다"고 진단한 적이 있는데 **틀렸다** —
브라우저만 막혀 있었고 명령줄로는 받아진다.

## E. 진행 방식에서 반복된 실수

기술 문제가 아니라 **일하는 방식**에서 반복된 것들. 이쪽이 사용자를 더 많이 지치게 했다.

| 실수 | 어떻게 할 것 |
|---|---|
| 요청받지 않은 문장을 임의로 추가하거나 다른 위치로 옮김 | 옮길 만하다고 판단돼도 옮기지 않는다. "이 문장이 없어지는데 어떻게 할까"만 묻는다 |
| 고칠 내용을 확인받기 전에 바로 반영 | 문구 변경은 **before/after를 먼저 보여주고** 승인 후 반영한다 |
| 시키지 않은 스크린샷 촬영 | 요청 없으면 찍지 않는다 (사용량 낭비) |
| 선택지를 팝업창으로 물어봄 | 채팅으로 묻는다 |
| "푸시할까요?"를 반복해서 물어봄 | 사용자가 때가 되면 요청한다. 반복해서 묻지 않는다 |
| 확인 없이 단정 — 저장 기간을 30일이라 했으나 실제 24시간, "이벤트 기간 상한은 없다"고 했으나 실제로는 프리오더 기간에 묶임 | 수치·규칙은 코드나 문서에서 확인한 뒤 말한다 |
| 문제만 나열하고 어떻게 할지는 안 냄 | 문제를 제기하면 **구체적인 before/after 안**까지 같이 낸다 |
| 같은 증상이 재신고될 때 앞서 고친 곳만 다시 봄 | 이미 정상으로 확인된 신호가 있는지부터 보고, 있으면 **손대지 않은 인접 코드 전체**를 처음부터 훑는다 |
| 내부 사정이 드러나거나 경고처럼 읽히는 문구 | 크리에이터에게 보이는 글은 회사 일정·처리 사정을 노출하지 않고, 부담 주는 표현을 피한다 |
