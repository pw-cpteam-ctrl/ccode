# creator-guide — 크리에이터 협업 가이드 + 문의 응대 챗봇

> **이 문서가 이 프로젝트의 설계도다.** 구현을 맡는 쪽(사람이든 AI든)은 이 문서에
> 적힌 구조를 그대로 따르고, 여기 없는 구조를 새로 만들지 않는다.
> 설계를 바꿔야 할 이유가 생기면 코드를 먼저 고치지 말고 이 문서를 먼저 고친다.

## 이 프로젝트가 하는 일

인플루언서·크리에이터 협업 가이드 페이지와, 그 가이드 내용만으로 답하는
문의 응대 챗봇. **목적은 실무자에게 오는 반복 문의를 줄이는 것.**

## 1. 폴더 구성

```
creator-guide/
├─ index.html              # 메가하우스 가이드 (진입점)
├─ brand2.html             # 굿스마일·부시로드 가이드
├─ shared.jsx              # 메가하우스 — 가이드 내용(데이터)
├─ finalOption.jsx         # 메가하우스 — 화면 렌더링
├─ styles.css              # 메가하우스 — 스타일
├─ shared-brand2.jsx       # 굿스마일·부시로드 — 가이드 내용(데이터)
├─ finalOption-brand2.jsx  # 굿스마일·부시로드 — 화면 렌더링
├─ styles-brand2.css       # 굿스마일·부시로드 — 스타일
├─ assets/                 # 가이드에 쓰는 이미지
├─ knowledge-megahouse.md  # 챗봇 지식 베이스 — 메가하우스
├─ knowledge-brand2.md     # 챗봇 지식 베이스 — 굿스마일·부시로드
├─ build-standalone.js     # 배포용 단일 파일 생성 스크립트
├─ standalone/             # ↑의 결과물 (git에 안 올림 — 언제든 다시 만들 수 있음)
├─ api/chat.js             # (예정) 서버리스 함수 — 챗봇 API 1개
├─ chat-widget.js          # (예정) 채팅 UI — 두 가이드가 공유
└─ vercel.json             # (예정) 이 폴더만 재배포되도록 제한
```

### 배포용 단일 파일 만들기

```
node creator-guide/build-standalone.js
```

원본(html·jsx·css·이미지)에 React·Babel·웹폰트까지 전부 한 파일에 넣어
`standalone/` 에 만들어 준다. 인터넷 없이 열리고, 메신저로 파일 하나만 보내도
된다. Netlify에는 이 결과물을 올린다.

**결과물은 git에 올리지 않는다.** 파일당 8MB이고 원본에서 언제든 다시 만들 수
있는 파생물이라, 커밋마다 쌓이면 저장소만 무거워진다. 가이드를 고쳤으면
위 명령을 다시 실행해서 새로 만들면 된다 — 예전처럼 손으로 동기화할 필요가 없다.

두 브랜드 버전은 데이터·렌더링·스타일 파일이 완전히 분리되어 서로 영향이 없다.

## 2. 절대 원칙 (구현 시 어기면 안 되는 것)

### 2-1. 지식 베이스에 없는 내용은 답하지 않는다
추측·창작 금지. 답을 모르면 정해진 문장으로만 답한다:

> `확인이 필요한 내용이라 제가 답변드리기 어렵습니다. 담당자에게 문의 부탁드립니다.`

### 2-2. 답변에는 항상 출처(탭 이름)를 붙인다
사람이 검증할 수 있어야 한다. **그리고 이 규칙은 프롬프트가 아니라 코드로 강제한다**
— 2-5 참고.

### 2-3. 브랜드는 분리하되, 코드는 하나만 만든다
보상 조건이 완전히 달라서 지식이 섞이면 오답이 난다. 하지만 **API 파일을 두 개
만들지 않는다.** `api/chat.js` 하나가 `brand` 값(`megahouse` | `brand2`)을 받아
해당 지식 파일을 읽는 구조로 간다. 코드 복제는 두 배의 버그를 만든다.

### 2-4. 매 요청을 새로 시작한다 (stateless)
규칙과 지식은 **매 요청마다 파일에서 다시 읽어 조립**한다. 대화가 길어지며 규칙이
흐려지는 것을 막기 위함이고, 규칙 변경은 대화가 아니라 파일 수정으로만 반영된다.

단, 후속 질문("그럼 그건 언제 받아요?")은 앞 대화를 알아야 답할 수 있으므로
**직전 대화 3턴(질문·답변 6개)까지만** 프론트가 같이 보낸다. 그 이상은 보내지 않는다.

### 2-5. 검증 가능한 것은 코드가 판단한다
"모르면 모른다고 한다"를 프롬프트로만 시키면 지켜지지 않는 날이 온다. 코드로 막는다:

```
AI 답변을 받은 뒤:
  답변에 "출처:" 가 없고            → 정해진 "확인이 필요한 내용" 문장으로 교체
  동시에 정해진 fallback 문장도 아니면
```

지식 베이스의 모든 답변에 `> 출처:` 가 붙어 있으므로, 출처 없는 답변은 곧
**지식 베이스 밖에서 지어낸 답**이다. 이 한 줄이 이 프로젝트의 안전장치다.

## 3. 기술 결정 (근거 포함, 바꾸지 말 것)

### 3-1. RAG(문서 검색) 안 씀
지식 베이스가 파일당 1만 7천 자 수준이라 매 요청마다 통째로 프롬프트에 넣는 게
더 간단하고 정확하다. 검색이 실패해서 엉뚱한 답을 하는 경로 자체가 없어진다.

### 3-2. 프롬프트 캐싱을 반드시 켠다 — 그리고 순서를 지킨다
매 요청에 1만 자 넘는 지식을 넣으므로, 캐싱 없이는 비용이 10배 난다.

**캐싱은 "앞에서부터 글자가 똑같은 만큼"만 적용된다.** 그래서 순서가 전부다:

```
system:  [규칙 + 지식 베이스 전문]  ← cache_control 붙임 (매번 똑같아야 함)
messages: [직전 대화 + 이번 질문]    ← 매번 달라지는 것은 반드시 뒤에
```

**절대 하면 안 되는 것**: system 안에 오늘 날짜, 요청 ID, 사용자 이름처럼
매번 달라지는 값을 넣는 것. 한 글자만 달라져도 캐시가 통째로 깨져서 비용이
10배가 된다. 캐시가 도는지는 응답의 `usage.cache_read_input_tokens` 값이
0이 아닌지로 확인한다.

### 3-3. 모델은 운영자가 고른다 (기본값: Claude Haiku 4.5)
셋 다 이 작업에는 충분하다. 차이는 비용이다. 아래 4번 표 참고.
`claude-haiku-4-5`로 시작해서, 답변 품질이 아쉬우면 `claude-sonnet-5`로 올린다.
모델 ID는 코드 상단 상수 한 곳에만 두고 그 값만 바꿔 교체할 수 있게 한다.

⚠️ Haiku 4.5는 **4,096토큰 미만 프롬프트는 캐싱이 안 된다.** 우리 지식 베이스는
그보다 훨씬 크므로 문제없지만, 지식 파일을 크게 줄이는 일이 생기면 캐싱이
조용히 꺼질 수 있다는 점만 기억할 것.

### 3-4. 배포는 Vercel 서버리스
이 레포의 `insta-gen`과 같은 구조. API 키를 브라우저에 노출하지 않기 위해
서버를 거친다. `vercel.json`의 `ignoreCommand`로 이 폴더가 바뀔 때만
재배포되게 제한한다.

### 3-5. 공개 엔드포인트 보호
챗봇 API는 누구나 호출할 수 있는 주소가 된다. 방치하면 외부에서 계속 호출해
API 요금이 나갈 수 있다. `insta-gen/api/log-download.js`에 이미 있는
**동일 출처(same-origin) 검사**를 그대로 가져다 쓴다. 그 위에 간단한 길이 제한
(질문 500자 이내)을 더한다.

## 4. 비용 (1,000건 문의 기준, 캐싱 켠 상태)

질문 1건 = 지식 1.2만 토큰(캐시 읽기) + 질문 200토큰 + 답변 300토큰 가정.
환율 1,430원 기준의 **개략 추정치**이며, 실제 토큰 수는 구현 후
`count_tokens`로 한 번 실측해서 이 표를 갱신할 것.

| 모델 | 모델 ID | 1건당 | 1,000건 |
|---|---|---|---|
| **Haiku 4.5** (기본값) | `claude-haiku-4-5` | 약 4원 | **약 4,300원** |
| Sonnet 5 | `claude-sonnet-5` | 약 8원 | 약 8,300원 |
| Opus 5 | `claude-opus-5` | 약 21원 | 약 21,000원 |

캐싱을 안 켜면 위 금액의 **약 8~10배**가 된다. 3-2를 반드시 지킬 것.

## 5. 파일 수정 시 같이 고쳐야 하는 것 (동기화 규칙)

가이드 내용을 바꾸면 **연쇄로 고쳐야 하는 파일이 있다.** 하나라도 빠지면
"가이드에는 바뀌었는데 챗봇은 옛날 답을 하는" 상태가 된다.

| 바꾼 파일 | 같이 고쳐야 하는 것 |
|---|---|
| `shared.jsx` | `knowledge-megahouse.md` |
| `shared-brand2.jsx` | `knowledge-brand2.md` |

standalone 배포본은 `node creator-guide/build-standalone.js` 한 줄로 다시 만들면
되므로 이 표에 없다 — 손으로 맞출 필요가 없다.

이 수동 동기화가 이 설계의 **가장 약한 고리**다(아래 7번). 잊어버리는 걸 막기
위해, 구현 단계에서 `npm run check-sync` 한 줄로 "가이드가 지식 파일보다
나중에 수정됐는지" 확인하는 스크립트를 만든다.

필요하고, 8번은 나중에 지식 파일에 항목만 추가하면 되므로 구조에 영향이 없다.

## 7. 이 설계의 약점 (알고 가는 것)

1. **지식 베이스가 가이드의 복사본이다.** `shared.jsx`와 `knowledge-*.md`가
   같은 사실을 두 곳에 갖고 있어서, 한쪽만 고치면 어긋난다. 자동 생성으로
   바꾸지 않은 이유는 "사람이 실제로 물어볼 문장"으로 재구성하는 작업이
   기계적으로 안 되기 때문이다. 5번의 동기화 체크 스크립트로 방어한다.
2. **"모른다"를 100% 보장하지는 못한다.** 2-5의 출처 검사가 지어낸 답의
   대부분을 걸러내지만, 지식 베이스 내용을 조합해 그럴듯한 오답을 만드는
   경우까지는 못 막는다. 7번 항목(함정 질문 검증)이 이걸 재는 작업이다.
3. **범위를 일부러 좁혔다.** 대화 기억, 사용자 인증, 관리자 화면, 다국어는
   지금 만들지 않는다. 문의를 줄인다는 목적에 직접 기여하지 않는다.
