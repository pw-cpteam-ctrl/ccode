### FAQ 5개는 고정 답변 버튼으로, 나머지 질문은 수집
- **요청**: 확실히 정해진 질문까지 매번 AI를 부르는 게 낭비 아니냐는 문의
  - 고정 답변 방식이 좋다는 결론, 어떤 질문이 많이 들어오는지 수집도 요청
  - 수집 사실을 화면에 안 밝혀도 된다는 확인 받음
- **확인**: 문자열 매칭은 사람마다 표현이 달라 실효성 없음 → 버튼이면 이 문제 자체가 없어짐
- **처리**
  - 브랜드별 FAQ 5개를 버튼으로 구현(`CHAT_FAQ` 테이블, `sendPreset`)
  - 버튼 질문·직접 입력 질문 모두 서버에 기록(`api/log-question.js`)
  - 개인정보로 보이는 부분은 저장 전 자동 마스킹(`scrub()`)
  - 로그는 `creator-guide/` 폴더 밖 별도 폴더에 저장 — 질문마다 재배포되는 것 방지
    (`creator-logs/`)
  - "대화는 저장되지 않으니" 문구를 사실에 맞게 "새로고침하면 사라지니"로 수정
- **결과**: 두 브랜드 모두 브라우저로 확인 — FAQ 버튼은 AI 호출 없이 즉답, 직접 입력
  질문은 로그 정상 기록

### 메인 병합 후 배포가 반영되지 않던 문제
- **문제**: 병합 후에도 "ANTHROPIC_API_KEY가 설정되지 않았습니다" 오류 지속 (환경변수는
  등록됐다고 확인받음)
- **확인**: 환경변수는 정상, 원인은 배포 스코프 제한(`ignoreCommand`)
  - 이 폴더에 실제 변경이 없으면 재배포가 "Skipped" 처리됨
  - 환경변수는 새 빌드가 돌 때만 반영되는데, 그 빌드 자체가 건너뛰어지고 있었음
- **처리**: `api/chat.js`에 설명 주석 추가해 실제 변경 발생 → 새 빌드 강제 트리거
- **결과**: 정상 응답 확인 — 출처 포함 정답, 프롬프트 캐시 작동(`cache_read: 8798`),
  브랜드별 보상 안내 정상 분기, 로그 API 정상 기록

### 도메인을 직접 구매하지 않고 무료 주소로 변경
- **문제**: `www.pw-creator-guide.app` 등록 시 "잘못된 구성" 오류 (도메인 자체를
  구매하지 않은 상태였음)
- **확인**: 유료 도메인(`.app`)과 Vercel 무료 주소(`.vercel.app`)는 별개 — 무료 쪽은
  구매 없이 이름만 변경 가능
- **처리**: 후보 4개 조회 후 `pw-creator-guide.vercel.app`으로 변경
- **결과**: 변경 완료. 기존 주소(`ccode-mvhy.vercel.app`)는 더 이상 안 열림

### 접속 코드로 가이드 잠그기
- **요청**: 링크 무단 접근이 걱정돼 비밀번호 요청 — 브라우저 검사 방식, 코드 6개
  만들어두고 2개월마다 하나씩만 활성화
- **확인**: 정적 페이지라 "화면만 가리는" 방식은 소스 열면 본문이 그대로 보여 무의미
  - 본문 자체를 읽을 수 없게 변환해서 올리고, 코드가 맞을 때만 브라우저가 되돌리는
    방식으로 설계
- **처리**
  - 접속 코드 10자리 6개 생성 (대소문자·숫자 혼합, 헷갈리는 글자 `0/O`, `1/l/I` 제외)
  - 배포 시점에 본문(jsx)을 코드 기반으로 암호화(`build-lock.js`, PBKDF2 20만회 +
    AES-GCM)
  - 입력받은 코드로 브라우저가 직접 복호화·실행(`gate.js`) — 코드는 서버로 전송 안 함
  - 한 번 입력하면 30일간 기억
  - 코드를 모르는 방문자에겐 React·Babel(약 3MB) 미전송, 해제 후에만 로드
  - `GUIDE_PASSWORD` 미등록 시 배포 자체를 실패시켜 실수 공개 방지
  - 운영 방법은 `ACCESS-creator-guide.md`에 정리 (코드 값 자체는 기록 안 함)
- **결과**: Playwright로 확인 — 소스에 본문 없음, 틀린 코드 차단, 맞는 코드 정상
  렌더링, 새로고침 후 기억 유지, JS 오류 없음
  - 배포 첫 시도는 결과물 위치 미지정으로 실패(`outputDirectory` 누락), 수정 후
    재배포로 해결
  - 실사이트에서 원본 jsx 파일 5개가 전부 404(직접 접근 불가)로 바뀐 것까지 확인

### 디자인 세션에서 인수인계받은 가이드로 문의 응대 챗봇 만들기 시작
- **무슨 문제/요청이 있었나**: 인플루언서 문의가 너무 많아 실무자 업무 부담이 큰 상황.
  가이드는 이미 만들어져 있으나 zip 파일로만 존재해 저장소에 없었음. 앞으로 가이드를
  계속 손볼 예정이라 이 프로젝트 전체를 이어서 관리해달라는 요청
- **확인해보니**: 인수인계 파일은 브랜드 2종(메가하우스 / 굿스마일·부시로드)이고, 데이터
  파일과 렌더링 파일이 브랜드별로 완전히 분리돼 있어 서로 영향이 없는 구조였음. 가이드
  분량이 크지 않아 문서 검색(RAG) 없이 매 질문마다 전체를 AI에게 넘기는 방식이 더 간단하고
  정확하다고 판단
- **어떻게 처리했나**: `creator-guide/` 폴더를 만들어 파일 이관. 가이드 내용을 "사람이 실제로
  물어볼 문장" 형태의 질문·답변으로 재구성해 지식 베이스 2개 작성. 답변마다 어느 탭을 보면
  되는지 출처를 붙임
- **결과**: 메가하우스 40항목, 굿스마일·부시로드 30항목 작성 완료. 두 가이드를 브라우저로
  열어 7개 탭을 모두 클릭해 확인 — 렌더링·이미지(5/5)·핵심 수치 모두 정상, JS 오류 없음

### 가이드에 이미 있는 내용부터 먼저 챗봇에 넣기
- **무슨 문제/요청이 있었나**: 실제 문의 내역을 모으는 데 시간이 필요하니, 이미 가이드에
  있는 내용부터 먼저 넣어달라는 요청. 답변 형식은 "질문에 대한 답 + 몇 페이지 무엇을
  참조하라"는 식으로 출처가 같이 나오게 해달라는 것
- **확인해보니**: 가이드가 페이지가 아니라 탭 7개(01 진행 순서 ~ 07 FAQ) 구조여서, 페이지
  번호 대신 탭 이름을 출처로 쓰는 게 맞았음. 또한 FAQ 탭 맨 아래에 "FAQ에 없는 문의가
  있어요 — 아래에 작성 후 복사해서 담당자에게 전달해주세요"라는 입력창이 이미 있었음 —
  지금 실무자에게 문의가 쏟아지는 통로가 바로 이 자리
- **어떻게 처리했나**: 모든 답변에 `> 출처: 02 업로드 순서 탭` 형태로 탭 이름을 붙임.
  챗봇 UI는 새로 끼워 넣지 않고 이 기존 입력창 자리를 그대로 대체하기로 설계
- **결과**: 사용자가 이미 질문을 쓰던 자리가 답을 주는 자리로 바뀌는 구조로 확정.
  출처 표기는 이후 "지어낸 답 걸러내기" 장치로도 쓰게 됨(아래 항목 참고)

### 커밋이 훅에 막힘 — 배포용 파일의 이미지 데이터를 시크릿으로 오탐
- **무슨 문제/요청이 있었나**: 작업 결과를 커밋하려는데 커밋 전 검사(pre-commit 훅)가
  "시크릿으로 의심되는 패턴이 있다"며 차단함
- **확인해보니**: 진짜 유출이 아니라 오탐이었음. 오프라인 배포용 단일 파일에 이미지가
  base64(영숫자 난수 문자열)로 내장돼 있는데, 그 안에서 우연히 구글 API 키 형태
  (`AIza` + 35자)가 만들어진 것 (`.claude-hooks/pre-commit`의 시크릿 패턴 중
  `AIza[0-9A-Za-z_-]{35}`에 일치). PNG 헤더(`iVBORw0KGgo`) 뒤에 이어지는 데이터라
  실제 키가 아님을 확인
- **어떻게 처리했나**: `--no-verify`로 우회하지 않고 원인 자체를 없앰. 배포용 단일 파일은
  원본에서 다시 만들 수 있는 파생물이므로, 원본에서 생성하는 스크립트를 만들고
  (`build-standalone.js`) 생성물은 저장소에서 제외함(`.gitignore`). 이 과정에서 앞서
  "이 작업 환경은 CDN 접속이 막혀 있다"고 했던 진단이 틀렸음을 발견 — 브라우저만 막혀
  있었고 명령줄로는 받아져서, 포기했던 방식(React·Babel·웹폰트까지 전부 내장)이 가능했음
- **결과**: 생성된 두 파일을 브라우저로 열어 7개 탭 전부 확인 — 외부 요청 0건(인터넷 없이
  열림), 이미지 5/5 정상, 웹폰트 적용, JS 오류 없음. 인수인계 문서에 있던 "원본 수정 시
  배포본도 손으로 동기화 필요"라는 작업이 없어짐. 훅은 손대지 않았고 그대로 작동함

- **확인해보니**: 스스로 점검한 결과 문제 4건이 나옴 — ① 모델·비용을 실제 수치 확인 없이

  고르도록 확정. "지식 베이스의 모든 답변에는 출처가 붙어 있으므로, 출처 없는 답변은 곧
  지어낸 답"이라는 성질을 이용해 코드가 걸러내도록 설계(출처 없으면 정해진 안내 문장으로
  교체). 공개 엔드포인트 보호(동일 출처 검사)도 추가
- **결과**: `PLAN.md`를 구현 기준 설계도로 재작성. 이 설계의 약점 3가지(지식 베이스가
  원본의 복사본이라 수동 동기화 필요 등)도 숨기지 않고 문서에 명시함

  쓴다"고 모호하게 적어 의존과 참고가 구분되지 않았음 ⑤ 가이드 페이지 배포처가 정해지지

- **결과**: 허브 카드 추가는 보류함 — 가이드 본문에 "쿠폰·보상 금액 등 협업 조건은

  확인한 뒤 운영자가 판단하도록 남겨둠

### 공개 저장소 결정 및 챗봇 API·화면 구현
- **무슨 문제/요청이 있었나**: 저장소·배포가 공개라는 답을 받음. 그럼 카드가 뭘 말하는지
  다시 설명해달라는 요청이 있었고, 설명 후 카드는 넣지 않고 그대로 두기로 확정. 이어서
  실제 챗봇(API + 화면)을 만들어달라는 요청
- **확인해보니**: 저장소가 공개면 허브 카드를 안 넣어도 이미 커밋된 보상 금액(`shared.jsx`,
  `knowledge-megahouse.md` 등)은 주소만 알면 볼 수 있는 상태였음. 이 부분은 별도로
  안내하고 "그대로 둔다"는 결정을 받음
- **어떻게 처리했나**: `api/chat.js` 하나로 두 브랜드를 처리(brand 값으로 지식 파일만
  분기). 지식 베이스를 시스템 프롬프트에 넣고 캐시 표시(`cache_control`)를 붙여, 매번
  달라지는 대화·질문은 반드시 뒤에 오도록 구성. "지식 베이스의 모든 답변에는 출처가
  붙어있다"는 성질을 이용해, 답변에 출처가 없으면 코드가 정해진 안내 문장으로 바꿔치기하는
  안전장치(`groundAnswer`)를 별도 함수로 분리해 만듦. 외부 남용을 막기 위해 같은 출처에서
  온 요청만 받도록 검사(insta-gen의 로직을 복사, import는 안 함)하고 질문 길이도 500자로
  제한. 화면은 FAQ 탭 맨 아래 있던 기존 "문의 있어요" 입력창 자리를 챗봇으로 그대로 교체
  (`chat-widget.jsx`, `chat.css`) — Enter 전송, 대기 중 점 세 개 표시, 답변 옆 복사 버튼,
  출처를 누르면 해당 탭으로 이동, 실패해도 입력한 질문은 지우지 않음, 모바일 키보드 대응,
  처음 열었을 때 예시 질문 3개 노출까지 반영
- **결과**: 브라우저로 직접 조작해 14개 항목 확인 — 챗봇 렌더링, 예시 질문 클릭, 대기
  표시, Enter 전송, Shift+Enter 줄바꿈, 오류 시 입력 보존, 모르는 답변은 노란 배경으로
  구분, 출처 클릭 시 실제로 "02 업로드 순서 탭"으로 이동, 서버로 브랜드 값이 정확히
  전달됨. JS 오류 없음. API는 방어 로직 8종(GET 요청 거부, 외부 사이트발 요청 거부, 잘못된
  브랜드, 빈 질문, 501자 질문, 키 미설정 등) 확인했고, 마지막 "잘못된 키" 테스트는 실제로
  Anthropic 서버까지 도달해 SDK 연결과 지식 파일 읽기까지 같이 확인됨. 안전장치는 7가지
  입력(정상 답변·안내 문장은 유지, 출처 없는 답·빈 응답은 교체)으로 따로 검증함. 다만
  실제 API 키가 없어 답변 품질 자체는 아직 확인 못 함 — 키 등록은 요청해둔 상태

### package.json 추가로 배포 스크립트가 깨짐
- **무슨 문제/요청이 있었나**: 챗봇에 필요한 패키지(`@anthropic-ai/sdk`)를 쓰려고
  `package.json`을 새로 만들었는데, 이미 있던 배포용 파일 생성 스크립트를 돌리니 오류가 남
- **확인해보니**: `package.json`에 `"type": "module"`을 넣으면서 폴더 전체가 최신 문법
  기준으로 바뀌었는데, 먼저 만들어둔 `build-standalone.js`는 구식 문법(`require`)을 쓰고
  있어서 실행 자체가 안 됐음. 파일을 따로따로 만들다가 서로 영향을 주는 걸 놓친 것이
  원인 — 미리 못 잡은 이유는 새 파일을 추가할 때 이미 있는 스크립트에 미치는 영향까지
  같이 확인하지 않았기 때문
- **어떻게 처리했나**: `build-standalone.js`를 최신 문법(`import`)으로 고침
- **결과**: 다시 실행해서 정상적으로 배포용 파일 2개가 만들어지는 것까지 확인함
