## 2026-08-19

### 영어로 수집하다 보니 작품명이 틀린다 — 일본어로 바꿔야 하는지
- **무슨 문제/요청이 있었나**: 지금 영어 페이지에서 수집하는데 실무에서 불편이 생긴다며,
  일본어 페이지로 바꿔야 하는지 상의 요청. 팀원이 "일본어 원문으로도 수집 가능하냐"고
  물어본 상황이었고, 둘 다는 못 하고 하나를 골라야 하는지도 함께 물음
- **확인해보니**: 일본어판이 실제로 존재하고(`/b2b/ja` 정상 응답, `/b2b/jp`는 없음),
  주소에서 언어 부분만 바뀌는 구조라 **둘 다 받는 것도 가능**했음
  - 일본어가 유리한 것도 사실 — 한국 정식 제목은 일본어에서 번역된 것이라 `鬼滅の刃`는
    한자가 그대로 "귀멸의 칼날"이고, 영어 `Demon Slayer`는 아예 별개 작명이라 도달 불가
  - 그런데 **로케일을 갈아타면 조용히 깨지는 것들**이 있었음. 지금 코드가 화면의 영어
    라벨 글자를 찾아 값을 읽는 방식이라, 일본어 페이지에서는 라벨이 달라져 작품명·사양·
    제조사·발매월이 전부 빈 값이 됨 — 오류 없이 비어버림
  - 특히 위험한 건 성인 상품 제외 기능. 영어 문구(`adults 18 years of age`)로 판별하고
    있어서 일본어 페이지에서는 **필터가 통째로 안 먹게 됨**
- **어떻게 처리했나**: 로케일을 갈아타지 않고, 영어판을 기준으로 유지한 채 일본어
  페이지에서 **상품명·작품명 두 개만** 추가로 받아오게 함 (`extractJapaneseNames`)
  - 검증된 로직(성인 상품 판별, 발매월·사양·제조사 추출)은 손대지 않아 깨질 여지를 없앰
  - 일본어판이 없거나 느린 상품이 있어도 수집 전체를 실패시키지 않고 빈 값으로 넘어감.
    몇 건이 비었는지는 끝에 알려줘서 사이트 구조가 바뀐 걸 눈치챌 수 있게 함
  - 성인 상품은 이미 걸러진 뒤에만 일본어 페이지를 열어 불필요한 접근을 막음
  - 일본어 원제는 결과 파일에만 넣고 **AI에게 주는 원문에는 넣지 않음** — 영어와 일본어를
    한꺼번에 주면 둘을 섞은 엉뚱한 제목이 나올 수 있어서 AI 입력은 영어 기준을 유지함
    (`buildOutputProduct`의 `titleJa`·`workJa`는 `officialText`에서 제외)
- **결과**: 실제 사이트는 로그인이 필요해 자동 검증이 안 되므로, 같은 화면 구조의 가짜
  사이트(영어판·일본어판)를 세워 브라우저로 전체 흐름을 돌림. 4건 중 일본어 원제 2건이
  정상 수집되고, 일본어판이 없는 1건은 빈 값으로 넘어가며 안내 문구가 출력됨. 성인 상품
  1건은 기존대로 제외됐고, AI에게 가는 원문에 일본어가 섞이지 않은 것도 확인함
  - **팀원 PC에 반영하려면 업데이트 실행(`update.bat`)이 한 번 필요함**

## 2026-07-31

### 전날 저녁 6시에 공개되는 "다음날 상품"을 못 받아오던 문제 (팀원 신고)
- **무슨 문제/요청이 있었나**: 팀원이 써보니 굿스마일 상품은 **전날 18시에 다음날 것이 미리
  공개**되는데, 도구는 그날 것만 받아진다는 신고. 더해서 "오늘이 아니어도 과거나 미래나 특정
  날짜를 지정해서 받고 싶으면 어떻게 할 거냐"는 질문. 바로 만들지 말고 먼저 상의하라는 요청
- **확인해보니**: 받아올 상품을 고르는 기준이 **PC 시계의 오늘 날짜와 정확히 일치하는 것만**
  이었음. 그래서 29일 19시에 실행하면 화면에 이미 30일 상품이 올라와 있는데도 29일만 찾아서
  0건이 되거나 아침에 받은 것만 다시 잡힘 (상품 목록을 걸러내는 조건이 `오늘 날짜와 같은가`로
  고정, `todayYYYYMMDD()`). 그리고 상품 카드 자체에 **발표일이 데이터로 이미 박혀 있는 것**을
  확인함 (`data-guidance_date="20260730"`) — 즉 시계를 볼 필요가 없었음
  - 점검하다가 팀원이 신고하지 않은 버그를 하나 더 찾음: **결과 폴더 이름이 세계 표준시(UTC)
    기준**으로 만들어져서, 한국시간 오전 9시 이전에 실행하면 어제 날짜 폴더에 저장됨. 실제로
    계산해보니 한국시간 07-30 08:00 실행 → 받는 건 30일분인데 폴더는 `2026-07-29`로 어긋남
    (폴더 이름은 `toISOString()`(UTC), 상품 필터는 현지 시간 기준으로 서로 다른 시계를 씀)
- **어떻게 처리했나**: 상의 결과 "시계를 아예 안 보고, **사이트에 실제로 올라와 있는 발표일**을
  기준으로 한다"로 정함. "18시 넘으면 내일로 치기" 같은 시계 기반 추측은 공개가 늦어진 날
  없는 날짜를 찾아 0건이 되므로 채택하지 않음
  - `run.bat`(평소): 사이트에 올라온 **가장 최신 발표일**을 자동으로 받음 — 팀원 타이핑 0 유지
  - `run-pick-date.bat`(신규, 필요할 때만): 받을 수 있는 발표일을 건수와 함께 목록으로 보여주고
    번호로 고르게 함 (엔터만 치면 최신). 매일 쓰는 길에 "판단하는 순간"을 만들지 않으려고
    **분기를 프로그램 안이 아니라 "무엇을 더블클릭하나"로 올림**
  - 결과 폴더 이름을 **받은 발표일 그대로** 짓게 바꿔서 시계를 아예 쓰지 않게 함 — 위 UTC 버그가
    구조적으로 생길 수 없게 됨. 같은 날짜를 다시 받으면 같은 폴더가 갱신되고 다른 날짜분과
    섞이지 않음 (날짜 판단 로직을 브라우저와 분리해 `target-date.js`로 뺌)
  - 사이트에 없는 날짜를 지정하면 조용히 0건이 아니라, 이유와 함께 받을 수 있는 날짜 목록을
    보여주게 함. 결과 파일에 어느 발표일분인지도 기록 (`output.json`의 `guidanceDate`)
- **결과**: 실제 사이트 화면 구조를 흉내낸 가짜 사이트를 세워 브라우저로 전체 흐름을 돌려서
  검증함. **고치기 전 코드는 같은 상황에서 0건 + 실행일 폴더, 고친 후는 3건 발견 → 2건 저장
  (성인 상품 1건은 규칙대로 제외) + 발표일 폴더**로 확인됨. 날짜 판단 로직 단위 테스트 9건
  (입력 형식 여러 개 허용, 중복·불량 카드 제외, 시간대 무관), 날짜 지정·목록 선택·없는 날짜
  지정·같은 날짜 재실행까지 전부 통과. 다만 **로그인이 필요한 실제 사이트에서는 확인 못 했음**
  — 사이트 첫 화면에서 밀려난 오래된 날짜를 받을 수 있는지는 정찰 기록이 없어 미확인 상태로
  남겨두고 문서에 한계로 적음

### 업데이트할 때마다 사람이 파일을 손으로 복사해야 했던 문제
- **무슨 문제/요청이 있었나**: "업데이트될 때마다 내가 일일이 파일 교체해주는 게 귀찮은데,
  update.bat 하나 누르는 것처럼 안 되냐"는 요청
- **확인해보니**: 팀원 PC는 개발 저장소가 아니라 **별도 공개 저장소(`share`)**에서 코드를
  받아가는 구조였고, 개발 저장소에서 `share`로 옮기는 일을 사람이 매번 손으로 해야 했음.
  `share`를 따로 둔 이유는 용량이 아니라 **역추적 방지** — 팀원에게 개발 저장소 링크가 알려지면
  다른 프로젝트와 작업 이력이 전부 열리기 때문
  - 처음에 "둘 다 공개 저장소니 `share`를 없애자"고 제안했다가 철회함. 사용자가 이미 설명한
    이유(역추적 방지)를 놓친 잘못된 제안이었음
  - GitHub Action으로 자동 미러링하는 방법도 검토했으나 채택하지 않음 — 토큰이 필요하고 그
    토큰이 만료되면 **미러링이 조용히 멈춰서**, 개발자도 사용자도 모르는 채 팀원만 옛 버전을
    쓰게 됨. 지금(사람이 직접 옮기는 것)보다 오히려 위험
- **어떻게 처리했나**: 배포 통로를 **Vercel 주소 하나**로 바꿈. 개발 저장소에 올리면 그 주소가
  이 폴더를 읽어서 팀원용 파일만 골라 내려주고, 팀원 PC가 그걸 받아 갱신함 — **사람이 파일을
  옮기는 단계가 사라짐** (`api/files.js`, `update.js`, `update-source.js`)
  - 받는 파일이 전부 글자 파일이라 압축을 다룰 필요가 없어 구조가 단순해짐
  - 개발용 문서·정찰 도구·배포 설정은 내려보내지 않음. 팀원용 문서는 따로 새로 씀 (`사용법.md`)
  - 압축 파일을 통째로 받아 푸는 예전 방식과 달리, **다른 프로젝트 파일이 팀원 폴더에 잠깐이라도
    풀리는 일이 없음**
  - 원본이 공개 저장소라 **토큰이 필요 없음** → 토큰 만료로 배포가 조용히 멈추는 실패가 구조적으로
    불가능
  - 실패해도 팀원 업무가 멈추지 않게, 받은 내용을 **전부 검사한 뒤에야** 파일을 쓰기 시작하고
    (절반만 갱신된 상태 방지), 실패 시 "지금 버전으로 계속 사용할 수 있어요 + 화면 캡처해서
    담당자에게" 안내만 띄우고 파일은 건드리지 않게 함
  - 새 파일을 추가했는데 배포 목록에서 빠져 팀원 쪽이 실행 불가가 되는 사고를 막기 위해,
    내려보낼 파일들이 서로 필요로 하는 파일이 전부 들어있는지 **서버가 스스로 점검**하고 빠졌으면
    응답 자체를 실패시키게 함
  - 업데이트 실행 파일(`update.bat`)은 노드를 부르기만 하는 껍데기로 축소함 — 검은 창을 띄우는
    실행 파일은 한 줄씩 읽으면서 실행되기 때문에 실행 중에 자기 자신이 덮어써지면 오작동해서,
    그 파일만 배포 목록에서 빼고 실제 로직을 별도 파일로 옮김. **이 전환 이후에는 업데이트
    방식이 바뀌어도 팀원이 파일을 손으로 갈 일이 없음**
- **결과**: 배포 후 **라이브 주소로 실제 팀원 PC 상황을 재현해서 검증함** — 3개 파일만 넣은
  폴더에서 실행하니 나머지 14개가 자동으로 내려오고, 이미 받아둔 결과물·사진·설치된 라이브러리가
  전부 그대로 남아있는 것을 내용까지 확인함. 개발용 문서와 정찰 도구는 내려오지 않고, 내려가는
  18개 파일 어디에도 개발 저장소 이름이 없음. 2회차 실행은 "이미 최신"으로 아무 동작 없음.
  가짜 서버로 성공·서버 죽음·응답 깨짐·네트워크 끊김·폴더 밖 경로·배포 묶음 불완전 6가지 상황을
  재현해 총 16건 통과
  - 검증 중에 내가 만든 문제 2개를 찾아 고침: ① 새 실행 파일이 부르는 파일이 팀원 PC에 아직
    없어서 원인 모를 오류로 죽던 문제 → 무슨 파일이 빠졌는지 알려주고 기존 버전은 계속 쓸 수
    있다고 안내하게 함 ② 버전 확인 스크립트가 주소 파일을 못 찾으면 검은 창에 오류가 쏟아지던
    문제 → 조용히 넘어가서 스크랩 실행을 막지 않게 함
  - **사용자가 해야 하는 일이 한 번 남음**: 팀원 PC에 `update.bat`, `update.js`,
    `update-source.js` 3개를 함께 넣어주기. 그 전까지는 `share` 저장소를 지우면 안 됨
