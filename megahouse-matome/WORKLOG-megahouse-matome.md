## 2026-10-02

### 사진 카피라이트가 잘리는 문제 — 인스타용 상세컷을 따로 뽑는 기능 신설
- **문제** ▶ 사진의 저작권 표기(카피라이트)가 잘리지 않게 해달라는 요청을 받음. 마토메 포스터에 넣은 사진은 칸 비율에 맞춰 꽉 채워 자르기 때문에 사진 아래쪽 카피라이트가 날아감
  - 메가하우스는 한 달에 상품을 30개쯤 내보내서 마토메도 30칸이 되는데, 인스타그램은 한 번에 20장까지만 올릴 수 있음
  - 원하는 형태는 두 가지 — 한 상품이 4:5 한 장을 다 쓰는 "단독", 두 상품을 위아래로 나눠 쓰는 "2분할"
- **확인** ▶ 개발 전에 두 가지를 먼저 짚음
  - 사진을 올리는 순간 긴 변 900px로 줄여 저장하고 있어서, 그 상태로 1080×1350을 뽑으면 작은 사진을 늘려 쓰는 셈이라 오히려 더 뭉개짐 (`resizeDataURL(..., 900, ...)`)
  - 올려받은 크롭 도구는 한 장만 다루는 구조라 여러 장을 넣으면 앞엣것이 사라짐. 마토메는 칸이 여러 개라 그대로는 못 씀
- **처리** ▶ 레이아웃을 아스키 그림으로 먼저 합의한 뒤 구현
  - 저장 해상도를 긴 변 1400px·품질 0.85로 올림 (`IMG_MAX_SIDE`, `IMG_QUALITY`). 실제로 재보니 30장 기준 2.4MB→4.5MB로, 디스크 용량은 저장소 한계(IndexedDB)에 한참 못 미침
  - **사진은 한 장만 저장하고, 자르는 위치·배율만 두 벌 기억**하게 함 (`it.igSolo`, `it.igHalf`). 사진을 두 장 저장하면 용량이 두 배가 되고 한쪽을 고칠 때 다른 쪽이 어긋남. 숫자 세 개뿐이라 용량은 사실상 0
  - 사이드바에 `상세컷` 탭을 넣고, 누르면 오른쪽 작업영역이 포스터에서 상세컷으로 통째로 바뀌게 함 (`igSetStage()`)
  - 보기 방식 두 가지 — **전체보기**(4열 카드, 여러 장을 한눈에 비교하며 묶기·순서 정리)와 **한장크게**(썸네일 줄 + 420px 미리보기, 위칸·아래칸을 각각 드래그·휠로 조정)
  - 단독으로 찍은 칸에서 묶음이 끊기고 그 다음부터 다시 둘씩 묶이게 함 (`igCards()`)
  - 인스타 한도를 넘는지 항상 보이도록 `포스터 2 + 상세컷 15 = 17 / 20장` 카운터를 띄우고 넘으면 빨갛게
  - 카드 순서를 바꾸면 마토메 칸 순서도 같이 바뀌게 함 (`igMoveCard()`) — 따로 놀면 포스터와 상세컷을 매번 대조해야 함
  - 파일 이름에 올릴 순서 번호를 먼저 붙임 (`01_디지몬테이머즈_재판·초회특전+원피스.png`). 이름만 쓰면 업로드할 때 가나다순으로 들어가 순서가 꼬임
  - 자리만 잡아둔 회색 더미 칸은 상세컷에서 제외
- **결과** ▶ 입력 43개·버튼 41개 전수 조작, 탭 4개 순회, 저장→새로고침 복원, 새 항목을 전부 지운 예전 저장본 로드, 실행취소까지 돌려 오류 0. 드래그로 위칸만 움직이고 아래칸은 그대로인 것, 순서를 바꾸면 포스터도 같이 바뀌는 것, PNG 실제 생성까지 확인
  - 미리 알린 한계 — 2분할은 각 칸이 가로로 넓은데(1080×655) 상품 사진은 세로로 길어서, 전체를 다 보이게 하면 좌우에 흰 여백이 크게 남음. 꽉 채우면 위아래가 잘려 카피라이트가 날아가므로 피할 수 없는 구조. 가운데 여백을 줄이거나 장별로 휠 확대로 보완 가능

### 만들다 발견: 상세컷에서 사진이 아예 안 끌리던 문제
- **문제** ▶ 큰 미리보기에서 드래그해도 사진이 꿈쩍도 안 함
- **확인** ▶ 사진이 칸보다 **클 때만** 움직이도록 조건이 걸려 있었음. 상세컷은 기본이 "전체 보이게"라 사진이 칸보다 **작은** 상태가 대부분이어서 그 조건에 한 번도 안 걸림
- **처리/결과** ▶ 계산식은 사진이 클 때와 작을 때가 같고 부호만 뒤집히므로 조건만 절댓값으로 바꿈. 흰 여백 안에서도 자리를 잡을 수 있게 됨

### 곁다리로 발견: 사이드바 위쪽이 텅 비던 문제 (예전부터 있던 버그)
- **문제** ▶ 상세컷 탭을 열면 사이드바 위쪽에 큰 빈 공간이 생기고 저장 슬롯 한 줄이 비정상적으로 길어짐
- **확인** ▶ 패널은 제목·저장슬롯·페이지탭·그룹탭·스크롤영역·하단버튼 **6줄**인데, "남는 공간을 먹는 줄" 지정을 3줄까지만 적어둬서 그게 2번째 줄(저장 슬롯)에 걸려 있었음 (`grid-template-rows:auto 1fr auto`). 저장 슬롯 높이를 재보니 42px→356px
  - 지금까지 모든 탭이 내용이 길어 남는 공간 자체가 없었던 덕에 드러나지 않았던 것 — 상세컷 탭이 짧아서 처음 노출됨
- **처리/결과** ▶ 6줄을 모두 적어 다섯 번째(스크롤 영역)에 정확히 걸리게 함. 모든 탭에서 저장 슬롯이 42px로 유지되는 것을 수치로 확인

### 정식 사진 오기 전에 배치부터 잡아보고 싶다는 요청 — 회색 더미 칸 버튼 추가
- **문제** ▶ 사진이 한 장도 없으면 칸 자체가 안 생겨서, 몇 칸짜리로 갈지·어느 상품을 위로 올릴지를 사진이 다 모인 뒤에야 볼 수 있었음
- **처리** ▶ 회색 임시 칸을 한 개씩 추가하는 버튼을 신설 (`addDummy()`)
  - 위치는 사진을 넣는 유일한 자리인 드래그 영역 옆에 **7:3**으로 나란히 둠 — 설정 쪽에 두면 정작 필요한 순간에 못 찾음
  - 회색 그림은 파일이 아니라 코드로 그려 넣어 저장 용량을 거의 안 씀 (`DUMMY_SRC`)
- **결과** ▶ 실측 239px : 103px = 2.33배로 7:3 확인. 14번 눌러 12칸을 넘기면 다음 페이지로 자동으로 넘어가는 것, 제품명·배지·블러·드래그·확대가 일반 사진과 똑같이 먹는 것, 새로고침 후 유지, PNG 내보내기 정상 생성까지 확인

### 로고 크기 슬라이더를 움직여도 아무 변화가 없다는 신고
- **문제/확인** ▶ 오픈용 헤더의 동그란 로고만 크기가 CSS에 52px로 못 박혀 있어 슬라이더를 따르지 않았음 (`.oh-logo`). 평소 헤더 로고(`.p-logo`)만 반영되고 있었음
- **처리/결과** ▶ 같은 슬라이더를 따르게 함 (`syncLogoSize()`). 64→100으로 올렸을 때 실제로 커지는 것 확인

### 푸터는 눌리는데 헤더는 눌러도 디자인 탭으로 안 간다는 신고
- **문제** ▶ 헤더 띠를 눌러도 디자인 탭으로 이동이 전혀 안 됨. 푸터는 정상
- **확인** ▶ 오픈용 헤더는 사진 위에 투명하게 덮이는 겹침 영역이라, 밑의 사진을 계속 조작할 수 있도록 클릭을 통째로 통과시키게 돼 있었음 (`pointer-events:none`). 그래서 헤더를 눌러도 클릭이 사진에게 감
- **처리/결과** ▶ 글자·로고가 실제로 있는 자리만 클릭을 받게 함. 빈 공간은 그대로 사진 조작에 양보해 드래그·확대는 안 막힘

### 오픈용 헤더 날짜를 페이지별로 끄고 싶다는 요청
- **문제** ▶ 기존 on/off는 지금 보는 페이지 하나만 조작할 수 있어, 페이지를 오가며 눌러야 했음
- **처리** ▶ 페이지 수만큼 버튼을 깔아 한 줄에서 끝내게 함 (`날짜 표시 [1p][2p][3p]`, `syncOpenBtn()`). 불 켜진 페이지에만 날짜가 보임
  - 평소 헤더 날짜만 꺼지고 오픈용 헤더 날짜는 그대로였던 것도 같이 묶어 처리
- **결과** ▶ 2p만 꺼서 1p는 보이고 2p는 숨는 것을 두 헤더 모두에서 확인

### 디자인 탭을 보는 중엔 그리드를 눌러도 아무 반응이 없던 버그
- **문제/확인** ▶ 칸을 누르면 해당 항목 행이 펼쳐지는데 그 행이 **사진 탭 안**에 있어서, 디자인 탭을 보고 있으면 화면에 변화가 전혀 없었음
- **처리/결과** ▶ 칸을 누르면 사진 탭으로 같이 이동하게 함 (`gotoPhotoTab()`)

### 실행취소가 직전이 아니라 한참 전으로 되돌아가던 문제
- **문제** ▶ 실행취소를 누르면 바로 전이 아니라 여러 단계가 한꺼번에 날아감
- **확인** ▶ 원인이 두 겹이었음
  - 되돌릴 지점을 "바꾸기 직전"이 아니라 **바꾼 뒤** 상태로 쌓고 있었음 — 첫 실행취소는 헛돌고 이후로는 계속 한 칸씩 밀림
  - 기록이 **화면 전체를 다시 그릴 때만** 남아서, 체크박스·이름 수정·칸 이동처럼 화면 일부만 갱신하는 변경은 아예 기록이 안 됨
- **처리** ▶ 직전 상태를 하나 들고 있다가 그걸 쌓는 방식으로 바꾸고(`_lastSnap`), 저장이 일어날 때도 한 단계로 기록하게 함. 값이 실제로 안 바뀌었으면(슬라이더 연타 등) 중복은 안 쌓임
- **결과** ▶ A·B·C·D 네 번 추가 후 네 번 취소하면 완전히 빈 상태까지 한 단계씩 되돌아가는 것 확인. 화면을 다시 안 그리는 배지 체크도 한 단계씩 기록됨

### 이 프로젝트만 전수점검 요청
- **처리** ▶ 정적 검사(중복 id·없는 함수 호출·없는 요소 참조)와 브라우저 전수 조작(입력 43개, 버튼 104개, 셀 드래그·휠·배경 4단계, 저장/복원/구버전 로드/초기화, 실행취소, 실제 PNG 생성)을 돌림
- **결과** ▶ 실제 버그 1건 발견·수정
  - 화면 그리기를 "다음 갱신 때 실행"으로 예약해두는 구조라, 그 사이에 실행취소·페이지 삭제·불러오기로 그 페이지가 없어지면 예약된 코드가 빈 대상을 붙잡고 터졌음 (`applyRowHeights()`에 빈 대상 확인 없음). 실행취소 연타 시 한 번에 15회까지 터지는 것을 확인 — 겉으로는 조용히 실패해서 그동안 안 드러났지만 그 시점의 줄 높이·그리드 갱신이 통째로 누락되고 있었음
  - 같이 막은 것 — 보던 페이지 번호가 남은 페이지 수보다 커지면 항목 목록이 빈 채로 굳어버리는 구멍
  - 오류는 아니지만 알린 것 — 다운로드 라이브러리를 외부 CDN에서 받아오는 점(실패 시 안내는 이미 있음), 저장슬롯을 바꾸면 페이지가 통째로 새로고침되는 점(의도된 설계), 항목을 전부 지워도 빈 페이지가 남는 점

### 메모를 눌렀을 때 줄이 찌그러지고 위/옆 버튼이 안 먹던 문제
- **문제** ▶ 메모를 누르면 레이아웃이 깨져 보이고, 위치를 고르는 `위`·`옆` 버튼을 눌러도 아무 변화가 없음
- **확인** ▶ 두 건이 각각 다른 원인이었음
  - 펼친 줄은 `[라벨 56px | 내용]` 2열 구조인데 메모 줄은 라벨을 비워서 넘겼고, 라벨이 없으면 라벨 칸을 안 만들어서 내용이 통째로 첫 칸(56px) 안으로 들어가 접혔음 (`irow()`)
  - `위`/`옆` 버튼은 값을 저장하고 자기 색만 바꿀 뿐, 포스터를 그리는 쪽이 그 값을 아예 안 읽고 있었음 (`makeCell()`이 `it.memoPos`를 참조하지 않음)
- **처리** ▶ 라벨 없는 줄은 한 칸짜리로 만들어 폭을 다 쓰게 하고(`.irow.nolbl`), 메모를 실제로 이름 위/옆에 나눠 그리게 함. 기본값을 `위`로 통일해 표시와 결과가 어긋나던 것도 맞춤. 메모를 옆에 두면 이름과 한 줄을 나눠 쓰므로 이름 자동 축소 계산에 메모 폭을 포함시킴 (`fitCellNames()`)
- **결과** ▶ 입력·크기·색·버튼 5개가 모두 한 줄에 서고 가로 넘침 0, 기본 `이름 위` → `옆` 클릭 시 `이름 옆` → `위` 클릭 시 복귀하는 것 확인

  - 반면 흔히 의심하는 "설명문이 너무 많다"는 해당 없음 (설명 대 조작 면적비 0.66, 가장 큰 설명 블록이 전체 설명 면적의 5.7%뿐)
- **어떻게 처리했나** ▶ 지침 순서대로 ① 진단 보고 → ② 버그만 따로 먼저 → ③ 클릭되는 목업으로 합의 → ④ 실제 코드 반영으로 진행. 목업은 레포를 건드리지 않는 링크(Artifact) 형태로 만들어 여러 차례 수정하며 방향을 맞춤

### 하단 버튼 바가 패널 글씨를 덮고 있던 버그 (배치 변경과 분리해 먼저 처리)

- **확인** ▶ 원인은 화면에 붙는 배치(`position:sticky`)가 아니라, 보조 버튼 세 개의 배경이 아예 투명이었던 것 (`button.ghost{background:transparent}`) — 버튼 면적을 그대로 통과해 뒤 패널 내용이 읽혔음
- **처리** ▶ 보조 버튼 배경을 다른 입력 요소와 같은 흰색으로 지정 (`var(--ui-card)`), 버튼 바 배경이 35% 지점부터 불투명해지던 것을 10px 안에 불투명해지도록 좁힘
- **결과** ▶ 계산된 배경색이 흰색으로 잡히는 것과 겹침이 사라진 것을 스크린샷으로 확인. 지침대로 배치 변경과 섞지 않고 별도 커밋으로 분리

### 좌측 패널을 사진 / 디자인 / 도움말 3개 탭으로 재편

  - 동시에 펼 수 있던 설정 묶음 4개를 탭 3개로 바꿔 한 번에 한 묶음만 보이게 함 (`switchGroup()`, `.gpane`)

  - 셀 배경 블러·하단 그라데이션을 로고 옆에서 떼어내 사진 쪽으로 옮김 — 페이지 전체 사진에 걸리는 설정이라 목록과 같은 화면에 있어야 맞음

  - 결과물 버튼을 2줄로 나누고, 되돌리기 어려운 초기화는 작은 링크로 분리

### 목업과 실물이 다르다는 지적 — 세 군데가 실제로 안 맞춰져 있었음

- **확인** ▶ 스크린샷을 나란히 놓고 대조하니 구조만 옮기고 생김새를 안 맞춘 곳이 있었음
  - 그룹 탭이 선택 시 파랗게 채워진 상자였음 (목업은 회색 레일 위 파란 글씨 + 파란 밑줄)

### 사진 칸을 눌러도 세부 설정은 또 화살표를 눌러야 나오던 불편
- **문제** ▶ 포스터 칸을 누르면 파란 표시만 들어오고 세부 설정은 화살표를 한 번 더 눌러야 나와서 같은 상품에 두 번 손이 감. 펼친 줄의 "표시", "옮기기" 같은 라벨은 옆을 보면 아는 것들이라 자리만 먹음
- **처리** ▶ 포스터 칸을 누르면 그 상품 행이 바로 펼쳐지고, 다른 칸을 누르면 이전 것은 접히게 함(한 번에 하나). 페이지 이동 버튼은 삭제 ✕ 아래 세로로 수납해 3페이지 중 2페이지를 보고 있으면 ✕ / ←1 / →3 세 칸이 되게 함. 펼친 줄은 라벨을 전부 없애고 체크 3개 · 구분선 · 배경 스테퍼 한 줄로 정리
- **같이 고친 것** ▶ 펼친 상태가 목록을 다시 그릴 때마다 사라져 체크 하나만 눌러도 행이 접혔음 (`refresh()`가 목록을 다시 만들면서 클래스가 날아감) → 펼친 상품을 따로 기억해두고 복원하게 함 (`_openItemId`, `setOpenItem()`)

### 사진이 종횡비 안 맞을 때 잘리고 위아래 드래그가 안 되던 문제 (근본 수정까지 3차 시도)
- **무슨 문제/요청이 있었나**: 그리드 사진 여백(빈 배경) 방지 코드를 넣은 뒤, 종횡비가 칸이랑 안 맞는 사진(예: 세로로 긴 인물 사진)에서 머리·글씨가 잘리고, 잘린 부분을 드래그로 되찾으려 해도 위아래로 안 움직인다는 반복 신고
- **확인해보니(1차, 실패)**: 처음엔 CSS `object-fit:cover`로 여백을 없앴는데, 이게 **칸의 고정 크기 기준으로 이미지를 이미 한 번 크롭해서 렌더링**해버려서, 그 위에 얹은 확대·이동은 이미 잘려나간 결과물만 움직일 뿐 크롭된 부분은 애초에 화면에 없어 드래그로도 못 돌아옴 (`object-fit:contain·cover`류 공통 함정)
- **확인해보니(2차, 근본 원인 확정)**: `object-fit`을 아예 버리고 이미지 원본 크기(`naturalWidth/Height`) 기준으로 직접 `width/height/left/top`을 계산하는 진짜 cover-fit 수식(`baseScale = max(칸가로/사진가로, 칸세로/사진세로)`)으로 전면 재작성. 이러면 "잘리는" 부분도 실제 이미지 데이터로 남아있어 드래그로 끝까지 훑어볼 수 있음
- **어떻게 처리했나**: `applyImgTransform()`을 `object-fit` 없이 직접 좌표 계산하는 함수로 교체, 드래그/터치 이동량 계산에서 배율 나누기 제거(화면 그대로의 픽셀 단위로 변경), 로드 완료 후(`img.onload`)·행 높이 슬라이더 변경 후 재계산되도록 보강. 추가로 Shift+휠로 "사진 전체가 다 보이는" 지점까지는 축소 허용(`containMinScale`)
- **결과**: Playwright로 세로로 긴 사진의 잘렸던 머리 부분이 드래그로 실제 노출되는 것, 어떤 경우에도 칸을 완전히 덮는 것, 행 높이를 극단적으로 바꿔도 정확히 커버되는 것, Shift 뗀 후 안전 배율로 스냅되는 것까지 모두 검증. **"버그가 재신고되면 이전 수정을 의심하고 근본부터 재검토할 것"을 다시 한번 상기한 사례**

### 블러 배경·흰배경 연출이 위 수정 이후 안 보이던 버그
- **무슨 문제/요청이 있었나**: 위 cover-fit 수정 이후 "블러 배경 켜도 블러가 안 보인다"는 신고, 이어서 "블러↔흰배경 오갈 때 사진 크기(줌)가 확 바뀌어 보인다"는 추가 신고
- **확인해보니**: 블러/흰배경은 원래 "사진이 칸을 다 못 채우고 남는 자리에 배경이 비쳐 보이는" 연출인데, 새 cover-fit 기준(cover=항상 꽉 채움)으로는 사진이 항상 칸을 덮어버려 배경이 보일 자리가 아예 없어짐. 흰배경은 그 중에서도 기준을 안 고쳐서 블러(contain 기준)와 오갈 때마다 크기가 확 달라 보였음
- **어떻게 처리했나**: `it.blur`나 `it.whiteBg`가 켜진 사진은 기준을 cover가 아니라 contain(전체가 다 보이는 크기)으로 분기. 그리고 "1줄 높이" 슬라이더 재계산 로직이 셀 안의 블러 배경 이미지(`.blur-bg`)를 메인 사진으로 착각해 크기를 잘못 건드리던 별도 버그도 같이 발견해 수정(`:not(.blur-bg)`로 명시)
- **결과**: 체크무늬 테스트 이미지로 스크린샷 찍어 블러가 다시 칸 전체를 감싸는 것 확인, 블러→흰배경 전환 시 사진 크기가 완전히 동일하게 유지되는 것도 검증

- **어떻게 처리했나**: 원래 동작으로 복원 — 뱃지는 이름 옆 유지가 기본, 이름이 길면 글자 크기를 반응형으로 줄여서 옆에 맞추고, 그래도 안 될 만큼 극단적으로 길 때만 위로. 다운로드 시 겹침은 뱃지를 옆에 두는 대신 이름 상자에 여유 폭을 확보하는 방식으로 대응
- **결과**: 사용자 데이터로 재검증 후 반영. **"버그 고치다 근처의 잘 작동하던 로직까지 덮어쓰지 말 것"을 CHANGELOG 교훈에 추가**

### 뱃지 글자 크기가 이름 대신 슬라이더 값을 그대로 따라가던 버그
- **무슨 문제/요청이 있었나**: 헌터x헌터·페르소나3 리로드가 한 줄에 있는 상태에서 줄 글자크기 슬라이더를 올리면, 헌터는 이름이 커지는데 페르소나는 이름은 그대로고 "초회특전" 뱃지만 커지는 이상한 현상 신고
- **확인해보니**: 뱃지 글자 크기가 CSS `em` 단위로 "칸 기준 크기(슬라이더 값)"에 그대로 묶여 있었음. 페르소나는 이름이 칸에 맞춰 자동으로 작아지는데 뱃지는 슬라이더 값 그대로 커지니 균형이 깨진 것
- **어떻게 처리했나**: 뱃지 크기를 슬라이더 값이 아니라 "실제로 화면에 표시되는 이름 크기"에 비례하도록 계산해서 직접 지정
- **결과**: 슬라이더를 올려도 뱃지가 이름 크기를 따라 같이 커지고 작아짐을 확인 후 반영

### 다운로드-미리보기 미묘한 차이(뱃지 밀림·스토어 정렬)의 진짜 근본 원인 해결
- **무슨 문제/요청이 있었나**: 뱃지 텍스트 위치가 미묘하게 밀리고, 오픈헤더 스토어명이 중앙정렬 안 되고 밀려 보인다는 신고. "익스포트랑 미리보기가 왜 자꾸 미묘하게 차이나냐"는 반복 지적과 함께, 페르소나처럼 이름이 길어 확대하면 뱃지가 커지기만 하고 위로 안 올라간다는 지적
- **확인해보니**: 지금까지 여러 차례(1~8차) 여유 마진으로 증상만 땜질해왔는데, 진짜 근본 원인은 따로 있었음 — 다운로드 엔진(html-to-image)이 CORS 때문에 CDN 폰트(프리텐다드·페이퍼로지)를 못 읽어서, 다운로드 시엔 화면과 다른 폴백폰트로 그려지고 있었던 것. 그래서 화면과 다운로드가 항상 미세하게 다른 폭으로 렌더됨
- **어떻게 처리했나**: 다운로드 직전 웹폰트를 CDN에서 받아 data URL로 만들어 `htmlToImage`의 `fontEmbedCSS` 옵션으로 직접 박아넣음 → 화면과 다운로드가 100% 동일한 폰트로 렌더. 이후 그동안 넣어뒀던 여유 마진들을 전부 제거하고, 배지 배치 로직도 "이름이 슬라이더 크기 그대로 옆에 들어가면 옆 유지, 안 들어가면 위로"로 정확하게 재정리. 배지 위치를 조정할 때마다 처음부터 다시 판단하도록 해서, 한 번 위로 올라간 배지가 조건이 바뀌어도 안 내려오던 부수 버그도 같이 잡음
- **결과**: 사용자 실제 데이터로 화면·다운로드 결과물을 나란히 비교 검증, 뱃지 밀림·스토어 정렬·잘림 모두 해소되고 페르소나 확대 시 배지가 정확히 위로 올라가는 것까지 확인 후 `main` 반영. 사용자가 "이제야 되네"로 확인. **CHANGELOG에 9차로 근본원인·해결법·교훈("여유 마진으로 덮기 전에 근본을 없애라") 상세 기록**
