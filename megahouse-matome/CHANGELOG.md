# 2026-09-03 (V2.2 사이드바 리뉴얼)

### 사이드바 구조
- **설정 묶음 4개를 사진 / 디자인 / 도움말 3개 탭으로 재편** — 동시에 펼칠 수 있어 패널 스크롤이 3157px(1366 화면의 4.1배)까지 늘어났던 것을 한 번에 한 묶음만 보이게 함
  (기술: `.psec-toggle` 아코디언 제거, `switchGroup()` + `.gpane`/`.gt` 탭 전환)
- **라벨·조작·값을 항상 같은 줄에 배치** — 조작요소가 앉은 줄 77개 중 40개가 혼자 한 줄을 차지했고 그중 26개는 폭이 패널 절반 미만이었음
  (기술: `.frow` 3열 그리드, 짝인 값은 `.frow.pair` 4열)
- **패널을 [머리 / 스크롤 본문 / 버튼] 3단 구조로 전환**
  (기술: `.panel`을 `grid-template-rows:auto 1fr auto`로, 본문만 `.pane-scroll`이 스크롤)
- **페이지 탭을 사진 섹션 밖 고정 자리로 이동 + 알약형으로 축소** — 다른 탭에 있으면 현재 페이지가 안 보였음
  (기술: `#tabsRow`를 `.pgbar`로 이동, `flex:1` 제거해 내용 폭만 사용)
- **저장 슬롯을 라벨·드롭다운·추가 버튼 한 줄로 통합**
  (기술: `.slotrow` 3열 그리드, 라벨 폭 82px로 다른 설정과 열 정렬)
- **셀 배경 블러·하단 그라데이션을 사진 탭으로 이동** — 페이지 전체 사진에 걸리는 설정이라 목록과 같은 화면에 있어야 함
  (기술: `.fixedbox`로 묶어 제품명 일괄입력 아래에 배치)

### 사진 목록
- **항목당 조작요소 13개 상시 노출 → 썸네일·이름만 보이고 나머지는 펼침** (사진 8장이면 104개 → 32개)
  (기술: `.item-body` 분리, `.item.sel`일 때만 표시)
- **포스터 칸을 누르면 그 상품 설정이 바로 펼쳐짐** — 한 번에 하나만 펼쳐지고 다른 칸을 누르면 이전 것은 접힘
  (기술: `_openItemId` + `setOpenItem()`, `refresh()` 후에도 펼침 상태 복원)
- **교체·삭제 버튼을 마우스 올릴 때만 표시, 터치 기기는 항상 표시**
  (기술: `.item .ctrl{opacity:0}` + `@media (hover:none)` 예외)
- **페이지 이동 버튼을 삭제 버튼 아래 세로로 수납** — 3페이지 중 2페이지면 ✕ / ←1 / →3
  (기술: `makeSwapBtn()` 결과를 `.ctrl`에 세로 배치)
- **펼친 줄에서 라벨 제거하고 체크 3개 · 구분선 · 배경 선택 한 줄로 정리**

### 신규 기능
- **작업가이드** — 배치할 때 지킬 원칙 5개를 제목 오른쪽 버튼에서 바로 펼쳐 확인
  (기술: `#btnGuide` + `.guide-pop`, 탭 밖 고정 자리라 어느 탭에서도 열림)
- **셀 배경에 '색상' 추가** — 흰배경 대신 원하는 색을 직접 골라 칸 배경으로 사용
  (기술: `BG_OPTS`에 '색상' 추가, `it.bgColorOn`/`it.bgColor`, 배경 계산 기준은 흰배경과 동일한 contain)
- **개선사항 메모장을 결과물 버튼 옆으로 이동** — 도움말 안쪽에 있어 존재를 알기 어려웠음
  (기술: `#btnMemoOpen` + `.memo-pop` 팝오버)
- **저장 상태 표시 추가** — 저장 중이면 노란 점, 끝나면 초록 점
  (기술: `markSaving()`을 `saveState()` 진입 시 호출)

### 입력 편의성
- **셀 배경 선택을 세로 ▲▼에서 가로 ◀ 이름 ▶으로 변경** — 어디를 누르는지 알기 어려웠음
- **항목 이름 정리** — '그라데이션' → '하단 그라데이션', '블러 설정' → '셀 배경 블러 (셀 배경이 '블러'인 칸에만 적용)'
- **안내 문구 크기 축소** (13px → 12px)

### 버그 수정
- **하단 버튼 뒤로 패널 글씨가 비쳐 겹쳐 보이던 문제**
  (기술: `button.ghost`의 `background:transparent` → `var(--ui-card)`)
- **버튼 바가 사진 목록 중간을 덮던 문제** — 패널 아래 여백 100px 때문에 화면 맨 아래가 아니라 100px 위에서 멈췄음
  (기술: `position:sticky` 제거하고 패널 3단 그리드로 구조 변경)
- **펼친 사진 행이 목록을 다시 그릴 때마다 접히던 문제** — 체크 하나만 눌러도 접혔음
  (기술: `refresh()`가 `#itemList`를 재생성하며 클래스 소실 → `_openItemId`로 복원)
- **개선사항 메모장 팝업이 버튼 칸 폭에 갇혀 입력창이 82px밖에 안 되던 문제**
  (기술: `left:0;right:0` → `right:0` + `width:350px`)
- **하단 버튼 세 개 중 하나만 10px 좁았던 문제**
  (기술: flex 분배가 버튼 최소 폭에 밀렸음 → `grid-auto-flow:column` + `grid-auto-columns:1fr`)

### 기타
- 아무도 쓰지 않게 된 아코디언 코드 제거 (`toggleSection()`, `.psec-*`)
- 포스터(아트보드) 마크업·CSS는 변경 없음

# 2026-07-31 (V2.1 보드 관리 기능 확장 및 스테이지 조작 개선)

### 페이지 관리
- **보드(페이지)를 드래그로 순서 변경 가능**
  (기술: 페이지 탭 버튼에 `draggable=true` + `dragstart/dragover/drop` 등록, `reorderPages(from,to)`가 `pages`/`firstRowFlex` 배열을 같은 인덱스로 함께 splice)
- **페이지 삭제 기능 추가** — 지금까지 추가만 가능하고 삭제 기능 자체가 없었음
  (기술: 탭에 `.ptab-del`(×) 버튼 추가, `deletePage()`. 마지막 1개 남으면 삭제 차단, 사진이 있으면 확인창 노출, Ctrl+Z로 복구 가능)

### 셀(사진 칸) 조작
- **파일 탐색기에서 사진을 칸 위로 직접 끌어다 놓으면 그 칸 사진만 교체**
  (기술: `dragover`에서 `e.dataTransfer.types.includes('Files')`로 파일 드래그와 기존 셀↔셀 순서교환 드래그를 구분, `drop`에서 파일이면 `resizeDataURL`로 교체 후 반환해 기존 스왑 로직과 분기)

### 미리보기 조작 (스테이지)
- **미리보기 줌 팝업을 원하는 위치로 옮길 수 있음** — 항상 화면 상단에 고정돼 있어 캔버스를 가리던 문제
  (기술: `#stageToolbar`를 `position:fixed`로 전환, 팝업 전체(슬라이더 제외)에 드래그 이벤트 부여, 마지막 위치를 `localStorage`에 저장해 다음에 열어도 유지)
- **베이지 배경을 세로로 드래그해도 안 움직이던 문제 수정** — 줌%가 낮을 때 캔버스 높이가 화면에 딱 맞아 스크롤할 여백 자체가 없었던 것
  (기술: 위아래 대칭으로 화면 높이의 45%씩 여백 확보, 처음 열 때 스크롤 위치를 그 여백 한가운데로 자동 이동시켜 캔버스가 화면 중앙에 오도록 함)

### 증상
- **미리보기 화면에선 멀쩡한데, 다운로드한 PNG에서만 글자가 잘림**
  (기술: 제품명 "페르소나3 리로드"→"페르소나3 리로", "명탐정 코난"→"명탐정", 오픈헤더 스토어명 "메가하우스 공식 스토어"→"메가하우스 공식 스토" 등 끝 글자 잘림 + 뱃지와 겹침)

### 진짜 원인 (한 줄 요약)
- **다운로드 엔진(html-to-image)이 텍스트를 화면보다 미세하게 넓게 그리는데, 글자 상자가 `overflow:hidden`으로 내용에 딱 맞게 잘려 있어 끝 글자가 잘려나감**
  (기술: 화면은 웹폰트 프리텐다드로 렌더 → 폭이 좁음 / 다운로드는 CORS로 폰트 임베드 실패 시 폴백폰트로 렌더 → 폭이 넓음. 상자는 화면 기준 폭으로 고정 → 다운로드에서 초과분이 잘림)

### ⚠️ 왜 6차까지 갔나 — 타 프로젝트 재발 방지용 상세 기록
> 이 버그는 "고쳤다"고 6번 보고했다가 6번 다시 잘렸다. **테스트 환경과 실제 사용자 환경이 달라서** 매번 헛다리를 짚은 것이 핵심 실패다. 아래를 순서대로 읽으면 같은 삽질을 피할 수 있다.

- **1차 — 폰트 로딩 타이밍 의심 (실패)**
  - 캡처 직전 `document.fonts.ready`를 기다리게 함. 그럴듯했지만 증상 그대로였음
  - (교훈: 테스트 환경에 웹폰트가 아예 안 깔려 있어서 폴백폰트로 통과된 것을 "해결됐다"고 오판. **폰트 없는 환경의 테스트 통과는 증거가 아니다**)

- **2차 — 오픈헤더 타이틀만 부분 해결 (부분 성공)**
  - 헤더 타이틀/날짜를 한 줄 고정(nowrap) + 넘치면 글자 크기 자동 축소. 헤더는 고쳐졌으나 그리드 제품명은 여전
  - (교훈: 증상이 여러 곳에서 나면 한 곳만 고치고 "됐다" 하지 말 것)

- **3차 — 제품명 자동 축소 추가했으나 측정이 거짓말 (실패)**
  - `scrollWidth > 여유폭`이면 글자 축소하도록 함. 코드상 측정은 "안 잘림"으로 나왔지만 실제로는 여전히 잘림
  - (교훈: 제품명이 `white-space:normal`이라 넘칠 때 **가로로 넘치는 대신 아래로 줄바꿈** → `scrollWidth`가 작게 나와 "안 넘친다"고 거짓 판정. **측정값(clipped:false)을 믿지 말고 실제 렌더 결과 이미지를 눈으로 봐라**)

- **4차 — 제품명 nowrap 전환 + 폰트 로드 후 재조정 (실패)**
  - 한 줄 고정으로 넘침이 측정되게 하고, 폰트 로드 완료 후 크기 재계산. 그래도 다운로드에서 잘림
  - (교훈: 여기서 "미리보기 ≠ 다운로드"라는 사용자의 반복 지적이 결정적 단서였음. 화면 기준으로 아무리 맞춰도 다운로드 렌더가 다르면 소용없다)

- **5차 — 실제 폰트를 테스트 환경에 심어서 재현 성공 (원인 확정)**
  - 사용자가 올린 실제 작업파일(JSON)을 그대로 툴에 주입 + 프리텐다드/페이퍼로지 폰트를 강제로 로드시켜, **미리보기와 다운로드를 같은 페이지에서 나란히 생성해 비교**
  - 미리보기는 완벽, 다운로드만 잘림 → 원인이 html-to-image 렌더 차이임을 눈으로 확정
  - (교훈: **재현이 안 되면 사용자 환경과 똑같은 조건(실제 데이터 + 실제 폰트)을 강제로 만들어라.** 이 한 번의 제대로 된 재현이 앞의 다섯 번보다 값졌다)

- **6차 — 근본 수정 (성공)**
  - 제품명 상자의 강제 잘림(`overflow:hidden`) 제거 → 다운로드가 살짝 넓게 그려도 안 잘림
  - 뱃지는 **원래대로 이름 옆(인라인)에 유지**하되, 이름 상자에 10% 여유 폭을 확보해 뱃지를 그만큼 오른쪽으로 밀어둠 → 다운로드가 글자를 넓게 그려도 그 여유 안에 들어와 뱃지 밑으로 안 삐져나감
  - 이름이 길면 글자 크기를 반응형으로 자동 축소(export 여유 마진 포함), 옆에 두기엔 너무 작아질(30px 미만) 극단적 경우에만 뱃지를 윗줄로 이동
  - 스토어명은 헤더 폭의 38%로 상한 + 폰트 로드 후 재조정
  - 실제 폰트 환경에서 다운로드 결과물까지 브라우저로 최종 검증
  - (추가 교훈: html-to-image는 **요소 위치는 화면 기준으로 두고 글자만 넓게 그려서**, 옆 요소 밑으로 텍스트가 삐져나가 겹침 → 옆 요소가 있으면 텍스트 상자에 미리 여유 폭을 확보해 둘 것)

- **7차 — 버그 고치다 기존 로직까지 훼손한 것을 사용자 지적으로 재점검 (성공)**
  - 6차에서 "이름이 길면 뱃지를 무조건 윗줄로" 규칙을 넣었는데, 이건 **원래 있던 반응형 동작을 멋대로 바꿔버린 것**이었음 (원래: 글자 크기에 따라 옆에 들어가면 옆에, 안 되면 위로)
  - 사용자가 "왜 또 거지같이 바꿔놨냐, 원래 그런 설정이었다"고 지적 → 원래 동작으로 복원
  - **뱃지는 이름 옆(인라인) 유지가 기본**, 이름이 길면 글자 크기를 반응형 축소해 옆에 맞춤, 옆에 두기엔 너무 작아질(30px 미만) 극단적 경우에만 윗줄로
  - export 겹침은 뱃지를 올리는 대신 **이름 상자에 여유 폭 10% 확보**로 해결
  - (교훈: **버그를 고칠 때 그 근처의 잘 작동하던 로직을 새 규칙으로 덮어쓰지 말 것.** 기존 동작은 사용자가 의도해 만든 사양일 수 있다. 고정 임계값(예: "80% 넘으면")으로 기존 반응형 로직을 대체하면, 증상은 사라져도 사용자가 쓰던 동작이 사라진다)

- **8차 — 뱃지 크기가 이름 대신 슬라이더 값을 따라가던 버그 (성공)**
  - 증상: 헌터·페르소나가 한 줄에 있을 때 줄 글자 크기 슬라이더를 올리면 헌터는 이름이 커지는데, 페르소나는 이름은 그대로고 **뱃지("초회특전")만 커짐**
  - 원인: 뱃지 글자 크기가 CSS `.72em`으로 **칸 기준 크기(슬라이더 값)**에 묶여 있었음. 페르소나는 이름이 칸에 맞춰 작게 축소되는데 뱃지는 슬라이더 값 그대로 커져 균형이 깨짐
    (기술: `em`은 부모(`.name`=슬라이더 값)에 상대적 → 자동 축소된 `.name-text`의 실제 크기를 반영 못 함)
  - 수정: 뱃지 크기를 fitCellNames에서 **실제로 표시되는 이름 크기 × 0.72**로 직접 지정 → 이름이 작으면 뱃지도 작게, 이름에 비례
    (교훈: **자동 축소되는 요소에 딸린 부속(뱃지 등)의 크기를 `em`으로 원본 크기에 묶지 말 것.** 축소 후 실제 크기 기준으로 다시 계산해 붙일 것)

- **9차 — 근본 원인(폰트 미임베드) 해결 + 배지 반응형 정리 (성공)**
  - 1~8차는 "다운로드가 화면보다 넓게 그린다"를 여유 마진으로 땜질하다 계속 다른 게 틀어졌음. **진짜 근본 원인은 다운로드 엔진이 웹폰트를 못 박아넣어 폴백폰트로 그린 것**
  - 수정: 다운로드 직전 웹폰트(프리텐다드/페이퍼로지)를 CDN에서 받아 data URL로 만들어 `fontEmbedCSS`로 넣음 → **화면과 다운로드가 100% 동일**하게 렌더
    (기술: `htmlToImage.toPng(el, {fontEmbedCSS})`. CORS로 CDN 스타일시트를 못 읽는 문제를 우회해 폰트를 직접 임베드)
  - 이로써 여유 마진(15%씩 축소)·상자 여유폭(10%) 같은 땜질을 전부 걷어냄 → 글자가 불필요하게 작아지던 것도 해소
  - 배지 배치를 정확한 반응형으로 재정리: **이름을 슬라이더 크기 그대로 두고, 뱃지와 함께 한 줄에 들어가면 옆에 유지 / 안 들어가면(=크게 확대하거나 이름이 길면) 뱃지를 윗줄로**
  - 배지 위치를 매 조정마다 **처음부터 다시 판단**하도록 함(한 번 윗줄로 올라간 배지가 조건이 바뀌어도 안 내려오던 버그 수정 — 로딩 중 폰트 로드 전 넓게 측정돼 굳던 문제)
  - (교훈: **여유 마진으로 증상을 덮기 전에 "왜 화면과 결과가 다른가"의 근본을 먼저 없애라.** 폰트 임베드 한 방이 여덟 번의 마진 땜질보다 깔끔했다. 또한 상태를 바꾸는 함수는 매번 처음부터 재판단하게 만들어 이전 상태가 굳지 않게 할 것)

### 교과서 (다른 이미지 생성 도구에 그대로 적용)
- **화면 캡처/이미지 export는 화면 렌더와 다르다 → 폰트를 직접 박아넣어 원천 차단** — 웹폰트가 CORS로 임베드 안 되면 폴백폰트로 폭이 달라져 잘림. 해결책은 여유 마진이 아니라 **`fontEmbedCSS`로 폰트를 data URL로 박아넣어 화면=결과를 동일하게** 만드는 것
  (기술: html-to-image·dom-to-image·html2canvas 계열 공통. `toPng(el,{fontEmbedCSS})`에 CDN woff2를 fetch→base64로 넣으면 됨. `getFontEmbedCSS` 실패 로그를 흘려보지 말 것)
- **여유 마진으로 증상을 덮기 전에 근본을 없애라** — "화면과 결과가 왜 다른가"를 먼저 제거하면, 마진·예외처리 같은 땜질이 통째로 필요 없어진다
- **"딱 맞게 자르는" UI(overflow:hidden + 콘텐츠 폭 상자)는 export의 미세 폭 증가에 취약** — 여유 마진 + 강제 잘림 제거로 견고하게
- **측정값과 실제 렌더가 다를 수 있다** — `scrollWidth`류 측정은 줄바꿈·overflow 설정에 따라 거짓음성. 스크린샷으로 눈으로 확인
- **테스트 환경 통과 ≠ 사용자 환경 통과** — 폰트·데이터가 다르면 재현 자체가 안 된다. 사용자 실제 데이터와 폰트를 강제 주입해 동일 조건을 만들 것
- **버그 수정이 기존 동작을 훼손하지 않게 할 것** — 증상만 없애려고 근처의 잘 작동하던 로직을 새 규칙으로 덮어쓰면, 사용자가 의도해 만든 사양이 사라진다. 고칠 땐 "이 동작이 원래 의도된 것인지"부터 확인하고, 기존 로직은 최대한 보존한 채 최소 침습으로 고칠 것

### 🔁 사용자가 같은 증상을 반복해서 호소할 때 (대응 원칙)
> 이번에 "고쳤다"→"또 잘린다"가 6번 반복되며 사용자를 지치게 했다. 반복 신고는 **내 진단이 틀렸다는 강한 신호**다. 아래 순서로 임한다.

- **1. "저번 수정이 덜 됐나 보다"라고 단정하지 말 것** — 같은 부분만 또 들여다보는 것이 가장 흔한 함정. 재신고는 "그 부분이 원인이 아닐 수 있다"는 뜻으로 받아들이고, **인접 코드 전체를 처음부터 다시 의심**한다
- **2. 이미 정상인 신호부터 확인** — 예: "글자가 잘린다"는데 글자 내용·개수·위치는 정상이라면, "글자를 그리는 코드는 정상, 자르는(크기/폭) 코드가 범인"이라는 뜻. 정상 신호가 가리키는 반대편을 볼 것
- **3. 사용자의 표현을 문자 그대로 신뢰할 것** — 이번엔 "미리보기랑 다운로드가 다르다"는 반복된 지적이 정답이었는데, 내가 계속 미리보기(화면)만 검증해서 헛다리를 짚었다. 사용자가 구분해서 말하는 조건(A는 되고 B는 안 됨)은 그 자체가 원인의 위치를 알려주는 단서다
- **4. 스크린샷·측정값을 맹신하지 말고 재현하라** — 간접 증거(측정 `clipped:false`, 화면 스샷)로 판단이 안 서면, **사용자 실제 데이터 + 실제 폰트로 동일 조건을 강제 재현**해 결과물 자체를 눈으로 볼 것. 이번에도 실제 폰트를 심어 재현한 5차에서야 원인이 보였다
- **5. 못 고쳤으면 솔직히, 왜 놓쳤는지까지 설명** — "이번엔 됐다"를 남발하지 말고, 검증한 조건(무엇을·어떤 환경에서 확인했는지)을 함께 밝혀 신뢰를 회복할 것
