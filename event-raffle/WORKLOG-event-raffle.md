## 2026-08-10

### 첨부해준 스니펫으로 트위터/인스타그램 게시물 임베드 보기 추가
- **무슨 요청이었나**: 트위터/인스타그램 임베드 스니펫 파일을 첨부하면서, 후보로
  추려진 사람들의 실제 게시물을 화면에서 바로 볼 수 있게 반영해달라는 요청 —
  단 기본으로 항상 보이게 하지 말고, 버튼을 눌렀을 때만(예: 필터링 한 번 한
  상태에서 필터된 것만) 보이게 해달라는 조건이 붙음.
- **어떻게 처리했나**:
  - 1단계에 "SNS 게시물 링크 컬럼" 선택칸을 새로 추가하고, 트위터/인스타그램
    URL이 담긴 컬럼을 자동으로 찾아 미리 골라둠.
  - 후보 표에 "필터링된 게시물 보기" 버튼을 추가해서, 이 버튼을 누르기 전엔
    아무 게시물도 안 보이고 누른 순간에만 후보들의 게시물이 나타나게 함.
  - 첨부 파일에 적혀있던 주의사항(인스타그램 위젯은 트위터와 달리 "이 영역만
    처리해줘"라고 범위를 지정할 방법이 없어서, 숨겨진 상태로 있다가 위젯이 페이지를
    한 번 훑고 지나가면 나중에 보여줘도 다시 카드로 안 바뀌는 버그)을 그대로
    반영해서, 게시물 마크업을 버튼을 누르기 전까지 `<template>` 안에만 넣어두고
    누른 순간에만 실제 화면(DOM)으로 옮기도록 만듦.
  - 만드는 과정에서 "본문" 컬럼 자동 추정이 게시물 링크(URL)처럼 글자가 긴
    컬럼을 실제 댓글 본문보다 먼저 골라버리는 부수적인 문제를 발견해서 같이
    수정함(URL이 대부분인 컬럼은 본문 후보에서 제외).
- **결과**: 이 샌드박스는 실제 트위터/인스타그램 서버에 접근할 수 없어서, 위젯
  스크립트를 가짜로 대체해 "우리 쪽 연동 로직"(버튼 누르기 전엔 안 보임, 누른
  순간 템플릿에서 실제 화면으로 옮겨지고 위젯 처리 함수가 호출됨, 링크 없는
  후보는 제외됨)만 Playwright로 확인함 — 실제 카드가 예쁘게 그려지는지는
  라이브 배포에서 직접 확인이 필요하다고 미리 안내함.

### 열(컬럼) 삭제 기능 추가
- **무슨 요청이었나**: 필요 없는 컬럼을 통째로 지우는 기능도 넣어달라는 요청
  (1단계든 2단계든 상관없다고 함).
- **어떻게 처리했나**: 1단계 미리보기 표의 컬럼 제목마다 ✕ 버튼을 추가함.
  참가자 데이터 자체(`participants`)에서 지우는 방식이라 미리보기뿐 아니라
  이후 후보 표·다운로드 등 모든 화면에 그대로 반영됨 — 2단계 후보 표에서
  지우면 후보만 반영되고 원본은 안 바뀌어서 일관성이 떨어지길래 1단계에
  두기로 함. 지금 지정된 본문/닉네임/게시물 링크 컬럼이 지워진 게 아니면
  선택을 그대로 유지하고, 지워진 컬럼이 그중 하나였을 때만 남은 컬럼 기준으로
  다시 추정함.
- **결과**: Playwright로 컬럼 삭제 시 미리보기 컬럼 수가 정확히 줄어드는지,
  지정 컬럼은 유지/재추정되는지, 삭제 후에도 필터링이 정상 동작하는지 확인함.

### 조회수 정렬 버튼 추가 + 게시물 보기 전에도 링크를 파란색으로 표시
- **무슨 요청이었나**: "본문 글자 수로 정렬" 옆에 "조회수로 정렬" 버튼도
  추가해달라는 요청. 그리고 "필터링된 게시물 보기"를 누르기 전에도 표 안의
  링크 자체는 파란색 하이퍼링크로 걸어달라는 요청.
- **어떻게 처리했나**:
  - 1단계에 "조회수 컬럼" 선택칸을 추가함(쉼표 표기, "3.5만" 같은 만/천 단위
    표기까지 숫자로 인식). 정렬 버튼을 하나만 지원하던 구조를 여러 개
    지원하도록 바꿔서, 조회수 컬럼이 지정되면 "조회수로 정렬" 버튼이 "본문
    글자 수로 정렬" 옆에 같이 생기게 함.
  - 표 셀 값이 `http(s)://` 로 시작하는 URL이면 평문이 아니라 실제 클릭 가능한
    링크(파란색, 밑줄)로 보여주도록 함. 링크를 눌렀을 때 기존 "행 클릭하면
    접히는" 동작이 같이 일어나지 않도록 이벤트가 겹치지 않게 처리함.
- **결과**: Playwright로 조회수 정렬(오름차순/내림차순, 쉼표·만 단위 표기
  전부 정확히 정렬됨), 미리보기·후보 표 양쪽에서 링크가 실제 파란 링크로
  나오는지, 링크를 눌러도 행이 안 접히는지까지 확인함.

### 조회수 컬럼이 "번호"(순번) 컬럼으로 잘못 잡히는 문제
- **문제**: 실제로 써보니 "조회수" 컬럼 자동 추정이 1,2,3,4...로 한 칸씩
  올라가는 "번호"(행 순번) 컬럼을 조회수로 잘못 골랐음(원인: 순수 숫자이기만
  하면 골랐던 것 — 순번도 숫자라 구분이 안 됐음).
- **어떻게 처리했나**: 여러 행의 값을 확인해서, 값이 정확히 1씩 증가하는
  순번 패턴이면 조회수 후보에서 제외하도록 수정함.
- **결과**: "번호"와 "조회수" 컬럼이 같이 있는 파일로 확인해서 번호 대신
  조회수가 정확히 선택되는 것 확인.

### "SNS 게시물 링크 컬럼" 안내 문구가 화면 밖으로 튀어나오는 문제
- **무슨 문제였나**: 컬럼 선택 칸 라벨/드롭다운 영역이 자기 칸 밖으로
  삐져나온다는 신고. 새 파일을 다시 올려도 그대로였음.
- **확인해보니**: 처음엔 "브라우저에 저장된 예전 선택값 때문"이라고 잘못
  짐작했었음 — 실제 원인은 캐시가 아니라 CSS 버그였음. 컬럼 선택 드롭다운
  (`<select>`)에 폭(width) 스타일이 전혀 지정돼 있지 않아서, 옵션 텍스트가
  길면(예: 게시물 링크의 URL 예시) 브라우저가 "가장 긴 옵션 기준"으로 드롭다운
  폭을 자기 마음대로 넓게 그려버려 정해진 칸 밖으로 삐져나오고 있었음.
- **어떻게 처리했나**: 글자·숫자 입력칸에만 있던 `width:100%` 규칙에 드롭다운도
  포함시킴.
- **결과**: 구버전 코드로 직접 재현해서 칸 폭 229px인데 드롭다운이 327px로
  실제로 튀어나오는 것을 측정으로 확인, 수정 후에는 드롭다운 폭이 칸 폭과
  정확히 일치하는 것까지 확인함.

### "조회수 정렬 누르면 지운 컬럼이 되살아난다" 신고 (원인 특정 못 함)
- **무슨 문제였나**: 컬럼을 지운 뒤 "조회수로 정렬"을 누르면 지운 컬럼이 다시
  나타난다는 신고.
- **확인해보니**: 있을 법한 경로 세 가지(① 필터링 → 컬럼 삭제 → 재필터링 →
  정렬, ② 재필터링 없이 정렬 버튼을 강제로 클릭, ③ 컬럼 삭제 후 새로고침해서
  캐시가 복원되는 경우)를 Playwright로 직접 실행해봤지만 컬럼이 되살아나는
  현상 자체는 재현되지 않음 — 다만 그 과정에서 진짜 결함 두 개를 발견함:
  컬럼을 지우면 후보 표가 사라져야 하는데 다운로드·복사·게시물 보기 버튼은
  안 사라지고 그대로 남아있던 문제, 그리고 표 데이터가 화면에서는 숨겨져도
  내부(DOM)에는 안 지워지고 남아있던 문제.
- **어떻게 처리했나**: 위 두 결함은 같이 수정함(컬럼 삭제 시 관련 버튼도 모두
  숨기고, 표 내용도 실제로 비움).
- **결과**: 두 결함 수정은 Playwright로 확인함. 다만 신고된 "정렬 누르면
  컬럼이 되살아난다" 그 현상 자체는 재현/확인을 못 했고, 정확한 재현 순서를
  사용자에게 다시 확인 요청한 상태 — 아직 미해결.

## 2026-07-29

### 같은 단어/문장을 반복해서 도배하는 사람 잡아내기
- **무슨 요청이었나**: 같은 단어나 문장을 4번 이상 반복하는 "도배" 댓글이 너무 많다는
  문제 제기. "사스케사스케사스케사스케..." 처럼 띄어쓰기·구두점 없이 완전히 붙여 쓴
  경우까지 잡을 수 있는지, 그리고 "ㅋㅋㅋㅋ" 같은 1글자 반복(감탄 표현)은 도배가 아니니
  예외로 해달라는 요청이 이어짐.
- **확인해보니**: 처음엔 이 판별용 정규식을 AI(plan-filter)가 조건 문장을 보고 직접
  새로 작성하게 했는데, 실제 프로덕션 API로 여러 번 확인해보니 AI가 "1글자 반복은
  먼저 뭉개고 봐야 한다"는 핵심 단계를 계속 빠뜨려서 "ㅋㅋㅋㅋ"를 도배로 잘못 판단하는
  문제가 반복 재현됨 — 정규식이 복잡한 다단계 로직이라 AI에게 매번 그대로
  재현시키는 건 신뢰할 수 없다고 판단함.
- **어떻게 처리했나**: 이 판별 로직(공백·구두점·기호 제거 → 연속으로 같은 글자가
  반복되는 부분을 하나로 뭉개기 → 2글자 이상 단위가 붙어서 반복되는지 정규식
  역참조로 확인)을 브라우저 코드에 미리 검증된 함수로 고정해둠(`isRepeatSpam`).
  AI에게는 이 함수를 이름으로 호출하는 codeRule만 만들도록(예:
  `isRepeatSpam(row["본문"], 4)`) 역할을 제한해서, 정규식을 직접 새로 짜지
  못하게 함. 조건 입력 화면에 "+ 반복 도배 조건 추가" 버튼과 반복 횟수 입력칸(기본
  4번)을 새로 추가함.
- **결과**: Node와 브라우저 양쪽에서 12가지 경우(붙여쓰기/띄어쓰기 반복, 3번뿐이라
  통과 안 되는 경우, 1글자 반복 예외, 겹받침 있는 정상 단어 등)를 미리 검증함. 실제
  프로덕션 API에 같은 조건을 4번 반복 호출해봐도 매번 정확히 `isRepeatSpam` 호출
  형태로 나오는 것 확인. 실제 도배 예시가 섞인 파일로 끝까지 돌려서 도배 작성자만
  정확히 잡히고 감탄 표현("ㅋㅋㅋㅋ")은 제외되는 것까지 확인함.

### "300자 이상 쓴 사람 중에서 도배한 사람 제외"로 추리기
- **무슨 문제였나**: 도배 조건을 실제로 써보니, 지금 방식은 "도배에 해당하는 사람만
  걸러내는" 방향으로만 동작해서 "도배 아닌 사람만 남기기(제외)"로는 못 씀 —
  글자 수 조건과 반복 도배 조건을 그냥 그리고(AND)로 묶으면 오히려 "도배한
  사람"까지 걸려버림.
- **확인해보니**: 조건 칸 자체에 "이 조건에 해당하면 뺀다(반대로 적용)"는 개념이
  없었던 게 원인 — 조건을 걸면 무조건 "포함" 방향으로만 조합되고 있었음.
- **어떻게 처리했나**: 모든 조건 칸(자유 텍스트/글자 수/반복 도배)에 "제외"
  체크박스를 추가함. 체크하면 그 조건이 반대 의미 문장으로 바뀌어 조합됨 —
  글자 수 조건은 "~자 미만인 사람", 반복 도배 조건은 "반복되지 않는 사람(도배
  제외)", 자유 텍스트는 "~에 해당하지 않는 사람"으로 바뀜. plan-filter
  프롬프트에도 반복 도배 조건이 "제외" 형태로 표현되면 `isRepeatSpam` 호출 앞에
  `!`를 붙이도록(다른 조건과 `&&`로 결합하는 예시 포함) 지침을 추가함.
- **결과**: "글자 수 300자 이상 AND 반복 도배 제외" 조합을 실제 프로덕션 API에
  4번 반복 호출해서 매번 정확히
  `row["본문"].length >= 300 && !isRepeatSpam(row["본문"], 4)`
  형태로 나오는 것까지 확인함. 사용자가 직접 이 조합으로 필터링해서 37명이
  선정되는 것도 확인함.

### 다운로드 전에 필터링한 목록을 클립보드로 복사하고 싶다는 요청
- **무슨 요청이었나**: 후보 명단을 파일로 다운로드하기 전에, 클립보드로 바로 복사해서
  쓸 수 있는 기능도 넣어달라는 요청.
- **어떻게 처리했나**: 후보 명단 다운로드 버튼 위에 "후보 명단 클립보드로 복사"
  버튼을 추가함. 처음엔 엑셀에 붙여넣기 좋은 탭 구분(TSV) 텍스트로 만들었음.
- **결과**: Playwright로 복사된 내용이 실제 후보 수·헤더와 일치하는지, 후보를 하나
  수동으로 삭제한 뒤 다시 복사하면 줄어든 인원만 반영되는지 확인함.

### 복사한 게 표(|)로 안 보여서 불편하다는 피드백
- **무슨 문제였나**: 위에서 만든 탭 구분 복사 결과를 실제로 써보니, 노션·슬랙·깃허브처럼
  마크다운을 그대로 표로 렌더링해주는 곳에 붙여넣으면 탭 문자가 그냥 밋밋한 텍스트로만
  보이고 표 모양이 안 나와서 불편하다는 지적.
- **어떻게 처리했나**: 복사 형식을 탭 구분에서 `|`로 구분된 마크다운 표 형식(제목 행 +
  `---` 구분 행 + 데이터 행)으로 바꿈. 셀 안에 `|` 문자가 실제로 들어있는 경우는
  표가 깨지지 않도록 이스케이프 처리함.
- **결과**: 복사된 텍스트를 다시 확인해서 제목 행에 `|`가 정확히 들어가고, 구분 행이
  `| --- | --- | ... |` 형태인지, 데이터 행도 형식에 맞는지 Playwright로 확인함.

### 조건을 여러 칸으로 분리 + AND/OR 명시 선택 + 본문 컬럼 직접 지정
- **무슨 문제였나**: 같은 409명 파일로 계속 테스트하는 과정에서, 조건 문장 하나에 여러
  조건을 자연어로 섞어 쓰면(예: "사진 첨부하고 정성스럽게 쓴 사람") 그리고/또는이 정확히
  어디에 걸리는지 애매해지는 문제, 그리고 컬럼명만 보고는 어떤 컬럼이 진짜 참가자 댓글
  본문인지 코드도 AI도 확신할 수 없는 문제가 확인됨(이 파일엔 참가자 댓글과 무관한 캐릭터
  랭킹 집계표까지 같은 시트에 섞여 있었음).
- **어떻게 처리했나**: 조건 입력을 텍스트 한 칸에서 "조건1/조건2/조건3..." 여러 칸으로
  나누고, 각 조건 사이에 그리고(AND)/또는(OR)을 사용자가 직접 고르게 함. 왼쪽부터 순서대로
  묶어서 "(조건A) AND (조건B) OR (조건C)" 형태의 명확한 문장으로 조합해 서버에 보내도록
  바꿈(자연어 문장이 가진 연산자 우선순위 모호함 자체를 없앰). 업로드 직후 "댓글/후기 본문"
  컬럼과 닉네임 컬럼을 사용자가 직접 지정하게 하고(값이 평균적으로 가장 긴 컬럼을 본문으로
  자동 추정해 미리 골라둠), 이후 필터링/AI 판단은 오직 이 컬럼 내용만 기준으로 판단하도록
  변경 — 무관한 컬럼(랭킹 집계표 등)은 애초에 API에 보내지 않으므로 전송 데이터도 줄고
  비용도 낮아짐.
- **결과**: 실제 파일로 Playwright 검증 — 자동 컬럼 추정이 실제 댓글/닉네임 컬럼을 정확히
  찾아냄, 조건 3개+AND/OR 조합이 서버에 올바른 문장으로 전달됨, 당첨자 카드에 실제 닉네임이
  표시됨을 확인. 기존 회귀 테스트(코드/AI 세 시나리오 + 0명 처리)도 모두 재검증 통과.

### "나히아 OR 정성스럽게"로 조건을 걸면 항상 전체 인원이 AI로 넘어가는 문제
- **무슨 문제였나**: "나히아(히로아카 동의어)" 단독 조건은 39명만 추려지는데, 여기에
  "또는 정성스럽게 쓴 사람"을 더하면 409명 전체가 AI 판단으로 넘어간다는 재신고. 처음엔
  "OR로 묶인 조건 중 하나라도 순수 주관적 판단(정성스러움)이면, 그 조건만으로도 통과할 수
  있는 사람이 있을 수 있어서 코드가 미리 걸러낼 수 없는 구조적 한계"라고 설명했으나, 이
  설명에 대한 반박(비용을 줄일 방법을 코드로 직접 제안)이 있었음.
- **확인해보니**: 구조적 한계 설명 자체는 틀리지 않았음(OR + 주관적 조건은 전체를 봐야
  하는 게 맞음) — 하지만 "정성스러움"을 무조건 AI 판단으로만 취급해야 하는 건 아니라는
  지적이 맞았음. 짧은 참여 인증성 댓글("참여요" 등)과 실제 이유를 풀어 쓴 긴 댓글은 글자
  수만으로도 상당히 잘 구분됨.
- **어떻게 처리했나**: plan-filter가 "정성스럽게/진심이 담겼는지/성의있게 썼는지" 같은
  조건을 만나면 기본적으로 글자 수 기준 코드 규칙(`row["본문"].length >= N`)으로 처리하도록
  프롬프트를 바꿈. 이러면 "나히아 OR 정성스럽게" 같은 조합도 양쪽 다 코드로 판단 가능해져
  AI 호출 자체가 필요 없어짐. 완벽한 정확도보다 비용 절감을 우선하는 트레이드오프라는 점을
  프롬프트에 명시함.
- **결과**: 실제 조건으로 다시 확인 — "(나히아) OR (정성스럽게 쓴 사람)" 조합이
  `(row) => /나히아|나히야|나희아|nahia/i.test(row["본문"]) || row["본문"].length >= 20`
  같은 코드 규칙 하나로 만들어져 AI 호출 없이(비용 0) 처리되는 것을 실제 API 호출로
  확인함.

### 글자 수 기준을 직접 정할 수 있는 "글자 수 조건" 칸 추가
- **무슨 요청이었나**: 위 글자 수 휴리스틱을 AI가 알아서 추측하게 두지 말고, 파일을 넣을
  때마다 실제 글자 수 분포를 통계로 보여주고 사용자가 직접 기준을 정하게 해달라는 요청.
  전체 400명 중 절반(200명)이 걸리는 기준이면 "정성 조건"으로 의미가 있는지 의문이라는
  지적도 있었음. 구체적인 구간 예시(0~10자/10~20자/20~40자/40~100자 이상)를 직접
  제시했으나, 그 구간을 그대로 쓰지 말고 파일마다 실제 분포에 맞게 자동으로 나누는 방식을
  생각해보라는 요청이 뒤따름.
- **어떻게 처리했나**: 파일 업로드 시 본문 글자 수를 5개 구간으로 자동 분할하되, 구간
  경계는 고정값이 아니라 이번 파일의 실제 최대 글자 수에 맞춰 매번 다시 계산하도록 함
  (`computeLengthStats` — 최소/중앙값/평균/최대까지 함께 계산). 이 통계를 화면에 보여주고,
  그 옆에 사용자가 직접 숫자를 입력하는 "글자 수 조건" 칸을 새로 추가함(기본값은 중앙값으로
  미리 채워둠). 이 조건은 100% 코드로만 판단되어 AI 호출이 전혀 없고, 기존 자유 텍스트
  조건과 그리고/또는으로 섞어 쓸 수 있음. 기존에 자유 텍스트로 "정성스럽게"라고만 입력했을
  때 AI가 알아서 글자 수 기준을 추측해주던 폴백 동작은 그대로 남겨둠(둘 중 골라 쓸 수
  있게).
- **결과**: 실제 업로드 파일로 확인 — 자동 통계가 실제 분포(중앙값 19자 등)를 정확히
  계산하고, 글자 수 조건 기본값이 중앙값으로 채워지며, "(나히아) OR (본문 글자 수가 50자
  이상인 사람)" 같은 조합이 코드로만(AI 비용 0) 처리되는 것까지 확인함.

### 표 셀이 잘려서 안 보이고, 당첨자 원본 데이터도 안 보이는 문제
- **무슨 문제였나**: 스크린샷으로 확인한 결과, 미리보기/후보 표에서 긴 댓글이 잘려 보이는데
  전체 내용을 볼 방법이 없었음. 또한 추첨이 끝난 뒤 당첨자 카드에는 닉네임과 판단 근거만
  보이고, 그 사람이 실제로 어떤 댓글을 남겼는지(원본 데이터)는 확인할 방법이 없었음.
- **어떻게 처리했나**: 표의 행을 클릭하면 그 행만 줄바꿈이 풀리며 전체 내용이 펼쳐지고,
  다시 클릭하면 원래대로 접히도록 함. 당첨자 카드에는 "원본 데이터 보기" 토글을 추가해서
  클릭하면 그 사람의 전체 컬럼 데이터를 볼 수 있게 함 (`<details>`/`<summary>` 사용).
- **결과**: 실제 업로드 파일로 Playwright 검증 — 표 행 클릭 시 펼쳐짐, 당첨자 카드 토글
  클릭 시 전체 원본 데이터가 표시됨을 확인. 기존 회귀 테스트 전체도 재검증 통과.

### 표 기본 펼침 전환 + xlsx 다운로드 + 결과 누적 저장 + 난수 화면 표시
- **무슨 요청이었나**: 리뷰 후 이어서 들어온 요청 묶음 — ① 표를 기본으로 펼친 상태로 두고
  접기/펼치기 버튼을 따로 넣을 것(클릭해서 개별 행 접는 기존 동작은 유지), ② 결과
  다운로드를 JSON 대신 엑셀로, ③ 당첨자 명단을 회차마다 파일 하나씩 받는 대신 서버에 계속
  쌓이게(누적) 저장, ④ 추첨에 실제로 쓰인 난수 값을 화면에도 표기.
- **어떻게 처리했나**: 표 기본 상태를 펼침으로 뒤집고(`.collapsed` 클래스를 붙였을 때만
  접히도록 CSS 반전), 표 위에 "전체 접기/펼치기" 버튼을 추가하면서 기존 행 클릭 토글도
  그대로 유지함. 다운로드는 이미 불러와져 있던 SheetJS로 엑셀 파일을 만들어 브라우저에서
  바로 받도록 변경함 (`XLSX.utils.json_to_sheet` + `XLSX.writeFile`). 저장은 회차별 파일
  대신 `event-raffle/results/history.json` 하나에 계속 이어붙이는 방식으로 바꾸고, 그
  사이 다른 저장 요청이 먼저 반영돼 충돌 나는 경우(sha 낡음)에는 최신 내용을 다시 받아와
  합친 뒤 최대 3번까지 재시도하도록 함(과거 기록이 덮어써져 사라지는 것 방지). 추첨 시마다
  실제 난수 값과 그 시점 후보 수, 몇 번째로 뽑혔는지를 기록해서 화면과 다운로드/저장 파일에
  모두 남기도록 함.
- **결과**: 누적 저장 로직은 실제 파일을 만들지 않고 가짜 GitHub API로 신규 생성/누적
  append/충돌 시 재시도 3가지 경우를 모두 검증함(진짜 저장 코드를 그대로 불러와서 검증 —
  재구현 아님). 그 외 UI 변경은 Playwright로 기본 펼침 상태, 전체 토글 버튼, 난수 값 화면
  표시, xlsx 다운로드 모두 확인함. 기존 회귀 테스트도 전부 재검증 통과.

### 본문 컬럼이 눌려서 표가 이상해진 문제 (필터 이후 표에도 적용 요청)
- **무슨 문제였나**: 스크린샷 확인 결과 댓글(본문) 컬럼이 갑자기 매우 좁고 어색하게
  줄바꿈되어 보임 — 조금 전까진 안 그랬는데 왜 이렇게 됐는지 문의. 그리고 제목 행만 있고
  그 이후로 값이 거의 없는(전체의 1% 이하) 컬럼은 표에서 아예 빼달라는 요청, 이어서 이
  컬럼 제거를 "미리보기 표"뿐 아니라 "필터링 이후 후보 표"에도 똑같이 적용해달라는 요청이
  추가됨.
- **확인해보니**: 두 가지가 겹쳐 있었음. ① 실제 파일 컬럼별 채움 비율을 직접 계산해보니
  스크래퍼가 남긴 무관한 랭킹 집계 컬럼(`__EMPTY_1~9`)들이 1%가 아니라 4.6~7.6% 정도
  채워져 있어서, 애초에 정해뒀던 "1% 이하만 제거" 기준(`getMeaningfulColumns`의
  `threshold`)이 이 컬럼들을 걸러내지 못하고 있었음. ② 컬럼 선택 드롭다운을 채우는 코드
  (`populateColumnSelectors`)가 표를 그리는 코드보다 나중에 실행되고 있어서, 본문 컬럼이
  아직 정해지지 않은 상태로 표가 먼저 그려져 폭 힌트가 적용되지 않고 있었음.
- **어떻게 처리했나**: 컬럼 제거 기준을 실측값에 맞춰 1%에서 10%로 올림. 두 함수의 실행
  순서를 바로잡아 컬럼이 먼저 정해진 뒤에 표를 그리도록 함. 필터링 이후의 후보 표는 전체
  참가자 기준이 아니라 후보 집합 자체를 기준으로 다시 계산해서 컬럼을 제외하도록 별도
  처리함. 본문으로 지정된 컬럼 헤더에는 최소 폭을 줘서 다른 빈 컬럼들 때문에 좁게 눌리지
  않게 함.
- **결과**: 실제 파일로 재검증 — 미리보기가 13개에서 5개 컬럼으로 줄어듦, 본문 컬럼에 폭
  힌트가 정상 적용됨, 후보 표도 후보 집합 기준으로 별도 계산되는 것까지 확인. 기존 회귀
  테스트 전부(세 시나리오 + 0명 처리 + 조건 칸 + 이전 UI 개선) 재검증 통과.

### 참가자 파일을 이 PC에만 캐싱해서 다음 방문 시 자동으로 이어서 쓰기
- **무슨 요청이었나**: 다른 프로젝트(inbound-image-composer)에서 쓰던 "슬롯 캐싱" 방식을
  참고해서, 파일을 업로드하면 기본적으로 실행되고 나중에 다시 들어왔을 때 저번 파일이
  캐싱돼서 보이도록 해달라는 요청(단 이 PC에서만). 캐시 항목에 삭제 버튼이 당연히 있어야
  한다는 확인도 함께 있었음.
- **어떻게 처리했나**: 참가자 파일을 업로드하면 이 PC의 브라우저에만(서버·깃허브에는 전혀
  안 올라감) 최근 5개까지 저장하고, 다음에 페이지를 다시 열면 가장 최근 파일을 자동으로
  불러오도록 함 (`localStorage` 기반 슬롯 캐시, `SLOT_MAX=5`). 내용이 완전히 같은 파일은
  중복 저장하지 않고, 저장 용량이 부족하면 오래된 슬롯부터 무거운 참가자 데이터를 빼고
  다시 저장을 시도함. 업로드 직후·컬럼 선택 변경 시·탭을 닫거나 전환할 때(안전망) 자동으로
  저장되도록 하고, 각 캐시 항목마다 불러오기 버튼과 삭제(✕) 버튼을 넣음. 참가자 데이터
  저장 범위가 달라진 만큼 소개 카드 문구도 "이 PC 브라우저에만 최근 5개까지 남는다"로
  정정함.
- **결과**: Playwright로 전체 흐름 검증 — 첫 방문엔 캐시 없음 → 업로드 직후 바로 캐싱됨 →
  새로고침해도 자동으로 복원됨 → 다른 파일을 올리면 캐시가 2개로 늘어남 → 삭제 버튼으로
  캐시 제거됨 → 남은 캐시를 클릭하면 다시 정상적으로 불러와짐, 전부 확인함. 기존 회귀
  테스트 5종도 모두 재통과함. 커밋 직후 다른 세션이 먼저 올린 커밋과 겹쳐 `main` 푸시가
  한 번 거절됐으나, 강제 푸시 없이 `git fetch` + `rebase` 후 재푸시로 정상 반영함.
