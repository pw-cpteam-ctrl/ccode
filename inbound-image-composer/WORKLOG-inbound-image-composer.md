## 2026-08-21

### 실제 스토어 페이지 스크린샷에서 사진이 어긋나게 크롭되는 문제
- **문제** ▶ "이 입고 이미지 계속 크롭 오류가 발견되는데" — 실제 브랜드 스토어 캡처(1000×1690px, 5×5=25칸)를 넣으면 몇몇 칸의 사진이 옆 칸이나 위아래로 어긋나게 잘림. "다시 검출"을 3번 눌러도 동일하게 재현됨
- **확인** ▶ 처음엔 채팅에 붙여넣은 스크린샷만으로 어느 칸이 얼마나 어긋났는지 픽셀 단위로 확신을 못 잡고 자꾸 되묻기만 해서 시간을 끎 — "재검출해도 똑같다"는 신고 자체가 이미 원인을 가리키고 있었는데(재시도는 흰색 판정 임계값만 바꿀 뿐 구조적 문제는 안 건드림) 그걸 놓치고 있었음
  - 코드를 다시 보니 두 군데에 같은 종류의 결함이 있었음
    - 열(가로) 위치를 검출된 행 중 **딱 하나에서만** 찾아 5개 행 전체에 그대로 재사용하고 있었음 — 실제 캡처는 행마다 카드 좌측 여백이 몇 px씩 다를 수 있어서, 대표로 뽑힌 행이 아닌 나머지 행은 사진 한쪽이 잘리고 반대쪽엔 흰 틈이 낌
    - 반대 방향(세로)도 마찬가지 — 행 위치도 5개 열 중 가장 많이 잡힌 딱 하나에서만 찾아 전체 열에 재사용하고 있어서, 상품명이 한 줄인 열과 두 줄인 열이 섞여 있으면 다음 행 시작 지점이 밀린 열은 사진 위아래가 이전 행 텍스트를 물거나 잘림
  - 합성 테스트(특정 행만 가로로 15px 밀림, 특정 열만 세로로 20px 밀림)로 두 가지 다 실제로 재현됨을 확인함
- **처리** ▶ 열/행 좌표를 대표 하나로 고정하지 않고, 각 행에서 열을 다시 검출하고(`colsByRow`) 각 열에서 행을 다시 검출하도록(`rowsByCol`) 바꿈 — 칸 하나의 좌표는 그 행·그 열 고유의 값으로 계산됨. 검출 개수가 기준과 다르면(그 칸이 유독 흰 편이라 덜 잡히는 경우 등) 안전하게 공통 좌표로 되돌아감
- **결과** ▶ 배포 후 라이브 페이지에서 확인해 반영된 것 확인. 합성 테스트로 가로/세로 어긋남 각각 재현 → 수정 후 정확히 잘리는 것 확인했고, 원래 정상이던(어긋남 없는) 케이스도 회귀 없이 그대로 동작함을 확인함

### 위 수정 배포 후에도 세로로 한 열만 계속 어긋나는 문제 (재신고)
- **문제** ▶ 시크릿 모드로 캐시까지 배제하고 재테스트했는데도 특정 한 열만 세로로 계속 어긋남. "다시 검출" 3번 다 동일
- **확인** ▶ 처음엔 이번에도 실제 스크린샷 없이 판단하려다 지적받음 — 사용자가 라이브 화면을 다시 캡처해서 보내준 뒤 코드를 다시 살펴봄. 열별로 행을 다시 검출하는 로직(`rowsByCol`)이 그 열의 **좌측 시작점** 픽셀에서 세로로 스캔하고 있었는데, 그 지점은 사진과 흰 배경의 경계선이라 사진 테두리가 둥글거나 그림자가 있으면 특정 행에서 흰색으로 잘못 읽혀 그 행이 통째로 누락될 수 있음 — 재검출을 눌러도 이 x좌표 자체는 안 바뀌니 매번 같은 열만 어긋났던 것
- **처리** ▶ 샘플링 지점을 열의 좌측 시작점에서 그 열 사진의 가로 중앙으로 변경 — 애초에 첫 행을 찾을 때부터 열 "가운데" 지점을 쓰던 방식과 통일함
- **결과** ▶ 둥근 모서리/비네트가 있는 합성 사진으로 재현 시도했으나 이번 합성 테스트에서는 수정 전후 차이가 뚜렷이 재현되지 않음 — 중앙 샘플링이 더 안전한 방식이라는 근거로 반영했으나, 사용자의 실제 캡처로 재확인이 아직 필요함

### 시크릿 모드로도 여전히 1열이 어긋나는 문제 (재신고)
- **문제** ▶ 시크릿 모드에서도 1열(왼쪽 첫 번째 칸들)만 계속 어긋남 — 위 두 차례 수정으로도 해결 안 됨
- **확인** ▶ 어느 열인지 계속 말로만 확인하려다 같은 질문을 반복해서 지적받음. "1열"이라는 답을 받은 뒤, 헤더 배너 디자인 요소가 특정 열의 위쪽까지 걸쳐 있으면 그 열만 "행 개수는 맞는데 위치 자체가 다른 열들과 완전히 동떨어진" 검출 결과가 나올 수 있는 경우의 수를 추가로 발견함 — 지금까지의 검출 로직은 "개수가 맞으면 그대로 믿는" 방식이라 이런 경우를 못 걸러냄
- **처리** ▶ 같은 행 번호끼리 5개 열의 검출값을 모아 중앙값을 구하고, 중앙값에서 30px 넘게 떨어진 열만 검출 오류로 보고 중앙값으로 대체하도록 안전장치 추가. 또한 "몇 번째 열"이라는 말이 사람마다 세는 기준이 달라 혼선을 만들었으므로, 1단계 미리보기 각 칸에 "행-열" 번호를 직접 표기해서 앞으로는 정확히 지목할 수 있게 함
- **결과** ▶ 배너 장식이 걸친 상황을 합성 테스트로 재현해 중앙값 보정이 정상 동작함을 확인함. 다만 이번에도 사용자의 실제 캡처 자체로 검증하지는 못했음(채팅에 붙여넣은 이미지는 파일로 접근할 방법이 없어 합성 테스트로만 확인 가능함) — 칸 번호 표기가 반영된 뒤에는 재신고 시 정확한 칸 번호로 확인 가능할 것으로 기대함

## 2026-07-13

### 배포가 갑자기 멈춘 문제 (다른 툴 포함, 원인 파악까지)
- **무슨 문제였나**: 새 기능을 올려도 실제 서비스 페이지에 반영이 안 됨. 배포 목록을 봐도
  5시간 넘게 아무 변화가 없었음. 사용량 초과, 서버 장애 등 여러 가능성을 하나씩 확인.
- **확인해보니**: 사용량 초과도 아니었고 서버 자체 장애도 아니었음. 실제 원인은 웹사이트를
  올리는 서비스(Vercel)와 우리 저장소(GitHub)를 연결해주는 통로 자체가 끊겨서, 코드를
  올려도 "새로 배포해야 한다"는 신호 자체가 전달이 안 되고 있었던 것.
- **어떻게 처리했나**: 이 통로 연결 문제는 다른 작업자가 같은 날 별도로 찾아서 고쳐놓음
  (연결 방식을 더 안정적인 방식으로 교체). 우리 쪽에서는 원인을 좁혀서 확인하는 역할을 함.
- **결과**: 이후 커밋부터는 정상적으로 배포에 반영되는 것을 확인함.

### 그리드(사진 칸) 인식이 특정 상황에서 실패하는 문제
- **무슨 문제였나**: 두 가지 증상이 보고됨. ① 업로드한 스크린샷 가로 폭이 표준(약 1000px)이
  아니면 사진 칸을 하나도 못 찾음. ② 표준 폭이어도 5칸 중 1칸(예: 흰 배경 스티커/아이콘류
  상품)이 계속 통째로 안 잡힘.
- **확인해보니**: ①은 칸 위치를 찾는 로직이 "가로 폭이 항상 딱 1000px일 것"이라고 가정한
  채 고정된 좌표만 보고 있었기 때문 (`sampleCols`/`cardW`/`cardH`가 1000px 기준 절대
  좌표로 고정돼 있었음). 폭이 다르면 완전히 엉뚱한 위치를 보게 됨. ②는 칸 경계를 찾을 때
  사진 한 줄 중 딱 한 지점만 확인하는 방식이었는데 (`detectColStarts`가 첫 행 시작점+40px
  딱 한 지점만 샘플링), 하필 그 위치의 색이 흰색에 가까운 상품(흰 배경 아이콘 등)이 있으면
  "여기 상품 없음"으로 잘못 판단해서 그 칸을 건너뛰어버린 것.
- **어떻게 처리했나**: ①은 고정된 숫자 좌표 대신, 실제 업로드된 이미지 폭에 비례해서
  위치를 계산하도록 바꿈(폭이 얼마든 같은 비율로 알아서 맞춰짐) (`img.width` 기준
  비율로 좌표들을 다시 계산). ②는 딱 한 지점만 보지 않고, 여러 줄 · 여러 높이를 번갈아
  확인해서 가장 많은 칸이 찾아지는 결과를 채택하도록 바꿈 (여러 행 × 여러 세로 오프셋을
  교차 시도해서 검출된 열이 가장 많은 결과를 채택) — 한 상품 사진이 흰 편이어도 다른
  줄의 같은 위치 상품은 대부분 다르게 생겼으니 잡힐 확률이 훨씬 높아짐.
- **결과**: 실제로 문제와 똑같은 상황(가로 폭이 다른 이미지, 흰 배경 상품이 낀 5칸 배치)을
  직접 만들어서 테스트해봤고, 둘 다 정상적으로 다 잡히는 것까지 확인함.

### 최종 이미지에 헤더(매장 배너)가 안 나오는 문제
- **무슨 문제였나**: 최종 페이지 만들기에서 헤더 이미지를 골랐는데도 실제로 다운로드해보면
  헤더 없이(또는 텅 빈 이미지로) 나온다는 신고가 있었음.
- **확인해보니**: 사진과 글자, 그리고 헤더를 화면에 합쳐서 그리는 부분 자체는 직접 만든
  테스트 데이터로 끝까지 돌려봐도 문제없이 정상 동작했음. 그래서 코드 자체의 버그라기보다,
  "헤더"로 쓰이는 부분이 애초에 "업로드한 스크린샷에서 첫 번째 상품 줄보다 위쪽 부분을
  그대로 오려낸 것"이라는 점이 원인일 가능성이 높다고 판단함 (`GridDetect.cropCell(원본이미지,
  0, 0, 이미지폭, 첫행시작y)`로 오려서 저장) — 만약 올린 스크린샷 자체가 매장 배너 없이
  상품부터 바로 시작하는 캡처였다면, 오려낼 배너 자체가 없으니 당연히 비어 보이게 됨.
- **어떻게 처리했나**: 정확한 원인을 말로만 설명하는 대신, 최종 페이지 화면에 "지금 선택된
  헤더가 실제로 어떤 그림인지" 바로 보여주는 미리보기를 추가함 (`updateHeaderPreview()`
  함수 추가, 헤더 드롭다운을 바꿀 때마다 썸네일 갱신). 이러면 사용자가 직접 눈으로
  "비어 있는지 아닌지" 바로 확인할 수 있어서, 원인이 코드 문제인지 원본 캡처 문제인지
  스스로 판단할 수 있게 됨.
- **결과**: 미리보기 기능은 실제로 이미지를 넣고 확인해봤고 정상적으로 화면에 뜨는 것까지
  확인함. 다만 실제로 신고된 그 헤더가 정확히 왜 비어 있었는지(원본 캡처 문제였는지 다른
  이유였는지)는 사용자가 미리보기로 직접 확인해야 최종 확정 가능.

### "등급표에 이미 있는 상품인데도 계속 미분류로 뜨는" 문제
- **무슨 문제였나**: 이미 유명해서 등급표에 등록해둔 상품(예: 특정 인기 애니메이션)인데도,
  AI로 자동 채우기를 한 뒤에는 계속 "미분류(기타)"로 표시됨.
- **확인해보니**: 이 프로그램은 "브라우저에 저장해둔 설정값"과 "기본 제공 설정값"을 합쳐서
  쓰는 구조인데, 합치는 방식에 문제가 있었음 — 브라우저에 저장된 값이 하나라도 있으면
  기본 제공 값 전체를 무시하고 덮어써버렸음 (`loadDict()`에서
  `local.gradeTable || seed.gradeTable` 식으로, 로컬 값이 있으면 시드값 전체를 통째로
  교체하는 구조였음). 그래서 나중에 기본 설정에 새로 추가된 등급 정보가 있어도, 예전에
  저장해둔 값 때문에 계속 반영이 안 되고 있었던 것. (사전 데이터를 관리하는 여러 항목—
  등급표, 분위기 클러스터, 스토어 프로필, 상품 라인명—이 다 같은 방식으로 잘못돼 있었음)
- **어떻게 처리했나**: 저장된 값과 기본 제공 값을 "덮어쓰기"가 아니라 "둘 다 합쳐서 쓰기"
  방식으로 바꿈 (`mergeGradeTable()`/`mergeMoodClusters()` 함수를 새로 만들어 배열을
  합집합으로 병합) — 같은 항목이 겹치면 저장된 값을 우선하되, 기본 제공 값 중 저장 안 된
  나머지는 그대로 살아있게 함.
- **결과**: 등급표에 있는 상품을 다시 인식시켜보니 정상적으로 자동 분류되는 것을 확인함.

### AI가 미등록 상품의 성향까지 추측하도록 기능 추가
- **무슨 요청이었나**: 등급표에 없는(신규) 상품은 매번 사람이 직접 "남성향/여성향"을
  분류해야 해서 번거로움 — AI가 이것도 좀 도와줄 수 없냐는 요청.
- **어떻게 처리했나**: 등급표에 이미 등록된 상품은 원래대로 그 정보를 그대로 쓰고(AI가
  건드리지 않음), 등록이 안 된 신규 상품에 한해서만 AI가 사진과 상품명을 보고 남성향인지
  여성향인지 추측해서 미리 채워두도록 함 (AI 응답 항목에 `genderLean` 필드를 추가하고,
  `applyAiGenderLean()` 함수가 등급표에 없는 IP에만 이 값을 반영). 다만 "얼마나 잘 팔릴
  것 같은지(우선순위 등급)"는 AI가 판단할 수 있는 영역이 아니라서, 일단 기본값으로
  채워두고 최종 확인/조정은 여전히 사람이 하도록 남겨둠.
- **결과**: 새로 만든 기능이라 실제 사진 인식 결과로는 아직 확인 못 했고, 코드 로직만
  점검한 상태 — 다음에 실제로 AI 자동 채우기를 써볼 때 결과를 같이 확인해야 함.

### 화면 단계 통합 (미리보기 화면과 정렬 화면이 겹쳐서 헷갈리던 문제)
- **무슨 문제였나**: "전체 미리보기" 화면과 "순서 정렬" 화면이 따로 있었는데, 둘 다
  "카드를 마우스로 끌어서 순서 바꾸기" 기능을 똑같이 갖고 있어서 왜 화면이 나뉘어 있는지
  헷갈린다는 지적이 있었음.
- **어떻게 처리했나**: 두 화면을 하나로 합침 (화면 두 개를 각각 그리던 렌더 함수 호출을
  하나로 합치고, HTML도 두 화면분 내용을 한 화면 안에 병합) — 이제 미리보기, 삭제, 자동
  정렬, 수동으로 끌어서 순서 바꾸기를 전부 한 화면에서 처리한다. 전체 진행 단계도 5단계에서
  4단계로 줄음.
- **결과**: 실제로 화면을 눌러가며 확인해봤고, 한 화면에서 삭제/자동정렬/수동조정이 다
  정상적으로 동작하는 것을 확인함.

### 표 정리 화면 편의 기능 추가
- **무슨 요청이었나**: ① 같은 상품(IP)끼리 구분하기 어려움. ② 여러 항목을 한 번에 골라서
  태그나 분류를 한꺼번에 바꾸고 싶음.
- **어떻게 처리했나**: ① 같은 상품명을 가진 항목끼리 카드 테두리 색을 맞춰서 한눈에 묶여
  보이게 함 (`colorForIp()` 함수가 상품명 글자를 계산해서 정해진 색상 목록 중 하나를
  자동으로 골라줌). ② 빈 공간을 마우스로 끌면 여러 항목을 한 번에 선택할 수 있게 하고,
  선택한 항목들의 태그나 분위기 분류를 한 번에 바꾸는 버튼을 추가함 (드래그 선택 기능을
  다른 화면과 공용으로 쓰게 만들고, 선택 시 나타나는 일괄편집 툴바를 새로 만듦).
- **결과**: 실제로 여러 항목을 골라서 태그를 한 번에 바꿔보고, 골랐던 개수만큼 정확히
  바뀌는 것까지 확인함.

### 마우스로 여러 개 선택하는 범위가 화면 일부에서만 되던 문제
- **무슨 문제였나**: 마우스로 드래그해서 여러 카드를 한 번에 선택하는 기능이, 특정 네모난
  영역을 벗어나면 선택이 끊기는 것처럼 느껴져서 불편하다는 지적이 있었음.
- **확인해보니**: 선택 영역을 표시하는 사각형이 특정 영역 안에서만 그려지도록 만들어져
  있어서, 그 영역을 벗어나면 화면에 안 그려질 뿐 실제 선택 자체는 되고 있었음 — 그래도
  눈에 안 보이면 사용자 입장에선 "안 되는 것"과 다름없음.
- **어떻게 처리했나**: 선택 영역 사각형이 화면 전체 어디로 끌어도 잘리지 않고 계속 보이게
  바꿈 (선택 박스를 표시하는 화면 요소를 특정 영역의 자식이 아니라 페이지 전체(`body`)에
  바로 붙이는 방식으로 교체).
- **결과**: 화면 끝까지 끌어봐도 선택 영역이 잘리지 않고 끝까지 따라오는 것을 확인함.

### "AI 전송 미리보기" 버튼 정리
- **무슨 지적이 있었나**: 예전에 추가했던 "AI 전송 미리보기" 버튼이 원래 있던 검출 결과
  화면과 똑같아 보여서 왜 따로 있는지 모르겠다는 지적이 있었음.
- **어떻게 처리했나**: 별도 버튼을 없애고 (`previewAiCrops()` 함수와 관련 버튼 삭제),
  원래 있던 검출 결과 화면 안에 같이 표시되도록 합침 — 사진이 잘리는 범위(빨간 테두리)와
  AI에게 실제로 전달되는 글자 포함 범위(초록 점선)를 한 화면에서 동시에 볼 수 있게
  정리함 (검출 결과를 그려주던 함수에 초록 점선 박스 그리는 부분을 추가).
- **결과**: 화면에서 두 범위가 겹쳐서 잘 보이는 것을 확인함.

### 이전 작업 자동 저장 기능 추가 (탭을 실수로 닫아도 복구 가능)
- **무슨 요청이었나**: 다른 도구(insta-gen)에 있는 "최근 작업 5개 자동 저장" 기능을 이
  도구에도 넣어달라는 요청. 참고용 코드도 같이 전달받음.
- **어떻게 처리했나**: 탭을 닫거나 다른 탭으로 넘어갈 때, 그 시점의 표 데이터(상품명·가격·
  태그·순서 등)와 사진을 최근 5개까지 자동으로 저장해두고 (탭이 닫히거나 화면에서 안
  보이게 되는 시점을 감지해서 저장 함수를 호출, 저장은 브라우저 안에 있는 `localStorage`
  라는 저장 공간 사용), 시작 화면에서 눌러서 그 상태로 바로 돌아갈 수 있게 함. 다만 저장
  공간을 아끼기 위해 사진은 화질을 낮춰서 저장하기 때문에, 이 저장 기능으로 되돌린 경우
  최종 결과물의 사진 화질이 원본보다 살짝 떨어질 수 있다는 점을 화면에도 안내 문구로
  남겨둠 — 정상적으로 작업 중이면 이 기능을 거치지 않고 그대로 이어서 하면 되고, 어디까지나
  "실수로 탭을 닫았을 때"를 위한 안전장치임. 저장 공간이 부족해지면 오래된 기록부터 사진을
  지우고 글자 정보만 남겨서 계속 동작하게 해둠 (저장 시도가 실패하면 오래된 순으로 사진
  데이터를 비우고 재시도하는 폴백 로직 추가).
- **결과**: 저장 → 새로고침 → 복원까지 실제로 반복해봤고, 저장된 상품 정보/사진/태그가
  다 정확히 돌아오는 것과 자동으로 표 정리 화면으로 이동하는 것까지 확인함.

### "다시 검출" 버튼이 작동을 안 하는 문제
- **무슨 문제였나**: 1단계에서 크롭을 이미 확정한 사진에 대해 "다시 검출" 버튼을 눌러도
  아무 효과가 없는 것처럼 보인다는 지적이 있었음. 같은 화면에서 최종 결과물에 헤더(매장
  배너)가 여전히 안 나온다는 신고도 같이 있었음.
- **확인해보니**: 진짜 원인을 찾았음 — 한 번 크롭을 확정하고 나면 "확인 및 크롭" 버튼이
  영구히 눌러지지 않게 잠겨 있었음 (`confirmSourceCrop()`이 이미 확정된 소스면
  아무 일도 안 하고 끝나버림, 버튼도 계속 비활성 상태). 그래서 "다시 검출"을 눌러서 칸
  위치를 새로 찾아내도, 그 결과를 실제로 적용할 방법 자체가 없었던 것 — 겉보기엔 버튼이
  고장 난 것처럼 보이지만 실제로는 "재검출 결과를 반영할 다음 버튼이 원천적으로 막혀
  있던" 구조적 문제였음.
- **어떻게 처리했나**: 이미 확정된 사진이어도 "다시 검출"을 누르면, "이 소스에서 만든
  항목이 전부 삭제되고 새로 만들어지며 2단계 이후에서 직접 고친 내용은 사라진다"는 경고
  창을 먼저 띄우고, 동의하면 확정 상태를 풀어서 "확인 및 크롭"을 다시 누를 수 있게 함.
  다시 확정을 누르면 이 소스가 예전에 만든 상품 항목·사진·헤더를 정확히 찾아서 지우고
  (항목의 고유 번호를 기준으로 지우기 때문에, 그 사이 표를 정리하거나 순서를 바꿔놨어도
  엉뚱한 항목이 지워지는 일은 없음) 새 결과로 다시 채움.
- **결과**: 실제로 확정 → 항목 하나 직접 수정 → 다시 검출(경고 문구 확인) → 재확정까지
  전체 흐름을 돌려봤고, 상품 개수·헤더 개수가 중복되지 않고 그대로 유지되면서 예전
  항목/사진은 깨끗이 지워지고 새 항목으로 교체되는 것까지 확인함. 다만 헤더가 여전히
  안 보이는 원인 자체(원본 스크린샷에 매장 배너가 없어서인지, 다른 이유인지)는 이 수정과
  별개라서, 다시 검출 후에도 헤더 미리보기가 비어 보인다면 원본 캡처 범위를 다시 확인해야 함.

### 스크린샷을 파일로 저장하지 않고 바로 붙여넣기(Ctrl+V) 요청
- **무슨 요청이었나**: 캡처한 스크린샷을 파일로 저장했다가 다시 파일 선택창에서 골라
  올리는 과정이 번거로우니, 클립보드에서 바로 Ctrl+V로 붙여넣을 수 있게 해달라는 요청.
- **어떻게 처리했나**: 1단계 화면에서 Ctrl+V를 누르면, 클립보드에 이미지가 있는지 확인해서
  있으면 파일 선택으로 올린 것과 완전히 동일하게 처리되도록 추가함 (기존 "파일 선택으로
  이미지를 받으면 처리하는 경로"를 그대로 재사용). 화면 안내 문구에도 이 사용법을 추가함.
- **결과**: 가짜 이미지를 만들어 붙여넣기 동작을 그대로 흉내내서 테스트해봤고, 파일
  선택 없이도 정상적으로 이미지가 추가되는 것을 확인함.

### "다시 검출"이 진짜 아예 먹통이라는 재신고 — 배포 파일까지 직접 대조해서 원인 확정
- **무슨 문제였나**: 앞서 "다시 검출" 버그를 고쳤다고 안내했는데도, 팝업도 안 뜨고
  아무 반응도 없다는 재신고가 있었음. 실제 서비스 주소(`inbound-image-composer.vercel.app`)가
  맞는지, 개발 중인 코드와 실제로 보이는 사이트가 다른 게 아니냐는 의심도 함께 제기됨.
- **확인해보니**: 실제 서비스 사이트에서 파일 3개(메인 화면, 상품 정리 로직, 그리드 인식
  로직)를 전부 직접 내려받아서 지금 갖고 있는 코드와 한 글자도 다른 부분이 없는지
  전부 대조해봤음 — 완전히 동일했음. 즉 배포가 안 된 게 아니라 코드는 이미 최신 상태로
  나가 있었음. 그다음 실제 화면의 개발자 도구 콘솔 로그를 확인해보니, 프로그램이
  멈추거나 깨졌다는 증거(빨간 에러)는 없고 무해한 경고 두 줄뿐이었음. 그래서 진짜 원인은
  ① 이미 확정된 소스에서 재검출하면 뜨는 경고창이 있는데, 아직 확정 전 상태에서
  "다시 검출"을 누르면 애초에 경고창이 뜰 이유가 없다는 점, ② 같은 이미지를 같은 방식
  으로 다시 스캔하면 검출 결과가 이전과 똑같이 나올 수 있는데, 그럴 때 화면에 "방금
  재검출이 실행됐다"는 표시가 전혀 없었다는 점 — 두 가지가 겹쳐서, 실제로는 정상 동작
  하고 있는데도 사람 눈엔 "버튼이 완전히 안 먹는다"로 보였던 것.
- **어떻게 처리했나**: 재검출 결과가 이전과 같든 다르든 상관없이, 버튼을 누르는 즉시
  해당 사진 영역 테두리가 잠깐 초록색으로 강조되고 버튼 글자도 "✓ 재검출 완료"로
  1.4초간 바뀌었다가 원래대로 돌아오게 함 — 눈에 보이는 확인 표시를 추가.
- **결과**: 실제로 버튼을 눌러서 테두리 강조와 문구 변경이 즉시 나타났다가 시간이
  지나면 원래대로 돌아오는 것까지 확인함.

  1000px 폭이었으니, 지금 이미지 폭이 그 몇 배면 카드 크기도 똑같이 그 배율만큼 커졌을
  것"이라는 추정치 하나로만 계산하고 있었음. 실제 매장 캡처는 화면 폭이 넓어진다고 해서
  카드 크기도 항상 똑같은 비율로 커지는 게 아니라(줌 배율, 좌우 여백 등이 캡처마다
  달라서) 이 추정이 어긋나는 경우가 많고, 그러면 칸 시작 위치는 정확한데 자르는 크기만
  틀려서 옆 칸 사진이 같이 잘려 들어오거나 카드 일부가 잘려나가는 정확히 "이상하게
  크롭된다"는 증상으로 나타남. 실제로 확인용 합성 이미지를 만들어 테스트해보니 이
  추정 방식은 카드 크기를 최대 27~180px까지 다르게 예측했음.
- **어떻게 처리했나**: 칸 시작 위치를 찾을 때 이미 픽셀을 스캔하고 있으니, 그 스캔에서
  실제로 사진이 있다고 판단한 구간의 진짜 길이도 같이 기록하도록 고침 (`detectRowTops`/
  `detectColStarts`가 각각 `{tops, heights}` / `{cols, widths}`로 실측 픽셀 런 길이를
  함께 반환하도록 변경). 그리고 카드 크기를 계산할 때 더 이상 추정 배율을 쓰지 않고,
  가장 많은 칸이 정확히 잡힌 스캔에서 나온 실측 길이들의 중앙값을 그대로 카드 크기로
  사용하게 바꿈 (`detectGrid()`에서 `median()`으로 중앙값을 구해 `cardW`/`cardH`로 사용).
  추정 배율은 실측값이 하나도 안 잡히는 극단적인 경우에만 예비용으로 남겨둠 (기존
  `176 * scale` 추정치는 `fallbackCardW`/`fallbackCardH`로 이름을 바꿔 최후 대안으로만 남김).
- **결과**: 1000px(기존에도 맞던 케이스), 1404px·2160px(실제 카드 크기가 폭 비율과
  다르게 설정된 케이스) 세 가지 합성 이미지로 검증 — 모두 실측 카드 크기와 정확히
  일치하는 결과를 확인함. 실제 사용자 파일로 재현 테스트는 못 했지만(붙여넣은 스크린샷은
  코드에 넣어 돌려볼 수 있는 원본 파일로 전달되지 않아서), 신고된 증상(칸 수는 맞는데
  크롭 경계만 어긋남)과 정확히 일치하는 원인을 코드에서 실제로 찾아 고쳤음.

### "텍스트는 유지하고 사진 순서만 바꾸고 싶다" — 잠금 모드 추가
- **무슨 요청이었나**: 이미 만들어둔 결과물(입고안내_6.jpg)처럼 IP명·가격 텍스트는
  그대로 두고 사진 순서만 바꾸고 싶은데, 페이지를 옮기다 보면 텍스트가 지워지는 것
  같다는 요청. 2단계쯤에 "텍스트 수정" ↔ "순서만 변경"을 켜고 끌 수 있는 체크박스를
  만들어서, 3단계에서는 순서만 바꿀 수 있게 해달라는 구체적인 기능 요청.
- **확인해보니**: 카드를 드래그해서 순서를 바꾸는 코드(`moveItemsBeforeTarget`)를
  직접 다시 읽고, 합성 데이터로 재정렬 전/후 값을 대조하는 테스트도 돌려봤음 —
  이 코드는 배열 안에서 항목의 위치만 바꿀 뿐 IP명·가격·태그 같은 텍스트 필드는
  전혀 건드리지 않음. "자동 정렬" 버튼이나 삭제·되돌리기 로직도 마찬가지로 텍스트를
  건드리지 않음. 즉 순서를 바꾸는 동작 자체가 텍스트를 지우는 버그는 없었음 — 다만
  이미 만들어둔 결과물을 새 원본으로 다시 올리면, 그 사진에서 새로 잘라낸 항목은
  이 도구가 사진 속 글자를 직접 읽어내지 못하니 처음부터 빈 칸으로 시작하는 게
  원래 동작이라, 그걸 "텍스트가 지워졌다"로 느끼셨을 수 있음.
- **어떻게 처리했나**: 요청하신 대로 2단계에 "🔒 텍스트 잠금 (순서만 변경)" 체크박스를
  추가함. 켜면 2단계 표의 모든 입력칸(IP명/가격/태그/등급)이 비활성화되고, 3단계에서도
  항목을 클릭해 수정하는 버튼과 삭제 체크박스가 비활성화됨 — 다만 카드를 드래그해서
  순서를 바꾸는 기능은 잠금 여부와 관계없이 항상 그대로 동작하게 해서, 잠금 켠 상태로
  3단계에 가면 정말로 "순서만" 바꿀 수 있음. 3단계 화면에도 지금 잠금 중이라는 안내
  배너를 띄움.
- **결과**: 잠금 켰을 때 2단계 입력칸 전부 비활성화, 3단계 수정 버튼·삭제 체크박스
  비활성화, 카드는 계속 드래그 가능, 실제로 드래그(재정렬 함수 호출)해도 텍스트 값이
  그대로 유지되는 것, 잠금을 끄면 다시 수정 가능해지는 것까지 자동화 테스트로 확인함.

### "AI로 정렬만 돕게 해줘, 근데 1단계 AI버튼이랑 헷갈리면 안 돼" — 저비용 정렬 보조 기능 추가
- **무슨 요청이었나**: 자동 정렬을 눌러도 결과가 안 바뀐 이유(등급표/클러스터에 없는
  IP는 전부 '기타'라 이름순으로만 정렬되고, 마침 이미 그 순서였음)를 설명한 다음,
  "그럼 텍스트는 잠가둔 채로 AI 도움만 받아서 정렬을 더 잘 시키고 싶은데, 이걸 1단계
  AI버튼처럼 사진을 다시 보내는 방식으로 할지, 3단계에 새로 만들지, 어느 쪽이 토큰(비용)을
  덜 쓰는지" 생각해달라는 요청. 답을 들은 뒤, 처음 쓰는 사람도 두 AI 버튼을 안 헷갈리게
  잘 구현해달라고 함.
- **어떻게 판단했나**: 1단계 AI버튼(사진을 다시 읽어서 IP명·가격까지 새로 뽑아내는 방식)을
  그대로 3단계에 새로 만드는 것도, 1단계 걸 재사용하는 것도 둘 다 사진(이미지) 데이터를
  다시 보내야 해서 비용이 큼 — 게다가 이미 확정한 텍스트를 다시 덮어쓸 위험도 있음. 근데
  IP명은 이미 텍스트로 다 알고 있으니, 사진 없이 "IP명 글자만" 보내서 성향·분위기만
  판단받으면 이미지 토큰이 아예 안 들어서 훨씬 저렴하고, 응답에 IP명/가격/태그 자체가
  없으니 텍스트를 실수로 바꿀 방법도 없음 — 이 방식을 추천하고 그대로 구현함.
- **어떻게 처리했나**: 텍스트만 보내는 새 API(`/api/classify-ip`)와 3단계 "🏷️ AI 분류로
  정렬 보조" 버튼을 추가함. 이미 등급표(S/A)에 있거나 이미 분위기 클러스터에 들어있는
  IP는 물어볼 필요가 없으니 대상에서 빼고, 중복 IP도 한 번만 물어봐서 호출량을 최소화함.
  응답을 받으면 성향(subGrade)과 분위기 클러스터만 갱신하고 자동으로 정렬까지 적용함.
  1단계 버튼과 헷갈리지 않도록: 1단계 안내문에 "3단계에는 사진 재인식 없이 정렬만 돕는
  더 저렴한 버튼이 따로 있다"는 문장을 추가하고, 3단계에는 버튼 바로 아래 회색 설명
  문구로 "1단계 버튼과 다르다"는 걸 바로 보이게 적고, 버튼에 마우스를 올리면 나오는
  설명(툴팁)도 붙임.
- **결과**: 합성 데이터 + 가짜 API 응답으로 자동화 테스트를 돌려서, 등급표에 이미 있는
  IP는 정확히 호출 대상에서 빠지고, 응답에 따라 성향만 반영되고, IP명·가격·태그는
  정렬 전후로 완전히 그대로 유지되는 것까지 확인함.

### "잠금 상태에서 3단계 갔더니 AI 분류할 IP가 없다고 뜬다" — 안내 문구가 원인을 잘못 짚던 문제
- **무슨 문제였나**: 텍스트 잠금을 켠 상태로 3단계에서 "AI 분류로 정렬 보조"를 눌렀더니
  "새로 분류할 IP가 없다"는 팝업만 뜨고 아무것도 안 바뀐다는 신고. 사용자가 스스로
  "잠금 상태에서 IP명이 비어있어서 그런 것 같다"고 정확히 원인을 짚어줌.
- **확인해보니**: 정확히 그 말대로였음. 크롭을 확정하면 그 항목들의 IP명은 원래
  빈 칸으로 시작하는데(1단계에서 사진 속 글자를 자동으로 읽어내는 게 아니라서), 아직
  아무것도 안 채운 상태에서 텍스트 잠금부터 켜버리면 2단계에서 IP명을 입력할 방법이
  없어져서 계속 빈 칸으로 남음. 근데 AI 분류 버튼을 누르면 "새로 분류할 IP가 없습니다
  (전부 이미 등급표/클러스터에 등록돼 있어요)"라는, 실제 원인과 전혀 다른 문구가
  떠서 혼란스러웠던 것 — 진짜 이유는 "등록이 이미 다 돼서"가 아니라 "IP명 자체가
  비어서"였음.
- **어떻게 처리했나**: 후보가 0개일 때 이유를 두 가지로 구분해서 안내하도록 고침 —
  IP명이 비어있는 항목이 있으면 그 개수를 알려주고, 지금 텍스트 잠금 중이면 "2단계에서
  잠금을 먼저 해제하고 IP명을 채운 뒤 다시 시도하라"고 구체적으로 안내함. 전부 채워져
  있는데 정말 이미 등록된 경우에만 기존 문구를 그대로 씀.
- **결과**: 크롭 확정 직후 곧바로 잠금부터 켠 뒤 3단계에서 버튼을 누르는 순서로 실제
  재현해봤고, 새 안내 문구("IP명이 비어있는 항목이 5개라서... 잠금을 먼저 해제하고
  IP명을 채운 뒤 다시 시도하세요")가 정확히 뜨는 것까지 확인함.

### "이미 만든 이미지 순서만 바꾸고 싶은데 상품 사진 인식은 필요 없잖아" — 라벨 전용 재인식 추가
- **무슨 문제였나**: 바로 앞서 고친 "IP명이 비어서 AI 분류를 못 쓴다" 문제의 근본
  원인을 짚은 뒤, 사용자가 정확한 지적을 함: "결국 IP명을 읽으려면 토큰이 드는 거
  아니냐, 그럼 이미 만들어진 이미지에서 순서만 바꾸고 싶은 경우엔 상품 사진(캐릭터가
  뭔지 알아맞히는 것) 인식은 필요 없고 'IP명 라벨' 부분만 인식하면 되는 거 아니냐"는
  구체적인 아이디어를 제시함.
- **어떻게 처리했나**: 정확히 그 아이디어대로 새 기능을 만듦. 이 도구가 이미 만든
  결과물(사진 아래 IP명·가격 글자가 이미 렌더링돼 있는 카드)을 다시 소스로 올렸을
  때 전용으로, 사진 자체는 아예 잘라서 빼버리고(`cropLabelStripRegion`) 그 아래
  텍스트 라벨 줄만 잘라서 신규 API(`/api/ocr-label`)로 보냄. 이미 깨끗하게 렌더링된
  글자라 원본 스크린샷처럼 "글자가 흐리면 사진 보고 캐릭터 추측" 같은 복잡한 규칙이
  필요 없어서, 프롬프트도 "보이는 글자 그대로 옮겨 적기"로 훨씬 짧고 저렴함. 1단계에
  "🏷️ 라벨만 재인식" 버튼으로 추가함.
  이제 총 AI 버튼이 3개(1단계 AI로 채우기 / 1단계 라벨만 재인식 / 3단계 AI 분류로
  정렬 보조)가 됐는데, 처음 쓰는 사람이 헷갈리지 않도록 1단계 상단에 세 버튼의
  "언제 쓰는지·비용이 어느 정도인지"를 한눈에 비교하는 표를 추가함.
- **결과**: 합성 이미지로 두 크롭 방식의 실제 전송 이미지 크기를 직접 재봤음 —
  같은 한 줄(행) 기준으로 사진까지 포함한 기존 방식은 높이 560px, 라벨만 자른 새
  방식은 208px로 약 63% 줄어드는 것을 확인함. 버튼을 실제로 눌러서(가짜 API 응답
  사용) IP명·가격·태그가 정확히 채워지고, "AI 추정" 배지 없이 곧바로 확정 상태로
  들어가는 것까지 확인함.

### "드래그가 안 된다, 4단계엔 다 없어졌다" — 드래그 방식을 통째로 교체
- **무슨 문제였나**: 라벨 재인식으로 텍스트를 다 채운 뒤 3단계에서 순서를 바꾸려는데
  드래그가 아예 안 먹힌다는 신고. 4단계(최종 내보내기) 화면 캡처도 같이 보내면서
  "여기 다 없어졌다"고 함.
- **확인해보니**: 먼저 코드 리뷰만으로 판단하지 않고, 실제 마우스로 누르고-이동하고-
  떼는 동작을 그대로 흉내내서 재현해봤음. 지금까지 쓰던 방식(브라우저 기본 제공
  `draggable` 속성 + dragstart/dragover/drop 이벤트)은, 자동화 도구의 마우스 시뮬레이션
  으로도 재현에 실패할 만큼 입력 방식에 따라 시작 자체가 안 잡히는 경우가 있다는 걸
  확인함 — 반대로 마우스를 누르고(mousedown) 움직이고(mousemove) 떼는(mouseup) 저수준
  이벤트로 직접 만든 방식은 안정적으로 재현됨. 이 김에 코드를 다시 훑다가 완전히
  별개의 버그도 하나 더 발견함 — 3단계의 "빈 배경 드래그로 여러 카드 한번에 선택"
  기능이 내부 함수 호출에서 필수 인자 하나가 통째로 빠져 있어서 처음 만들어질 때부터
  단 한 번도 실제로는 작동한 적이 없었음. 4단계의 "다 없어졌다"는 건, 원래부터 4단계는
  순서 변경이 아니라 최종 이미지 생성/다운로드 전용 화면이라 3단계식 카드 미리보기/드래그
  자체가 없는 게 맞는 설계였음 — 다만 그 사실이 화면에 안내돼 있지 않아서 "사라졌다"로
  오해하기 쉬웠음.
- **어떻게 처리했나**: 카드 드래그를 브라우저 기본 드래그 API에서 마우스 이벤트 기반의
  직접 구현으로 완전히 바꿈. 항목이 아주 많을 때(예: 155개) 화면이 매우 길어지는데,

  같이 고침. 4단계 화면 위쪽에 "여기는 순서 바꾸는 화면이 아니라 최종본을 만드는
  화면"이라는 안내 문구를 추가함.
- **결과**: 실제 마우스 누르고-이동하고-떼는 동작으로 단일 카드 드래그, 여러 페이지

### "다시 검출 눌러도 효과가 없다, 이 버튼이 대체 무슨 의미냐" + "헤더가 계속 사라진다"
- **무슨 문제였나**: 실제 매장 스크린샷(1463×7904px, 95개 셀)을 올렸는데 그리드가
  이상하고, "다시 검출"을 눌러도 전혀 효과를 못 본다는 신고. 없애지 말고 실제로 값어치를
  하게 고쳐달라는 요청. 4단계 헤더가 계속 없어진다는 지적도 같이 있었음.
- **확인해보니**: 이번엔 스크린샷을 붙잡고 추측하는 대신 코드부터 다시 봤음 — 그리고

  이 버튼은 "정상적으로 작동은 하지만, 애초에 아무것도 다르게 시도해볼 방법이 없어서
  다시 눌러봐야 의미가 없는" 상태였던 것. 합성 이미지(배경을 살짝 회색(232,232,232)으로

### "완전히 동일한 데이터는 갱신되지 않게 해줘" + "AI로 채운 것도 캐시에 남아?"
- **무슨 요청이었나**: 이전 작업 슬롯 목록에 내용이 똑같은 항목이 여러 개 쌓여 보이는 걸
  막아달라는 요청("완전히 동일한 데이터는 갱신되지 않게"), 그리고 AI로 채우기든 라벨만
  재인식이든 AI로 채운 데이터도 이 캐시에 같이 남는 게 맞는지 확인 요청.
- **확인해보니**: 탭을 닫거나 다른 탭으로 넘어갈 때마다 자동 저장이 실행되는데, 그 사이
  실제로 아무 작업도 안 했어도 매번 새 스냅샷을 만들어 목록 맨 앞에 추가하고 있었음 —
  내용은 완전히 같고 저장 시각만 다른 항목이 계속 쌓이는 구조적 문제였음. AI로 채운
  데이터 쪽은 코드로 직접 확인함 — "AI로 채우기"든 "라벨만 재인식"이든 결과는 전부
  `item.ip`/`price`/`tag`/`subGrade` 같은 일반 표 데이터에 그대로 쓰이고, 슬롯 저장
  함수(`snapshotState`)는 그 표 데이터 전체를 통째로 복사해서 저장하므로 AI로 채운
  값도 예외 없이 캐시에 포함됨.
- **어떻게 처리했나**: 새 스냅샷을 저장하기 직전에 저장 시각만 빼고 나머지 내용을 가장
  최근 슬롯과 비교해서, 완전히 똑같으면 새로 추가하지 않고 건너뛰도록 고침.
- **결과**: 똑같은 상태로 저장을 3번 연달아 시도해도 슬롯이 1개만 남는 것, 실제로 값을
  하나 바꾼 뒤 저장하면 정상적으로 슬롯이 하나 늘어나는 것, AI로 채운 IP명·가격·성향
  값이 저장된 슬롯 안에 그대로 들어있는 것까지 실제로 돌려서 확인함.

### "라벨인식 했는데 뭐야 이거, 우리식으로 바꿔야 할 거 아냐" — 지저분한 원문 그대로 나오던 문제
- **무슨 문제였나**: 원본 매장 스크린샷에 "라벨만 재인식"을 썼더니, IP명 자리에
  "[예약] GMG 콜렉션 17 지구연방군 세이라 마스 제복 버전ㅣ기동전사 건담"처럼 상품명
  전체가 그대로 들어가버렸다는 신고. 우리 방식(깨끗한 IP명)으로 나오게 고쳐달라는 요청.
- **확인해보니**: 이 버튼을 처음 만들 때 "이 도구가 이미 만든 결과물(사진 아래 이미
  깨끗한 IP명만 렌더링된 카드)을 재수입할 때 전용"이라고 전제하고, 그래서 "해석하지
  말고 보이는 글자 그대로 옮겨 적기"만 하도록 만들었었음. 근데 실제로는 지저분한
  원본 상품명이 그대로 있는 진짜 매장 스크린샷에도 이 버튼을 쓰고 있었음 — 그러면
  "그대로 옮겨 적기"가 곧 "상품명 전체를 그대로 베껴오기"가 돼서 전혀 쓸모가 없는
  게 당연했음.
- **어떻게 처리했나**: 1단계 "AI로 채우기"가 쓰는 것과 똑같은 IP명 추출 규칙(사전
  매칭, "|" 구분자 뒤 작품명 판단, 상품 라인명 걸러내기, VTuber 규칙, 태그/분위기
  클러스터/성향 판단)을 라벨 인식에도 그대로 적용하도록 바꿈. 사진이 없어서 "글자가
  흐리면 캐릭터 그림을 보고 유추해라"는 지시만 뺐고, 그 경우엔 확인 필요(⚠) 표시로
  남게 함. 결과적으로 사진만 안 보낼 뿐 인식 품질은 "AI로 채우기"와 동등해지고,
  원본 스크린샷/재수입 어느 쪽에 써도 깨끗한 IP명이 나오게 됨.
- **결과**: 가짜 API 응답(지저분한 원문 + 깨끗하게 추출된 IP명, 클러스터 매칭 1건,
  확신 없는 항목 1건 포함)으로 실제로 돌려서, 지저분한 원문이 그대로 안 남고 추출된
  IP명이 반영되는 것, 클러스터 자동 편입되는 것, 등급표에 이미 있는 IP(예: 에반게리온)
  는 성향 추측을 건너뛰고 사전 값을 우선하는 것까지 전부 확인함.

### "같은 IP 색상 표시가 안 됐고, 그룹 이동 중 개별/제외 이동은 어떻게 할 거냐" — 플랜 먼저 논의 후 구현
- **무슨 요청이었나**: 예전에 요청했던 "같은 IP끼리 카드 색 맞추기"가 실제로는 반영이
  안 된 것 같고, 같은 IP는 기본적으로 묶여서 이동하는 상황에서 그 그룹 중 하나만 개별로
  옮기고 싶거나 특정 상품만 그룹 밖으로 빼고 싶을 때 어떻게 할 건지 플랜부터 얘기해달라는
  요청(바로 고치지 말고 방식부터 상의).
- **확인해보니**: 색상 기능(`colorForIp()`)은 사실 예전에 만들긴 했는데 2단계 표
  화면에만 적용돼 있었고, 정작 순서를 드래그하는 3단계 미리보기 화면엔 안 붙어 있어서
  "안 됐다"고 느낀 것이었음. 그리고 "같은 IP는 기본으로 묶여서 이동한다"는 것도 사실
  그런 규칙이 코드에 있던 게 아니라, 자동 정렬이 같은 IP를 이미 나란히 배치해두다 보니
  마퀴로 화면 한 덩어리를 선택하면 우연히 같은 IP만 걸려서 그렇게 보인 것 — 진짜 "IP
  단위로 묶는다"는 로직 자체는 없었음.
- **어떻게 처리했나**: 플랜을 먼저 제시하고(3단계에도 색상 적용, 같은 IP 기본 그룹
  드래그를 새로 만들기, 개별 이동은 Alt+드래그와 카드 위 버튼 두 가지 다 지원), 그룹에서
  "영구히" 빼는 기능은 필요 없다는 답을 받아 그 부분은 만들지 않기로 확정한 뒤 구현함.
  ① 3단계 카드에도 2단계와 같은 방식으로 같은 IP 테두리 색 적용. ② 카드를 드래그하면
  마퀴로 직접 여러 장을 선택해둔 상태가 아닌 이상, 같은 IP를 가진 카드 전체가 자동으로
  같이 이동하도록 드래그 대상 계산 방식을 바꿈. ③ 그중 하나만 예외적으로 혼자 이동하고
  싶을 때를 위해 Alt(옵션)를 누른 채 드래그하는 방법과, 카드 위 "1개만" 버튼을 눌러
  "다음 드래그 한 번만 이 카드 혼자 이동"하게 만드는 방법 둘 다 추가함 — 이 무장 상태는
  기억해두는 값이 아니라 한 번 쓰이면(또는 버튼을 다시 눌러 취소하면) 바로 사라지는
  일회성 값으로만 관리함. IP가 하나뿐이거나 없는 카드엔 애초에 "묶일 그룹"이 없으니
  "1개만" 버튼 자체를 표시하지 않음.
- **결과**: 합성 데이터(IP: A×3, B×2, C×1)로 실제 마우스 드래그를 재현해서 — 같은 IP
  카드끼리 테두리 색이 정확히 일치하고 다른 IP와는 다른 것, 평범하게 드래그하면 A 3장이
  전부 함께 이동하는 것, Alt를 누른 채 드래그하면 A 1장만 이동하고 나머지 2장은 그대로
  있는 것, "1개만" 버튼을 눌러 무장한 뒤 평범하게 드래그해도 그 카드 1장만 이동하는 것,
  그리고 그 무장 상태가 한 번 쓰이자마자 자동으로 풀리는 것까지 전부 확인함.

### "배송비 껐다 켰다 하고 싶은데, 꺼도 가격 부분이 밀리지 않게" — 시작 전 방식부터 상의
- **무슨 요청이었나**: 배송비를 on/off로 켜고 끄고 싶은데, 껐을 때 배송비 글자가 사라지면서
  그 아래/위 요소(가격 등)가 그만큼 당겨지거나 밀리지 않고, 그냥 하얀색으로 가려지기만
  했으면 좋겠다는 요청. 구현 전에 먼저 방식을 상의해달라고 함.
- **확인해보니**: 배송비가 실제로 그려지는 곳이 두 군데였음 — ① 3단계 미리보기 카드
  (`.ship` div, 화면용), ② 진짜 최종 내보내기 이미지(`drawCard()`, 캔버스에 텍스트+
  장바구니 아이콘을 직접 그리는 부분). ①은 `display:none`으로 숨기면 그 칸 높이만큼
  카드가 짧아질 위험이 있었고, ②는 카드 한 칸의 높이와 다음 줄 카드가 시작되는 위치가
  배송비 유무와 상관없이 항상 고정된 값(`LAYOUT.cardBlock`)으로 계산되고 있어서, 사실
  배송비 그리는 부분만 안 그리면 다른 요소는 원래부터 전혀 안 밀리는 구조였음.
- **어떻게 처리했나**: 적용 범위(미리보기+최종 이미지 둘 다)와 단위(항목별이 아니라
  전체 항목 공통 스위치 하나)를 먼저 확인받은 뒤 구현함. 항목 데이터(`item.ship`) 자체는
  전혀 안 건드리고, 화면에 보여줄지 말지만 결정하는 전역 스위치(`state.showShipping`)를
  새로 추가함. 3단계 미리보기는 `display:none` 대신 `visibility:hidden`을 써서 그 칸의
  높이(공간)는 그대로 차지하되 안 보이게만 만듦. 최종 캔버스는 `drawCard()`에 배송비를
  그릴지 말지 결정하는 인자를 추가해서, 꺼져 있으면 아이콘+글자 그리는 코드 자체를
  건너뛰도록 함(이미 위에서 확인했듯 이래도 다른 요소 위치는 안 밀림).
- **결과**: 합성 데이터로 체크박스를 껐다 켰다 하면서 3단계 카드의 실제 화면 높이가
  단 1px도 안 바뀌는 것, 데이터(`item.ship`)는 꺼놔도 그대로 남아있다가 다시 켜면
  바로 보이는 것, 최종 내보내기 캔버스도 켰을 때/껐을 때 전체 크기가 완전히 같고
  배송비 영역에서만 잉크(색이 칠해진 픽셀)가 사라지며 IP명이 그려지는 영역은 픽셀
  단위로 전혀 안 변하는 것까지 전부 확인함.

### 사전관리 화면에서 등급표가 스토어 구분 없이 통합돼 있는 걸 발견 + 라인업 태그 개편 요청
- **무슨 문제/요청이었나**: "1페이지 사전 관리 버튼 열어봤는데 인기도 분류 기준(등급표)이
  브랜드 상관없이 통합돼 있는데, 메가하우스/굿스마일처럼 스토어 체계별로 분류하는 게
  낫지 않냐"는 질문. 이어서 "메가는 여성향, 굿스는 남성향이라 서로 반대 성향인데(메가에서
  상단에 있는 게 굿즈에선 하단이어야 하는 식)"라는 구체적인 예시를 제시함. 이 논의는
  "성향은 좀 생각해보고"로 일단 보류되고, 대신 바로 처리할 건으로 "라인업 태그를 굿스마일·
  부시로드에선 없애고, 룩업 태그도 아예 없애고, 테노히라·메가캣·GEM(신설)만 남겨달라"는
  요청이 이어짐.
- **확인해보니**: 코드를 보니 등급표(S/A급, `state.dict.gradeTable`)는 정말 스토어 구분
  없이 완전히 하나만 있었음. 반면 성향 우선순위(`genderPriority`)와 라인업 태그 화이트
  리스트(`tagWhitelist`)는 이미 스토어별로(`SEED_STORE_PROFILES`) 따로 관리되고 있었음.
  정렬 로직(`autoSortItems()`)을 다시 보니, B급/C급은 스토어의 성향 우선순위에 따라
  이미 순서가 뒤집히도록(`gradeOrderFor()`) 돼 있는데, S/A급만은 `effectiveGrade()`가
  스토어와 무관하게 무조건 맨 위로 고정시키고 있었음 — 사용자가 예로 든 "메가에서 상단인
  게 굿즈에선 하단이어야 하는" 증상이 정확히 여기서 날 수 있는 구조였음(이 부분은 결론을
  못 내려서 구현은 보류, 다음에 이어서 정하기로 함).
- **어떻게 처리했나**: 태그 화이트리스트는 이미 스토어별로 관리되는 구조라 시드 데이터만
  바꾸면 됐음. 굿스마일·부시로드는 `tagWhitelist`를 빈 배열로 비웠고, 메가하우스는
  "룩업"을 빼고 "GEM"을 추가해 테노히라·메가캣·GEM으로 바꿈. AI 인식 프롬프트
  (`api/parse-image.js`, `api/ocr-label.js`)에 있던 화이트리스트 기본값(프론트가 값을
  못 보냈을 때만 쓰이는 예비값)도 같이 맞춰서 고침.
- **결과**: 새 브라우저(로컬 저장값 없음) 기준으로 스토어별 태그 화이트리스트가 정확히
  적용되는 것, 사전 관리 화면의 스토어 프로필 편집 칸에도 그대로 반영되는 것까지 확인함.
  다만 실제 사용 중인 브라우저에 예전에 스토어 프로필을 저장한 이력이 있으면 그 저장값이
  이번 시드 변경보다 우선하므로, 그 경우엔 "사전 관리 → 스토어 프로필"에서 직접 한 번 더
  고쳐 저장해야 실제로 반영됨 — 이 부분은 확인 못 했고(테스트는 로컬 저장값 없는 상태
  기준), 사용자에게도 안내가 필요함.

### "사진 실수로 첨부한 경우 1페이지에서 없앨 수 있게 삭제도 만들어줘"
- **무슨 요청이었나**: 1단계에서 스크린샷을 잘못 올렸을 때, 그 사진을 목록에서 지울 방법이
  없어서 삭제 기능을 만들어달라는 요청.
- **확인해보니**: 실제로 1단계 화면엔 "다시 검출"/"확인 및 크롭"/AI 버튼들만 있고, 소스
  자체를 목록에서 빼는 기능이 없었음. 다만 이미 크롭을 확정한 소스를 다시 검출할 때
  그 소스가 만든 항목/사진/헤더를 정확히 지우는 로직(`confirmSourceCrop()`의 재크롭
  정리 부분, `src.itemIds`/`src.headerId`를 id 기준으로 추적)이 이미 있어서, 이걸 그대로
  가져다 쓰면 될 것 같았음.
- **어떻게 처리했나**: 각 소스 블록에 "🗑 이 사진 삭제" 버튼을 추가하고, 신규
  `removeSource(srcId)` 함수를 만듦. 아직 크롭을 확정하기 전이면(아직 아무것도 파생된
  게 없으니) 확인창 없이 바로 지우고, 이미 크롭을 확정해서 항목·사진·헤더가 만들어진
  소스면 "삭제하면 이 사진에서 만든 항목·사진·헤더가 모두 함께 삭제된다"는 확인창을
  먼저 띄운 뒤 동의하면 지움. 지우는 방식은 재크롭 정리 로직과 똑같이 id 기준이라, 그
  사이 2·3단계에서 순서를 바꾸거나 다른 항목을 지웠어도 엉뚱한 항목이 삭제되지 않음.
- **결과**: 소스 2개를 올리고 — 아직 크롭 안 한 소스는 확인창 없이 바로 삭제되는 것,
  나머지 하나는 크롭 확정 후 삭제하면 확인창이 뜨고 동의 시 항목 5개·사진 5개·헤더까지
  전부 같이 지워지는 것, 사진이 하나도 안 남으면 "다음 단계" 버튼이 자동으로 다시
  비활성화되는 것까지 전부 재현 테스트로 확인함.

### 원본 규칙 문서(사용자가 따로 관리하던 md 파일)와 코드를 대조해서 빠진 부분 반영
- **무슨 요청이었나**: 사용자가 따로 관리해온 "입고용 이미지 제작 원칙" 문서를 첨부하며,
  이 문서 내용을 지금 코드와 비교해서 반영할 부분을 정리해달라고 함. 정리해서 보여준
  항목들에 대해 하나씩 답을 받음 — ① 태그 화이트리스트는 방금 바꾼 대로(룩업 삭제·GEM
  신설)가 맞음, ② 캐릭터명 역추론 사전을 추가하되 "카에데"처럼 흔한 이름은 반드시
  풀네임("타카가키 카에데")으로 등록할 것, ③ 뱅드림 서브밴드명은 부시로드에서만 그대로
  쓰고 다른 스토어는 "뱅드림"으로 뭉뚱그릴 것, ④ IP명이 너무 길면 2줄로 나누는 것도
  맞음, ⑤ 푸터 크롭 기능은 필요 없음, ⑥ 빠진 사전 항목 5개는 추가해도 됨(DB가 크게
  무거워지지 않는 선에서).
- **확인해보니**: 코드를 문서와 한 줄씩 대조해본 결과, 표기 규칙·IP 등급표·분위기
  클러스터·정렬 순서 등 대부분은 이미 코드와 정확히 일치했음. 다만 캐릭터명→작품명
  역추론용 구체적 사전이 코드엔 전혀 없이 AI에게 "알아서 추론해라"는 일반 지시만 있던
  점, 스토어 프로필에 `bandNameAsIs`(밴드명 그대로 쓸지 여부) 플래그가 정의만 돼 있고
  실제로 이 값을 읽어서 뭔가 다르게 처리하는 코드가 어디에도 없어서 사실상 죽은 설정으로
  방치돼 있던 점, IP명이 길면 폰트만 최소 15px까지 줄여서 억지로 한 줄에 우겨넣고 실제
  줄바꿈/행높이 조정은 없던 점 — 이 세 가지가 진짜 빠진 부분으로 확인됨.
- **어떻게 처리했나**: ① IP명 사전(`SEED_IP_NAME_MAP`)에 캐릭터 역추론 항목 8건(타카가키
  카에데→신데렐라걸즈 등)과 누락된 표기 확정 항목 5건(토미에→이토 준지 등)을 추가함.
  이때 "양귀비→페이트/그랜드오더"처럼 문서에 적힌 표기를 그대로 쓰지 않고, 등급표 S급에
  이미 등록된 정확한 표기("페이트/페그오")와 일치시켜야 자동 등급 분류가 계속 걸린다는
  점을 확인하고 그쪽 표기로 맞춤. ② `bandNameAsIs` 플래그를 실제로 읽어서 동작하는
  `resolveBandName()` 함수를 새로 만들어, AI 인식 결과의 밴드명을 부시로드면 그대로,
  다른 스토어면 "뱅드림"으로 바꾸도록 함(수동 입력은 사용자가 직접 원하는 대로 적는
  거라 건드리지 않음). AI 프롬프트에도 "서브밴드명을 미리 축약하지 말고 정확히 그대로
  적으라"는 규칙을 추가해서, AI가 스스로 축약을 판단하려다 코드의 판단과 충돌하지
  않게 함. ③ IP명이 길어서 한 줄로는 최소 크기까지 줄여야 하는 경우, 억지로 줄이지
  않고 20px 고정 크기로 2줄로 나눠 표시하도록 바꿈. 행마다 카드들의 실제 필요 높이를
  먼저 계산해서, 2줄 카드가 있는 행은 그만큼 행 높이가 늘어나고 다음 행이 안 겹치게 함.
  ④ 푸터 크롭은 요청대로 만들지 않음.
- **결과**: 밴드명이 부시로드에서는 원어 그대로("Ave Mujica"), 다른 스토어에서는 전부
  "뱅드림"으로 나오는 것, 일반 IP는 이 로직에 안 걸리고 그대로 통과하는 것, 새로 추가한
  사전 항목(타카가키 카에데→신데렐라걸즈, 양귀비→페이트/페그오가 등급표 S급과 정확히
  일치하는 것, 토미에→이토 준지)까지 전부 확인함. 짧은 IP명은 그대로 1줄, 아주 긴 IP명은
  2줄로 전환되는 것, 2줄 카드가 있는 행의 실제 높이가 기본값보다 커지는 것, 2줄+밴드명
  축약이 섞인 실제 최종 내보내기까지 에러 없이 정상 생성되는 것을 전부 재현 테스트로
  확인함.

### "사진 2장 넣고 각각 글자인식 돌렸는데 1장만 반영되고 돈은 둘 다 나간다"
- **무슨 문제였나**: 사진 2장을 올려서 각각 AI 인식(1단계 "AI로 채우기"/"라벨만
  재인식")을 돌렸는데, 둘 다 API 호출은 정상적으로 나가서 비용은 그대로 발생하는데
  결과는 1장분만 반영되고 나머지 1장은 반영이 안 된다는 신고.
- **확인해보니**: 합성 데이터로 재현해봄 — 소스 2개를 올려 둘 다 크롭 확정한 뒤, 그중
  하나를 "다시 검출" 후 재확정("재크롭")하고 나서 다른 소스에 AI 인식을 돌리면, 결과가
  그 소스 자신의 항목이 아니라 방금 재크롭한 다른 소스의 새 항목에 잘못 쓰이는 것을
  확인함(재크롭 안 한 소스 자신의 항목은 계속 빈 칸으로 남음). 원인은 각 소스가 자기
  항목을 찾을 때 "배열의 몇 번째부터 시작한다"는 고정 숫자(`itemStartIndex`)로 찾고

  `cache_control: {type: "ephemeral"}`을 붙여서, 같은 세션의 첫 호출만 정가로
  과금되고 이후 호출들은 캐시 읽기 단가(정가의 약 10%)로 처리되게 함.
  `classify-ip.js`(3단계 AI 분류 보조)는 호출당 1회뿐이라 캐싱 이득이 없어 그대로
  둠.
- **중간 사고 (기록용)**: 첫 시도에서 사용자에게 확인 없이 바로 두 파일을 고치기
  시작했다가 "물어보지도 않고 혼자 고쳤다"는 지적을 받음 — 즉시 중단하고 plan
  모드로 전환, 계획을 문서로 정리해 예상 리스크(비용 절감 폭이 과장 없이 얼마나
  되는지, 실제 API 테스트 불가능 등)까지 공유한 뒤 승인받고 재개함. 그 과정에서
  `ocr-label.js`가 편집 중간에 막혀서 `buildPrompt is not defined`로 깨지는
  상태로 남아있던 것도 재개 시점에 같이 정리함.
- **결과**: 두 파일 모두 `node --check`로 문법 확인, 요청 바디 JSON 구조(`system`
  배열 안 `cache_control`)가 Anthropic API 문서상 올바른 형태인지 확인함. 이
  환경에는 실제 API 키가 없고 있어도 실제로 호출하면 과금이 발생해서, 라이브

  - 그래서 21~25번째 카드는 "1p" 박스 안에 있으면서 실제로는 2페이지로 출력됨 — 항목 23개면 3장, 47개면 12장이 어긋남
  - 같은 화면 위쪽 툴바는 "총 23개 → 20+3 (2페이지)"로 이미 20 기준으로 맞게 쓰고 있어서, 한 화면이 서로 다른 말을 하는 상태였음
- **처리** ▶ 미리보기 묶음 단위를 20으로 맞추고, 라벨을 "1p" → "1페이지 · 20개"로 바꿔 그 장에 몇 개가 들어가는지까지 보이게 함
  - 박스가 홀수 개일 때 짝을 맞추려고 붙이는 빈 박스에도 라벨이 붙어 존재하지 않는 페이지처럼 보이던 것도 함께 제거함
  - 화면 배치 개선과 섞지 않고 이 수정만 먼저 반영함 — 혼란이 줄어든 게 어느 수정 덕인지 따로 확인하기 위함
- **결과** ▶ 실제 브라우저에서 더미 항목 5·20·23·40·47개를 넣고 확인한 결과 박스 묶음과 라벨이 실제 분할과 전부 일치함 (47개 → "1페이지 · 20개" / "2페이지 · 20개" / "3페이지 · 7개" + 라벨 없는 빈 박스 1개, 자바스크립트 오류 0건)

### 화면 구조 재편 — 4단계를 3단계로 합치고 설명문·툴바·카드 컨트롤 정리
- **문제** ▶ 화면이 전반적으로 난잡하고, 정렬 화면(3단계)과 결과 화면(4단계)이 갈라져 있어 순서를 한 칸 고칠 때마다 두 화면을 왕복해야 했음
- **확인** ▶ 4단계에 "여기는 순서를 바꾸는 화면이 아닙니다(없어진 게 아니라 원래 이 화면엔 없습니다)"라는 방어 문구가 필요했던 것 자체가 화면 경계가 잘못 그어졌다는 신호였음
  - 계측해보니 4단계는 조작 버튼이 4개뿐인 거의 빈 화면이라 독립 단계를 유지할 만한 내용량이 아니었음
  - 설명문은 단계마다 흩어진 채 상시 노출돼 총 2,382자였고, 1단계는 화면 높이의 절반이 설명인데 실제 조작 요소는 2개뿐이었음
  - 사진 카드마다 체크박스·"1개만"·수정 버튼이 항상 떠 있어서 항목 23장이면 69개가 사진을 덮고 있었음
- **처리** ▶ 네 가지를 한 번에 반영함 — 나눠서 하면 앞 작업 결과물을 뒤 작업에서 다시 배치하게 되고, 직원 입장에서도 화면이 여러 번 달라지기 때문
  - 단계 재편 ▷ 4단계(최종 내보내기)를 3단계 아래 고정 바로 합침 (`step-4` 섹션 삭제 + `position: sticky` 내보내기 바) — 세로 사이드 패널이 아니라 가로 바로 둔 건, 세로 패널이 가로 폭을 250px 잡아먹어 페이지 박스를 2장 나란히 못 보여주기 때문
  - 관문 제거 ▷ "순서 확정하고 다음 단계 →" 버튼은 한 번 통과하면 그 뒤 변경을 못 잡으므로, 페이지를 만든 시점의 입력값을 기억해뒀다가 지금과 다르면 결과 이미지를 흐리게 하고 "다시 생성하세요"를 띄우는 방식으로 교체함 (`pagesSignature()` / `refreshPagesStale()`)
  - 설명문 ▷ 흩어져 있던 설명을 단계별 "사용법" 패널 하나로 모으고 접을 수 있게 함 (`<details class="help">`) — 기본은 펼침이고 한 번 접으면 그 상태를 기억함 (`setupHelpPanels()`의 localStorage 저장)
  - 툴바·카드 ▷ 3단계 툴바를 정렬 / 보기 그룹으로 묶고, 되돌리기 번거로운 "선택 삭제"는 선택이 있을 때만 나타나는 바로 내림 (`.select-bar`). 카드 위 버튼은 마우스를 올렸을 때만 보이게 하되, 손가락으로 쓰는 좁은 화면은 예전처럼 계속 보이게 남겨둠 (`@media (hover: hover)` 분기)
- **결과** ▶ 작업 중 스토어 프로필 드롭다운이 2·3단계에서 서로 동기화되지 않아 표시값과 실제 적용값이 어긋날 수 있던 버그도 함께 발견해 고침 (변경이 `setActiveStore()` 한 곳만 통과하게 함)
  - 실제 브라우저에서 자동 정렬·삭제·실행취소·텍스트 잠금·페이지 생성·이전 작업 슬롯 복원까지 전부 확인함, 자바스크립트 오류 0건
  - 예전 형식으로 저장된 슬롯(더 이상 쓰지 않는 `orderConfirmed` 항목이 남아 있는 것)도 그대로 복원되는 것까지 확인함
  - 중요하게 보던 밀도(2단계 3열, 페이지 박스 가로 2열)는 그대로 유지됨을 계측으로 확인함

### 바뀐 화면을 접속만으로 알 수 있게 하는 안내 팝업 추가
- **문제** ▶ 화면이 크게 바뀌었는데 따로 공지를 받지 못한 사람은 모른 채로 쓰게 됨
- **처리** ▶ 첫 접속 시 뜨는 안내 모달을 추가해 바뀐 점 4가지(단계 병합 / 미리보기 20개 단위 / 카드 버튼 노출 방식 / 사용법 위치)를 담음 (`<dialog id="noticeDialog">` + `setupNotice()`)
  - 처음엔 한 번 닫으면 영영 안 뜨는 방식이었는데, 실수로 바로 닫으면 내용을 아예 못 읽게 되므로 "봤는지 여부"가 아니라 "언제까지 숨길지"를 저장하도록 바꿈 (localStorage에 숨김 만료 시각을 밀리초로 저장)
  - "오늘 하루 그만보기"(24시간) / "3일간 그만보기"(72시간) 두 버튼을 두고, 그냥 닫으면(ESC) 아무것도 저장하지 않아 다음 접속에 다시 뜨게 함 (`noticeHide1d`, `noticeHide3d`)
  - 안내가 유효한 기간이 지나면 알아서 사라지도록 노출 마감일을 코드에 못 박음 (`NOTICE_UNTIL`, 2026-08-23 한국시간)
- **결과** ▶ 실제 브라우저에서 첫 노출 / ESC 후 재노출 / 24시간·72시간 저장값 / 만료 후 재노출 / 예전 저장값이 있는 경우까지 전부 확인함, 자바스크립트 오류 0건
  - 예전 저장값은 1970년으로 계산돼 자동 만료 처리되므로 별도 변환 코드 없이도 새 안내가 안전하게 뜸
  - 배포 직후 라이브 주소에 반영이 안 보인다는 확인 요청이 있었는데, 앞선 변경은 이미 반영돼 있고 이 커밋만 배포 진행 중이던 상태였음 — 완료 후 정상 노출 확인함
