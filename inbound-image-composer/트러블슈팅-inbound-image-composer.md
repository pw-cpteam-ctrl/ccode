# 트러블슈팅 기록 — 입고안내 이미지 자동 제작 툴

> **이 문서를 쓰는 법**: 문제가 생기면 먼저 아래 **증상**에서 비슷한 걸 찾는다.
> 이 도구에서 실제로 터졌던 문제들이고, 상당수가 **여러 번 재신고된 뒤에야**
> 진짜 원인을 찾은 것들이라 같은 함정을 다시 밟을 가능성이 높다.
>
> 각 항목은 `증상 → 원인 → 해결 → 재발하면 볼 곳` 순이다. 괄호 안 영어는
> 코드에서 실제로 쓰는 이름이라, 고칠 때 그 단어로 검색하면 된다.

---

## 🚨 먼저 확인할 것 — "고쳤는데 그대로예요"

**증상 하나로 가장 많은 시간을 날린 유형이다.** 코드를 아무리 봐도 멀쩡한데
팀원은 계속 같은 증상을 신고한다면, 코드가 아니라 **반영 경로**를 먼저 의심한다.

순서대로 확인한다.

1. **푸시가 됐는가** — `git log origin/main` 에 그 커밋이 있는가
2. **자동 배포가 켜져 있는가** — `vercel.json`의 `git.deploymentEnabled.main`
   (이 폴더는 평소 `false`로 꺼둔다. 자세한 건 `배포설정-메모.md`)
3. **배포가 성공했는가** — 이게 핵심이다. 아래 명령으로 확인한다.

   ```
   gh api repos/pw-cpteam-ctrl/ccode/commits/<커밋>/status
   ```

   `inbound-image-composer` 항목의 `state`가 `success`인지 본다.
   **`failure`면 배포는 돌았는데 실패한 것이다** — 사이트 응답만 계속
   확인하면 "배포가 안 돈다"로 오해하게 된다.
4. **사이트에 실제로 들어갔는가**

   ```
   curl -s https://inbound-image-composer.vercel.app/app.js | grep -c <고친함수이름>
   ```

## 1. 배포 · 반영

### 1-1. 설정 파일에 주석을 달았다가 배포가 열흘간 실패 (10/29)

- **증상** — 고친 코드를 올리고 자동 배포까지 켰는데 하루가 지나도 사이트에
  반영되지 않음. 배포가 아예 안 도는 것처럼 보였다.
- **원인** — `vercel.json` 안에 설명용 키(`_comment_deploy`)를 넣어뒀는데,
  **Vercel은 자기가 모르는 속성이 하나라도 있으면 설정 파일을 통째로 거부한다.**
  JSON에는 주석 문법이 없다는 걸 놓친 것이 시작이었다.
  발각이 열흘이나 늦어진 이유는, 그 키를 넣은 날이 **자동 배포를 끈 날과 같아서**
  배포가 실패해도 아무도 눈치챌 수 없었기 때문이다.
- **해결** — 설정 파일에는 Vercel이 정의한 속성만 남기고, 설명은
  `배포설정-메모.md`로 옮김.
- **재발하면** — 위 "먼저 확인할 것" 3번. 실패 링크가 Vercel의 설정 문서를
  가리키면 거의 확실히 `vercel.json` 문제다.

### 1-2. 빌드 건너뛰기 설정이 모든 배포를 영구히 막음 (7/9, 7/10 두 번)

- **증상** — 코드를 올려도 배포가 계속 건너뛰어짐.
- **원인** — "이 폴더가 안 바뀌었으면 건너뛴다"는 설정(`ignoreCommand`)의
  경로를 폴더명으로 줬는데, 이 명령은 **이미 그 폴더 안에서 실행된다.**
  그래서 존재하지 않는 하위 폴더(`inbound-image-composer/inbound-image-composer`)를
  보게 되어 **항상 "변경 없음"** 으로 판정됐다.
- **헷갈린 경위** — 7/10에 "다른 프로젝트 커밋에도 재배포된다"는 이유로 다시
  폴더명으로 바꿨다가, 같은 버그를 또 만들어 당일 되돌렸다. **같은 실수를
  이틀 만에 두 번 했다.**
- **해결** — 현재는 `ignoreCommand`를 **아예 쓰지 않는다.** 건너뛰어도 배포 1회로
  집계돼 한도를 못 아끼는 데다(Vercel 문의로 확인), 반영을 막는 쪽으로 작동한
  전력이 있다. 배포 횟수는 `deploymentEnabled`로만 조절한다.

### 1-3. 브랜치 차단 설정이 실제로는 안 걸려 있었음 (7/13)

- **증상** — `main` 외 브랜치는 배포를 막아뒀는데 실제로는 배포가 돌았다.
- **원인** — 차단 패턴을 `*`로 썼는데, 이 패턴은 **슬래시를 건너뛰지 못한다.**
  그래서 `claude/무언가` 형태의 브랜치명이 전혀 매칭되지 않았고, 매칭되는
  규칙이 없으면 "배포 허용"이 기본값이라 그대로 배포됐다.
- **해결** — `**`로 변경(슬래시 포함 여부와 무관하게 매칭).

## 2. 사진이 잘못 잘린다 (그리드 검출)

> **이 분류가 가장 많고, 가장 여러 번 재신고됐다.** 원인이 매번 달랐는데도
> "저번에 고친 그 부분이겠지" 하고 같은 코드만 다시 보다가 시간을 날린 적이
> 여러 번이다. 재신고가 오면 **이전 수정이 진짜 원인이었는지부터 다시 의심한다.**

### 2-1. 가로폭이 1000px이 아니면 그리드를 아예 못 잡음 (7/13)

- **원인** — 칸 위치를 찾는 기준 좌표가 1000px 기준 **고정 숫자**였다.
- **해결** — 이미지 실제 폭에 비례해 계산하도록 변경.

### 2-2. 5열 중 한 열이 통째로 누락 (7/13)

- **원인** — 열을 찾을 때 **딱 한 지점만** 봤는데, 하필 그 자리에 흰 배경
  상품(스티커·아이콘류)이 있으면 "여기 상품 없음"으로 판정했다.
- **해결** — 여러 행 × 여러 높이를 교차로 시도해 가장 많이 잡힌 결과를 채택.

### 2-3. 카드 크기를 잘못 추정해 옆 칸을 침범 (7/14)

- **원인** — 칸 **시작 위치**는 실제로 스캔해 정확했지만, 칸 **크기**는 이미지
  폭 비율로 추정만 했다. 실제 캡처는 폭에 정비례하지 않아서 어긋났다.
- **해결** — 스캔으로 찾은 실제 길이의 중앙값을 카드 크기로 사용.
- **교훈** — "개수는 맞는데 잘림이 이상하다"면 **위치가 아니라 크기 계산**을 본다.

### 2-4. 한 장의 사진이 두 칸으로 쪼개짐 (8/11)

- **원인** — 카드 안에 캐릭터가 여럿 있는 콜라주형 사진은 캐릭터 사이에 흰
  배경이 비치는데, 그 **좁은 틈을 칸 경계로 오인**했다.
- **해결** — 흰 구간이 일정 길이(`minGapPx`, 기본 8px) 이상 이어질 때만 경계로 인정.

### 2-5. 특정 줄만 사진이 옆으로 밀려 잘림 (8/21)

- **원인** — 열 위치를 **한 줄에서만 찾아 모든 줄에 재사용**하고 있었다. 실제
  스토어 페이지는 줄마다 좌측 여백이 몇 px씩 달라서, 샘플로 뽑힌 줄이 아닌
  나머지가 어긋났다. 같은 결함이 **반대 방향(행)에도** 있었다.
- **해결** — 줄마다 열을 다시 검출(`colsByRow`), 열마다 행을 다시 검출(`rowsByCol`).
- **왜 "다시 검출"로도 안 고쳐졌나** — 그 버튼은 흰색 판정 기준만 바꿀 뿐
  **재사용 구조 자체는 그대로**라, 몇 번을 눌러도 똑같이 재현됐다.

### 2-6. 특정 열만 계속 어긋남 (8/21)

- **원인** — 위 수정에서 열마다 행을 다시 찾을 때 **그 열의 왼쪽 경계선**에서
  스캔했는데, 거기는 사진과 흰 배경이 만나는 바로 그 자리라 테두리가 둥글거나
  그림자가 있으면 흰색으로 잘못 읽혔다.
- **해결** — 경계가 아니라 **사진 한가운데**에서 스캔.

### 2-7. 1열만 계속 어긋남 — 진짜 원인 (8/21)

- **원인** — 실제 스토어 캡처에는 상품 그리드를 감싸는 **프레임(테두리)**이 있고,
  프레임과 1열 사진 사이 흰 여백이 8px보다 좁았다. 그래서 **프레임과 1열이 한
  칸으로 합쳐져** 1열 시작점이 "사진 왼쪽"이 아니라 "프레임 왼쪽"으로 잡혔다.
  칸 너비는 나머지 4열 기준의 정상값이라, 1열만 프레임을 물고 오른쪽이 잘렸다.
- **해결** — 열 간격의 중앙값으로 이상적인 격자를 계산해, 거기서 크게 벗어난
  열만 제자리로 보정(`snapColsToLattice`).
- **교훈** — **"항상 같은 자리만" 어긋나면 데이터(캡처) 쪽 특징을 의심한다.**
  무작위가 아니라 고정된 위치라는 건 알고리즘이 매번 같은 판단을 한다는 뜻이다.

### 2-8. 잘려나간 부분은 되살릴 수 없다 (9/15, 기능 추가로 해결)

- **증상** — 부시로드 카피라이트 표기나 상품 일부가 크롭 경계에 걸려 잘림.
- **중요한 점** — 이미 잘라둔 사진 안에서 확대/축소하면 **경계 밖 픽셀은 애초에
  데이터가 없어서** 절대 되살아나지 않는다.
- **해결** — 조정할 때마다 **원본 스크린샷에서 범위를 다시 잡아 자른다.**
  2단계에서 `Ctrl(⌘)+휠` 확대/축소, 드래그로 위치 이동, `↺`로 원래대로.

## 3. 최종 이미지가 이상하다

### 3-1. 미리보기 페이지 구분이 실제와 달랐음 (8/20)

- **증상** — 미리보기에서 "1p" 박스에 있던 카드가 실제로는 2페이지로 나감.
- **원인** — 미리보기는 25개씩, 실제 출력은 20개씩 끊고 있었다. 항목이 47개면
  12장이 어긋났다.
- **해결** — 미리보기도 20개 기준으로 통일.

### 3-2. 긴 IP명이 카드 밖으로 튀어나감 (8/13)

- **원인** — 자동 2줄 분할이 **첫 줄만 폭을 검사**하고 둘째 줄은 나머지를 통째로
  넣었다.
- **해결** — 두 줄 각각 폭에 맞게 줄임.

### 3-3. 맨 아랫줄 상품명·가격이 통째로 사라짐 (9/16)

- **증상** — 마지막 줄은 사진만 나오고 글자가 아예 안 보임.
- **원인** — 헤더 배너가 크거나 상품명이 두 줄인 카드가 있으면 4번째 줄이
  **페이지 밖으로 밀려났다.** (헤더 216px + 두 줄 조건에서 68px 초과 — 글자
  영역 73px이 거의 다 사라지는 수준)
- **해결** — 20개로 채웠을 때 넘치면 **한 장에 15개로 자동 조정**하고, 왜 장수가
  늘었는지 화면에 이유를 표시. 넘치지 않으면 예전과 완전히 동일.

## 4. AI 인식

### 4-1. 결과가 엉뚱한 사진에 쓰임 (7/22)

- **증상** — AI 비용은 나가는데 결과가 반영이 안 되는 것처럼 보임.
- **원인** — 결과를 **위치(순번)** 기준으로 항목에 썼는데, 다른 사진을 다시
  크롭하면 항목 순서가 밀려서 그 순번이 엉뚱한 곳을 가리켰다.
- **해결** — 순번이 아니라 **항목 고유 id** 기준으로 찾도록 변경.

### 4-2. "라벨만 재인식"이 지저분한 원본 상품명을 그대로 베낌 (7/14)

- **원인** — 그 기능이 "보이는 글자 그대로 옮겨 적기"로만 설계돼 있었다.
- **해결** — "AI로 채우기"와 동일한 IP명 추출 규칙 적용(사진만 안 보낼 뿐 품질 동등).

### 4-3. 느릴 때 전체가 멈추고 엉뚱한 안내가 뜸 (10/2)

- **증상** — `AI로 채우기 실패: signal timed out`
- **원인** — 서버는 멀쩡했다(실제 크기 이미지로 7~9초). 일시적으로 느려졌을 때
  60초 제한에 걸린 것. 그런데 **동작이 두 가지로 나빴다**:
  ① 안내가 "백엔드가 배포되어 있지 않다면 정상입니다"였는데 백엔드는 멀쩡했고,
  영어 원문이 그대로 노출됐다.
  ② 상품을 5개씩 나눠 여러 번 호출하는데 **중간 하나가 끊기면 나머지는 시도도
  안 하고 멈췄다** — 20개 중 앞쪽 5개만 채워진 채 끝났다.
- **해결** — 실패해도 나머지 묶음은 끝까지 진행하고 어느 묶음이 왜 실패했는지
  안내. 자동 1회 재시도, 대기 시간 60초 → 120초.

## 5. 상품이 중복되거나 안 지워진다

### 5-1. 상품이 두 벌로 쌓이고 초기화해도 남음 (10/28)

- **증상** — "이미지를 하나 넣었는데 중복 생성되고, 첫 페이지에서 초기화해도 그대로"
- **재현 경로**

  ```
  이전 작업 불러오기(15개 복원) → 사진을 다시 올려 크롭 → 30개
  → "이 사진 삭제"로 초기화 → 15개가 그대로 남음
  ```

- **원인(두 겹)** — 세 기능이 **각자 설계대로 동작하는데 겹치면** 사고가 났다.
  - 크롭은 원래 "이미 담긴 것 뒤에 이어서 추가"하는 동작인데(사진 여러 장 지원),
    **화면에 몇 개가 담겨 있는지 안 보여서** 쌓이는 걸 알 수 없었다.
  - "이 사진 삭제"는 **그 사진이 만든 항목만** 지우는데, 이전 작업에서 이어온
    항목은 어떤 사진에도 속하지 않아 아무리 지워도 남았다.
- **해결** — 1단계에 담긴 상품 수를 항상 표시(이어온 것은 개수 별도 표기),
  담긴 게 있는 상태에서 크롭하면 먼저 확인받기, **"전부 비우고 처음부터"** 버튼 추가.

### 5-2. 이전 작업을 불러온 사진은 확대/축소가 먹통 (10/28)

- **증상** — 커서는 끌 수 있는 손 모양인데 끌어도 아무 반응이 없고 안내도 없음.
- **원인** — 조정 가능 여부를 **"원본 표시(`cropSrcId`) 값이 있는가"** 로 판정했는데,
  이전 작업을 불러오면 **그 값까지 그대로 복원된다.** 없는 건 원본 사진이지 값이
  아니다. 그래서 "조정 가능"으로 잘못 판정했다.
- **해결** — 판정 기준을 **"그 원본이 지금 메모리에 있는가"**(`canAdjustPhoto`)로 변경.
- **교훈** — 9월에 이미 "원본이 없으면 안내한다"고 고쳐뒀는데도 이 경로에서는
  안 떴다. **그때 검증을 실제 "이전 작업 불러오기" 경로가 아니라, 값을 일부러
  지운 인위적인 데이터로 했기 때문이다.**

## 6. 눌러도 반응이 없다

### 6-1. 실패해도 화면에 아무 표시가 없던 곳 3군데 (9/15)

- **증상** — 사전 저장·사진 업로드·페이지 생성이 실패하면 콘솔에만 에러가 남고
  화면엔 아무 반응이 없었다.
- **해결** — 셋 다 실패 시 이유를 안내하도록 변경.
- **같이 고친 것** — 사진 여러 장 중 하나가 손상되면 **멀쩡한 것까지 전부 안
  올라가던** 문제(이제 정상인 것은 올라가고 실패 개수만 안내).

### 6-2. 사진 드래그가 처음 몇 px만 움직이고 멈춤 (9/15)

- **원인** — 썸네일을 갱신할 때 이미지 요소를 **새로 만들어 갈아끼웠는데**, 그
  요소가 바로 드래그를 붙잡고 있던 주체라 교체되는 순간 잡고 있던 게 풀렸다.
  30px을 끌어도 첫 6px만 반영됐다.
- **해결** — 요소를 교체하지 말고 **그림(src)만 바꾸기.**

### 6-3. "다시 검출"을 눌러도 아무 일도 안 일어남 (7/13, 7/14 두 건)

- **원인 ①** — 크롭 확정 후에는 확인 버튼이 영구 비활성이라, 다시 검출해도
  **반영할 방법 자체가 없었다.** → 재확정 가능하게 변경(데이터 유실 경고 후).
- **원인 ②** — 검출 로직이 완전히 결정론적이라 **같은 이미지는 몇 번을 눌러도
  똑같은 결과**가 나왔다. → 판정 기준이 다른 3가지 변형을 번갈아 시도하도록 변경.
  + 클릭 즉시 눈에 보이는 피드백 추가(실행됐는지 알 수 없던 문제).

### 6-4. 안내 문구가 원인을 잘못 짚음 (7/14)

- **증상** — 텍스트 잠금 상태인데 "전부 이미 등록돼 있다"는 엉뚱한 안내.
- **해결** — 실제 원인(잠금 때문에 IP명을 못 채움)을 구분해 안내 + 해제 방법 포함.

## 7. 글자·버튼이 미묘하게 다르다

### 7-1. 버튼 글자만 커 보임 (9/2)

- **원인** — 버튼 기본 스타일을 지우려고 `font: inherit`를 썼는데, 이 한 줄이
  **글자 크기까지 같이 되돌려서** 12px이 16px이 됐다.
- **해결** — `font-family: inherit`로 바꿔 글꼴만 물려받기.
- **교훈** — 스크린샷만으로는 이런 미세한 차이를 못 잡는다. **실제 계산된 값을
  확인**해야 한다.

### 7-2. 2줄 IP명에서 태그 배지가 엉뚱한 곳에 붙음 (7/23)

- **원인** — 배지를 **첫 줄 끝**에 붙여서 IP명 중간에 낀 것처럼 보였다.
- **해결** — 마지막 줄 옆에 붙이도록 변경.

## 되풀이된 교훈

1. **"고쳤는데 그대로"면 코드보다 반영 경로를 먼저 본다.** 배포 실패는
   사이트 응답만 봐서는 "배포가 안 돈다"와 구분되지 않는다.
2. **같은 증상이 재신고되면 이전 수정이 진짜 원인이었는지부터 의심한다.**
   그리드 잘림은 원인이 매번 달랐는데 같은 코드만 다시 보다 여러 번 놓쳤다.
3. **"항상 같은 자리"에서 생기는 문제는 데이터 쪽 특징을 의심한다.**
   무작위가 아니라는 건 알고리즘이 매번 같은 판단을 한다는 뜻이다.
4. **검증은 실제 사용 경로로 한다.** 값을 손으로 만들어 넣은 인위적 데이터로
   테스트하면, 정작 가장 흔한 경로가 검증에서 빠진다(5-2가 그 사례).
5. **기능 하나씩만 보면 못 잡는 버그가 있다.** 각자 설계대로 동작하는 기능들이
   겹칠 때만 터지는 문제는, 사용자가 실제로 밟는 순서대로 이어서 돌려봐야 나온다.
6. **스크린샷으로 "된 것 같다"고 판단하지 않는다.** 미세한 차이와 잘림은
   실제 값·픽셀을 확인해야 드러난다.
