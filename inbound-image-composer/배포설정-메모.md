# 배포 설정 메모 (inbound-image-composer)

`vercel.json`에 대한 설명을 **여기에** 둔다. 설정 파일 안에 주석을 넣으면 안 되기
때문이다 — JSON에는 주석 문법이 없고, Vercel은 모르는 속성이 하나라도 있으면
설정 파일을 통째로 거부해서 **배포가 실패한다.**
(실제로 그 사고가 있었다: `트러블슈팅-inbound-image-composer.md` 1-1 참고)

## 자동 배포 켜고 끄기

`git.deploymentEnabled.main`

- **`false`** — 평소 상태. 자주 고치지 않는 동안 배포 한도를 아끼려고 꺼둔다.
  **끈다고 서비스가 멈추는 게 아니다.** 이미 올라가 있는 사이트와 API는 그대로
  돌아가고, 멈추는 건 "새 코드가 사이트에 반영되는 것"뿐이다.
- **`true`** — 고친 코드를 반영해야 할 때.
  **코드 수정과 같은 push에 함께 올린다.** 따로 올리면 배포가 2번 돌아서
  아끼려던 한도를 오히려 더 쓴다.

작업이 끝나면 다시 `false`로 되돌린다(끄는 push는 배포를 만들지 않아 한도를
쓰지 않는다).

## 반영됐는지 확인하는 법

사이트 응답만 보면 "배포가 안 돎"과 "배포가 실패함"을 구분할 수 없다.
**배포 성공 여부를 먼저 본다.**

```
gh api repos/pw-cpteam-ctrl/ccode/commits/<커밋>/status
```

`inbound-image-composer` 항목의 `state`가 `success`인지 확인한다.
그 다음 실제 반영을 본다.

```
curl -s https://inbound-image-composer.vercel.app/app.js | grep -c <고친함수이름>
```

## ignoreCommand를 쓰지 않는 이유

예전에는 "이 폴더가 안 바뀌었으면 빌드를 건너뛴다"는 `ignoreCommand`를 넣어뒀다.
두 가지 이유로 뺐다.

1. **한도를 아끼지 못한다.** 건너뛰어도 배포가 만들어진 뒤 취소되는 방식이라
   1회로 집계된다(Vercel 문의로 확인).
2. **반영을 막는 쪽으로 작동한 전력이 있다.** 경로를 잘못 줘서 모든 배포를
   영구히 건너뛰게 만든 사고가 두 번 있었다(트러블슈팅 1-2).

배포 횟수는 `deploymentEnabled`로만 조절한다.
